# Requirements: Accrue v1.66

**Milestone:** Admin Usability and Visual Consistency
**Defined:** 2026-10-11
**Authority:** Owner approved the feedback-led existing-Admin scope and automatic continuation. Canonical brief: [owner feedback](notes/2026-10-11-admin-owner-feedback.md). Approval covers the requirements below as concrete expressions of that scope; new capabilities remain excluded.

## v1.66 Requirements

### Rendered baseline and evaluation

- [x] **BASE-01**: Operators' existing Admin routes and materially distinct list/detail/overlay states are enumerated in a coverage ledger, with every entry inspected or explicitly accounted for.
- [x] **BASE-02**: Reviewers can inspect representative wide/narrow and light/dark captures with route, state, scenario, revision and served-asset provenance; unseen pages receive bounded Impeccable review before changes are selected.
- [x] **DEMO-01**: Reviewers can evaluate plausible ordinary billing situations without adversarial phase-number/long-name fixtures dominating the feedback preview; money, dates, relationships and processing history are checked for internal consistency.
- [ ] **DEMO-02**: Reviewers can reproduce the agreed ordinary, empty, failure and boundary evaluation states through documented existing or minimal host-only tooling without destructive implicit resets of the current preview.

### Shared collection interactions

- [ ] **FILTER-01**: Operators can distinguish page/view selection from applied constraints through one coherent shared filter region, visible field labels, compact removable chips and a predictable reset action.
- [ ] **FILTER-02**: Operators can select useful combinations of statuses on existing multi-status journeys, with controls, URL, query and displayed results agreeing, including default invoice and subscription queues.
- [ ] **FILTER-03**: Operators can use a general search whose stated capabilities match its predicates, with exact relationship filters discoverable and explicitly named instead of duplicate search-like fields.
- [ ] **SEARCH-01**: Operators can open and use a compact global billing search dialog with one unambiguous active result across mouse and keyboard, truthful loading visibility and usable narrow/wide composition.

### Shared reading and investigation

- [ ] **TABLE-01**: Operators can scan primary identity, significant state, money and dates without concatenated names/IDs, excessive row height or long-content displacement; shared tables retain full exact identifiers and useful responsive priorities.
- [ ] **TIME-01**: Operators can read timestamps in a clearly identified local timezone and copy an exact UTC value with keyboard/touch access and truthful success/failure feedback; any display preference is shared rather than repeated per row.
- [ ] **LANG-02**: Operators encounter consistent concrete destination names, headings, breadcrumb labels and task-specific help, with contextual navigation justified by the record or investigation task.
- [ ] **STATE-02**: Operators see restrained semantic attention/status presentation tied to actual evidence and useful next steps; missing history, fee fields, plan data or snapshots never imply unsupported success, failure, pending work or misconfiguration.

### Details and analytics

- [ ] **DETAIL-01**: Operators can understand webhook identity, observed processing state and replay availability in a deliberate hierarchy, with explicit disclosures, coherent empty histories and readable payload controls preserving exact evidence.
- [ ] **DETAIL-02**: Operators can investigate existing detail pages and action reviews with shared readable metadata/copy conventions while authorization, ownership, confirmation, step-up and accepted-versus-completed boundaries remain intact.
- [ ] **METRIC-01**: Operators can compare recovery metrics by currency without prose masquerading as deltas, duplicated definitions or misleading cash/churn claims; coverage dates and UTC windows are distinct from explicitly labeled help.

### Integrated acceptance

- [ ] **PROOF-01**: Reviewers can trace every accepted owner finding to its shared/page-specific fix or justified disposition and its executed owning checks, including rendered confirmation of changed surfaces and evidence tied to the tested revision.

## Future Requirements

- Rich interactive scenario selection UI remains deferred unless minimal evaluation tooling cannot meet DEMO-02. No production Admin scenario picker is approved.
- A second owner feedback pass may identify further refinements; this milestone does not predict or certify subjective acceptance of unseen results.

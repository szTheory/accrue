# Phase 206: Code Review Report

**Reviewed:** 2026-07-04T21:23:15Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Reviewed the Phase 206 forward-only finding-ledger stack: the shared lifecycle/fold module
(`ratchet-ledger.js`), the Opus adversarial-verifier panel (`ratchet-verify.mjs`), the
deterministic gate reducer (`phase-ratchet-ledger.mjs`), the independent CI re-verifier
(`scripts/ci/verify_ratchet_ledger.mjs`), and the `accrue_admin/package.json` script wiring.
`region-tags.js` was also read (imported by every file above) to confirm identity-boundary
behavior referenced by `assertIdentity`/`buildValidatedCandidateMap`.

The self-test discipline is thorough and the three-file independence design (shared fold vs.
duplicated recompute) is sound in principle. However, two issues undermine the actual
correctness/security guarantees the phase is supposed to deliver: (1) an unsanitized `png_ref`
is joined into a filesystem path and its contents are base64-encoded and sent to an external
API with no containment check — a path-traversal/exfiltration risk; and (2) the panel's vote
aggregation (`medianClamp`) has a `median === 0` kill-check that silently fails open when the
model returns fewer than 2 role verdicts (an array-index/falsy-comparison bug), because the
JSON tool schema does not enforce exactly 3 role entries. This lets a malformed/incomplete
panel response get written into the append-only, forward-only ledger as a "confirmed" finding
with an `undefined` (dropped) severity — a data-integrity defect in the exact mechanism this
phase exists to make trustworthy.

Several further robustness/maintainability gaps are noted below (missing lifecycle-transition
validation, missing `appendReopened` helper for the declared "reopen" event, hand-duplicated
closed-enum arrays with no cross-check, inconsistent CLI error handling, and an unused
dimension-validation guard).

## Critical Issues

### CR-01: Unsanitized `png_ref` path used to read and exfiltrate arbitrary local files to the Anthropic API

**File:** `accrue_admin/e2e/ratchet/ratchet-verify.mjs:339-346`
**Issue:** `verifyImageGroup()` builds the on-disk image path as `path.join(RESULTS_DIR, pngRef)`
where `pngRef` comes straight from a collapsed candidate row's `png_ref` field (originally
written by the Phase-205 proposer into `candidates.ndjson`, an ordinary NDJSON file with no
schema enforcement at read time here). `png_ref` is explicitly excluded from the identity
re-derivation performed by `assertIdentity()`/`buildValidatedCandidateMap()` (it is not one of
the fields folded into `claim_key`), so nothing in this file validates that `png_ref` stays
inside `RESULTS_DIR`. A value such as `"../../../../.env"` or `"../../config/runtime.exs"`
would resolve outside `RESULTS_DIR`, get read via `fs.readFileSync(abs, "base64")`, and — unless
it happens to exceed the 5 MB cap — get embedded as an `image` content block and sent directly
to the Anthropic API in `verifyImageGroup`'s `client.messages.create(request)` call. Given
`candidates.ndjson` is generated by a separate script (not in this review's scope) and is not
re-validated here, this is a live path-traversal / potential secret-exfiltration vector, not a
purely theoretical one — it only takes a bug or a compromised/adversarial proposer stage to
trigger it, and the harness sends the file bytes off-box.
**Fix:**
```js
function resolveWithinResultsDir(pngRef) {
  const abs = path.resolve(RESULTS_DIR, pngRef);
  const root = path.resolve(RESULTS_DIR) + path.sep;
  if (!abs.startsWith(root)) {
    throw new Error(`png_ref escapes RESULTS_DIR: ${JSON.stringify(pngRef)}`);
  }
  return abs;
}

// in verifyImageGroup:
let abs;
try {
  abs = resolveWithinResultsDir(pngRef);
} catch (err) {
  console.warn(`[ratchet-verify] Rejecting unsafe png_ref: ${err.message} — skipping`);
  return [];
}
```

### CR-02: `medianClamp()` silently confirms findings with fewer than 2 panel role votes, writing `severity: undefined` into the forward-only ledger

**File:** `accrue_admin/e2e/ratchet/ratchet-verify.mjs:79-86, 148-183, 252-286`
**Issue:** `PANEL_TOOL.input_schema.properties.verdicts.items.properties.roles` (lines 163-176)
declares `roles` as an `array` of role-verdict objects but sets no `minItems`/`maxItems` — the
strict tool schema only constrains item *shape*, not *count*. `medianClamp(buckets, ...)`
(lines 79-86) computes `const median = ranks[1];` and gates on `if (median === 0) return
{confirmed: false, severity: null};`. If the model ever returns 0 or 1 role verdicts for a
`finding_id` (truncated output, a refusal, or any non-conforming-but-schema-legal response),
`buckets` has length < 2, so `ranks[1]` is `undefined`. `undefined === 0` is `false`, so the
kill-check does **not** fire — the function falls through to `Math.min(undefined, proposerRank)`
(`NaN`) and `RANK_BUCKET[NaN]` (`undefined`), returning `{confirmed: true, severity: undefined}`.
Back in `confirmAndWrite()` (lines 252-286), this passes the `!confirmed` gate and (unless the
candidate's own `justification_token` happens to be inadmissible, an unrelated check) proceeds
to `ratchetLedger.appendOpen(candidate, ledgerPath, {..., severity, ...})` with
`severity: undefined`. Since `JSON.stringify` drops keys whose value is `undefined`, the
resulting ledger row is written *without* a `severity` field at all — a "confirmed" `open`
finding with no severity, permanently appended to the append-only ledger this phase is meant to
gate on. It also silently distorts `computeCurrentOpenCounts()`'s per-lens `total` vs.
`minor`/`real` sub-counts (counted in `total`, in neither sub-bucket), which can trigger bogus
`count-increase` regressions downstream. None of the four `medianClamp` self-test cases
((ii-a)-(ii-d) at lines 466-493) exercise a `buckets.length < 3` input, so this gap is untested.
**Fix:** Enforce the cardinality in both the schema and the aggregation function:
```js
// PANEL_TOOL schema:
roles: {
  type: "array",
  minItems: 3,
  maxItems: 3,
  items: { /* ... */ },
},

// medianClamp:
function medianClamp(buckets, proposerSeverity) {
  if (buckets.length !== 3) {
    return { confirmed: false, severity: null };
  }
  const ranks = buckets.map((b) => BUCKET_RANK[b]).sort((a, b) => a - b);
  if (ranks.some((r) => typeof r !== "number")) {
    return { confirmed: false, severity: null };
  }
  const median = ranks[1];
  if (median === 0) return { confirmed: false, severity: null };
  const proposerRank = proposerSeverity === "real" ? 2 : 1;
  const clamped = Math.min(median, proposerRank);
  return { confirmed: true, severity: RANK_BUCKET[clamped] };
}
```

## Warnings

### WR-01: `appendLifecycleEvent` performs no lifecycle state-machine transition validation

**File:** `accrue_admin/e2e/ratchet/ratchet-ledger.js:302-339`
**Issue:** `appendLifecycleEvent(finding_id, ledgerPath, event, extraFields)` re-validates the
prior row's *identity* (`assertIdentity(prior)`) but never checks whether the requested `event`
is a legal transition from the prior row's current `status`. Nothing stops a caller from
appending `"resolve"` on a finding whose latest status is already `"verified-closed"`, or
`"suppress"` on one that is already `"resolved"`, or bouncing a finding between statuses
repeatedly. Given the whole point of this module is to be the sole trusted writer enforcing the
D-38 lifecycle vocabulary, the absence of a transition table is a real integrity gap — a caller
bug (in the not-yet-built Phase 207 orchestration) could silently corrupt "terminal" states with
no detection here or in the fold()/verify tooling (both treat the *last* row as ground truth
with no legality check).
**Fix:** Add an explicit transition table and validate before writing, e.g.:
```js
const LEGAL_TRANSITIONS = {
  open: ["resolve", "suppress"],
  resolved: ["verify-close", "reopen"],
  "verified-closed": ["reopen"],
  suppressed: ["reopen"],
};
function appendLifecycleEvent(finding_id, ledgerPath, event, extraFields = {}) {
  const status = EVENT_STATUS[event];
  if (!status) throw new Error(`appendLifecycleEvent: unrecognized event ${JSON.stringify(event)}`);
  const rows = readLedgerRows(ledgerPath);
  const prior = latestRowForFindingId(rows, finding_id);
  if (!prior) throw new Error(`appendLifecycleEvent: no existing row found for finding_id=${JSON.stringify(finding_id)}`);
  if (!LEGAL_TRANSITIONS[prior.status]?.includes(event)) {
    throw new Error(`appendLifecycleEvent: illegal transition ${prior.status} -> ${event} for ${finding_id}`);
  }
  // ...
}
```

### WR-02: No `appendReopened()` helper — the declared "reopen" lifecycle event has no validated write path

**File:** `accrue_admin/e2e/ratchet/ratchet-ledger.js:58-59, 78-85, 620-634`
**Issue:** `EVENT_TYPES` (line 59) and `EVENT_STATUS` (lines 78-85) both include `"reopen"` as
part of the closed lifecycle vocabulary, but the module only exports `appendOpen`,
`appendResolved`, `appendVerifiedClosed`, and `appendSuppressed` (module.exports, lines
620-634) — there is no `appendReopened`. `appendLifecycleEvent` (the internal implementation
that would support it) is not exported either. Every other event in the vocabulary has a safe,
identity-re-validating, `justification_token`/`suppressed_reason`-gated wrapper; "reopen" does
not. Any future legitimate reopen (the exact scenario `checkReopenMarkers`/`reopen-markers.ndjson`
in `phase-ratchet-ledger.mjs` is built to police) has no sanctioned way to be appended through
this module — it would have to be hand-constructed as a raw NDJSON row, bypassing the seq
computation, identity re-validation, and carry-forward logic this module otherwise guarantees.
**Fix:** Add `appendReopened(finding_id, ledgerPath, extraFields)` mirroring the other three
wrappers, and export it, or explicitly document (as is done for `--freeze`/Phase 208) that this
is intentionally deferred to a later phase.

### WR-03: `GUARD_HOME_SPECS`/`LENS_KEYS` closed-enum arrays are hand-duplicated with no cross-check that the two copies stay in sync

**File:** `accrue_admin/e2e/ratchet/phase-ratchet-ledger.mjs:56-61`, `scripts/ci/verify_ratchet_ledger.mjs:70-90`
**Issue:** Both files independently define identical literal `GUARD_HOME_SPECS` (4-path
allowlist) and `LENS_KEYS`/`LENS_KEYS`-equivalent (7-value) arrays, by design, for genuine
code-path independence (per both files' own docstrings). However, no test in either self-test
suite asserts that the two copies remain byte-identical. If a future phase (e.g., 207's
guard-minting work) adds a 5th guard-home spec to the reducer's array and forgets to update the
CI verifier's copy (or vice versa), the "independent re-verification" guarantee silently breaks:
the deterministic reducer would accept a guard_ref the CI verifier rejects (or vice versa),
and nothing catches the divergence until it manifests as an unexplained CI failure/pass
mismatch.
**Fix:** Add a cheap cross-file self-test assertion (e.g., in `verify_ratchet_ledger.mjs`'s
`runSelfTest()`, dynamically `require`/read the sibling file's source and regex-extract its
`GUARD_HOME_SPECS` array, then `assertSelfTest` deep-equality) or extract both arrays into one
tiny shared constants module imported by both (acceptable exception to the "independence"
rule, since it's a static enum, not executable logic).

### WR-04: A single malformed `raised_by` value in `candidates.ndjson` aborts verification of the entire batch

**File:** `accrue_admin/e2e/ratchet/ratchet-ledger.js:136-149, 404-423`
**Issue:** `lensKeyFor(raisedBy)` throws on any unrecognized `lens_kind`/`persona_id` (by
design, to avoid silently corrupting DEDUP-03 counting). `collapseByFindingId()` calls it
inside a `.map()` (line 414) with no per-row try/catch. Since `ratchet-verify.mjs`'s `main()`
calls `ratchetLedger.collapseByFindingId(candidateRows)` (line 405) over the *entire*
`candidates.ndjson` file in one shot, a single corrupted or unexpectedly-shaped `raised_by`
value anywhere in that file (e.g., from an upstream proposer bug, or a hand-edited row) throws
an uncaught exception that aborts collapsing — and therefore verifying — every *other* valid
candidate in the run, not just the offending row. Given `candidates.ndjson` is bulk-produced by
an LLM-driven upstream stage, a single bad row taking down the whole verification pass is a
disproportionate blast radius for what should be an isolated data-quality problem.
**Fix:** Either validate/filter `candidateRows` before collapsing (drop and log offending rows
individually), or wrap the `lensKeyFor` call inside `collapseByFindingId`'s loop in a
per-row try/catch that skips and logs the bad row rather than propagating.

### WR-05: Inconsistent top-level error handling across the three CLI entry points

**File:** `accrue_admin/e2e/ratchet/phase-ratchet-ledger.mjs:607-625`, `accrue_admin/e2e/ratchet/ratchet-verify.mjs:686`, `scripts/ci/verify_ratchet_ledger.mjs:602-609`
**Issue:** `scripts/ci/verify_ratchet_ledger.mjs` wraps its `main()` call in a `try/catch` that
prints a clean `"verify_ratchet_ledger.mjs crashed: <message>"` and sets `process.exitCode = 1`.
Neither `phase-ratchet-ledger.mjs`'s `if (import.meta.url === ...) { main(); }` block nor
`ratchet-verify.mjs`'s bare `await main();` at end-of-file has equivalent protection. An
unexpected throw in either file (e.g., `fold()`'s tamper-evidence exception on a corrupted
ledger, or `regenerateBaseline()`'s frozen-baseline refusal error) surfaces in CI as a raw
Node stack trace / unhandled-rejection instead of the same clean, actionable failure message
the sibling verifier produces — an avoidable inconsistency for scripts that are explicitly
twinned by design elsewhere in this phase.
**Fix:** Wrap both entry points identically:
```js
if (import.meta.url === `file://${process.argv[1]}`) {
  try {
    main();
  } catch (error) {
    console.error(`phase-ratchet-ledger.mjs crashed: ${error.message}`);
    process.exitCode = 1;
  }
}
```

### WR-06: `assertDimension()` (the closed 12-value dimension enum guard) is never invoked anywhere in the ledger/verify/gate chain

**File:** `accrue_admin/e2e/ratchet/ratchet-ledger.js:216-232`, `accrue_admin/e2e/ratchet/ratchet-verify.mjs:224-240`
**Issue:** `region-tags.js` exports `assertDimension(d)` specifically to enforce the documented
"no 13th dimension" milestone guardrail, but `claimKey()` itself never calls it — dimension is
only interpolated via `String(dimension).padStart(2, "0")`. None of the four reviewed files
(`assertIdentity` in `ratchet-ledger.js`, `buildValidatedCandidateMap` in `ratchet-verify.mjs`,
or either gate script) call `assertDimension` before treating a row's `dimension` as trusted.
Since identity re-derivation only checks *self-consistency* (does the stored `claim_key` match
what `claimKey()` derives from the row's own fields), a row carrying a nonsensical dimension
(e.g., `13`, `0`, or a non-numeric string) passes `assertIdentity`/`buildValidatedCandidateMap`
without complaint as long as its own `claim_key`/`finding_id` were computed the same way — the
"exactly 12 rubric dimensions" invariant this phase's identity module is supposed to guarantee
is not actually enforced anywhere in the ledger-write or verification path.
**Fix:** Call `regionTags.assertDimension(candidate.dimension)` (or equivalent) inside
`assertIdentity`/`buildValidatedCandidateMap` before deriving `claim_key`, so a malformed
dimension is rejected rather than silently accepted as self-consistent.

## Info

### IN-01: No file locking around ledger append — safe only under the current strictly-sequential single-process usage

**File:** `accrue_admin/e2e/ratchet/ratchet-ledger.js:191-198, 234-237`
**Issue:** `nextSeq()`/`appendRow()` (via `appendOpen`/`appendLifecycleEvent`) re-read the
whole ledger file, compute the next `seq`, then `fs.appendFileSync`. This is race-free today
because `ratchet-verify.mjs`'s `main()` calls `confirmAndWrite` sequentially inside an
`await`-ed `for...of` loop (never `Promise.all`), so there is only ever one writer active at a
time. There is no code comment documenting this as a load-bearing invariant, so a future
refactor toward concurrent/parallel image processing (a reasonable-looking optimization) could
silently introduce duplicate/racing `seq` values without any test catching it until `fold()`'s
tamper-evidence check starts throwing.
**Fix:** Add an explicit code comment above `nextSeq`/`appendRow` noting that concurrent callers
against the same `ledgerPath` are unsafe, or add a simple advisory lock (e.g., `O_EXCL` lockfile)
if parallel verification is ever introduced.

### IN-02: `duplicate-of:<finding_id>` suppressed-reason suffix is never checked to reference a real, existing finding

**File:** `accrue_admin/e2e/ratchet/ratchet-ledger.js:151-160`
**Issue:** `isValidSuppressedReason()` accepts any string of the shape `duplicate-of:<suffix>`
as long as the suffix is non-empty — it does not check that `<suffix>` is a syntactically valid
`f-[0-9a-f]{16}` finding_id, nor that it references a finding that actually exists in the
ledger. A typo'd or dangling `duplicate-of:` reference is accepted silently.
**Fix:** Validate the suffix against the finding_id regex (`/^f-[0-9a-f]{16}$/`) and, where a
ledger is available, cross-check that the referenced finding_id exists among prior rows.

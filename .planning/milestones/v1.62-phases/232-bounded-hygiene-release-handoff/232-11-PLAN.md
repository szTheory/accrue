<objective>
Open one integration pull request a maintainer can actually review: risk first, every claim falsifiable,
the provenance-versus-behavior split stated, rollback in the body, and no unrelated scope.

Purpose: D-59, D-60, D-61. The failure mode to avoid is the wall-of-green-check-marks body, which
reviewers correctly learn to skim because it is unfalsifiable. The highest-leverage sentence in the body
is the one that tells a reviewer which branch to link and which branch to diff, because it is what
converts an unreviewably large change into a reviewable one.

Output: a committed pull-request body, an automated section-and-density contract over it, and one open
pull request.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| committed body file -> public pull request | Everything in the body becomes public and permanently visible, including anything pasted from a local shell. |
| reviewer attention -> change surface | A body that is unfalsifiable or oversized shifts the real review burden back onto a diff nobody can read. |
| open pull request state -> repeated runs | A re-run after an interruption can open a second competing pull request. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-232-11-01 | Information Disclosure | published pull request body | high | mitigate | Leak sweep for local path prefixes plus an adopter-name check over the committed body before publication, reusing an existing sanitization pattern; the body is reviewed at a maintainer checkpoint before opening. |
| T-232-11-02 | Repudiation | unfalsifiable claims | high | mitigate | The falsifiability check requires a command or a link on every outcome-asserting line and names the first offending line number. |
| T-232-11-03 | Tampering (with process) | duplicate or merged pull request | medium | mitigate | The open-pull-request count is checked before and after and asserted to be exactly one; merging is prohibited and asserted by the unmerged state. |
| T-232-11-04 | Spoofing (of a safety property) | strict flags on the body contract | medium | mitigate | Every accepted strict flag is wired to a comparison and named in the pass suffix; a run over an empty body fails. |
</threat_model>

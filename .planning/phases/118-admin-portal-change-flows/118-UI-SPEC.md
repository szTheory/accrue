# Phase 118 — UI Design Contract

> Visual and interaction contract for the subscription-change surfaces introduced in Phase 118 across **`accrue_admin`** and **`accrue_portal`**. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Provenance:** Pre-populated from `118-CONTEXT.md`, `117-CONTEXT.md`, `.planning/processor-support-matrix.md`, `accrue/guides/lifecycle_semantics.md`, the current admin/portal LiveViews, and the locked visual baseline in `101-UI-SPEC.md` plus `accrue_admin/assets/css/theme.css`. No new design system is introduced in this phase.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Phoenix LiveView + Tailwind + CSS variables; shadcn is not applicable) |
| Preset | not applicable |
| Component library | none; extend existing HEEx component patterns in `accrue_admin` and simple portal function components |
| Icon library | none required; inline SVG only for chevrons, disclosure arrows, and status affordances using existing 16-20px outline style |
| Font | System sans stack from `accrue_admin/assets/css/theme.css`: `system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` with existing mono fallback for references only |

### Design system continuity

This phase MUST inherit the existing Accrue semantic-token posture instead of inventing a new shell:

- `accrue_admin` continues using `--ax-*` semantic tokens.
- `accrue_portal` continues using `--ap-*` semantic tokens layered over the same locked `--accrue-*` brand tokens.
- Any new change-flow component must consume semantic variables only. No hard-coded hex values inside HEEx or Tailwind utilities except the already-established destructive color.
- Dark mode remains required on both surfaces and must follow the existing `data-theme="light|dark|system"` contract.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Badge padding, inline icon gaps, disclosure chevrons |
| sm | 8px | Form row gaps inside compact cards, helper-copy spacing |
| md | 16px | Default card padding blocks, label-to-input spacing, stacked action rows |
| lg | 24px | Section spacing inside the change shell, preview card padding |
| xl | 32px | Gap between workflow shell header, mode switcher, and result panels |
| 2xl | 48px | Separation between summary region and lower detail region |
| 3xl | 64px | Page-level vertical spacing between adjacent top-level cards on desktop |

Exceptions:

- Interactive controls must keep a 44x44px minimum hit area.
- Quantity steppers may render visually compact, but the tap targets for minus, plus, and direct quantity input must still meet 44x44px.
- Disclosure toggles for preview details may render as text-plus-chevron rows, but the whole row is the hit target.
- On mobile portal pages, page edge padding may collapse from 32px to 16px; internal component spacing does not change.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Typography rules:

- Use exactly two weights: `400` and `600`.
- Money, quantities, and renewal dates shown in comparison rows or preview summaries must use tabular numerals.
- Preview summary amounts use `Display` on portal and `Heading` on admin; invoice-line detail stays at `Body`.
- Helper and unavailable-state copy stays at `Body`, never smaller than 14px.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--ax-base)` / `var(--ap-base)` | Page background and default surface |
| Secondary (30%) | `var(--ax-elevated)` / `var(--ap-elevated)` | Change shell card, mode switcher surface, preview surface, inline unavailable panels |
| Accent (10%) | `var(--ax-accent)` / `var(--ap-accent)` | Active subflow selector, single primary CTA per step, focus ring, selected plan target |
| Destructive | `#B42318` light, `#FDA29B` dark readable pair | Destructive confirmations and hard error emphasis only |

Accent reserved for:

1. The selected subflow chip or segmented control item inside the admin change shell.
2. The selected target plan card or selected quantity mode in portal self-serve.
3. The primary action button for the current step: `Preview change`, `Apply change`, or `Confirm change`.
4. Focus-visible outlines and active input borders.
5. The preview summary delta badge when the value is neutral informational, not success or destructive.

Accent is not used for:

- Inline links in explanatory copy.
- Disabled or unavailable states.
- Destructive actions.
- Success or warning lifecycle badges.

Status color rules:

- Estimated charge uses accent plus explicit “Estimated charge” label; do not encode meaning by color alone.
- Estimated credit uses success token plus explicit “Estimated credit” label.
- Unavailable/provider-bound panels use warning-readable text on a muted elevated panel, not destructive red.
- Typed runtime failures and validation blockers use destructive color plus concrete next-step copy.

## Interaction Contract

### Shared shell posture

- The phase introduces one **conceptual** change-workflow family across admin and portal, but keeps actual mutations explicit.
- Preview is a separate step from commit wherever `preview_upcoming_invoice/2` is supported.
- Braintree never shows a fake preview control.
- Unsupported controls must remain visible as unavailable states with adjacent explanation, not silently disappear.

### Admin workflow

- Add one primary entry point labeled **Change subscription** on the subscription detail page.
- Opening the workflow reveals one unified shell with exactly three typed subflows:
  - `Plan`
  - `Quantity`
  - `Items`
- The shell uses a left-to-right or top-to-bottom staged layout:
  1. choose subflow
  2. enter change input
  3. review preview or direct outcome guidance
  4. confirm mutation
- `Plan` is available when the provider supports swap under the official contract.
- `Quantity` is available only for eligible single-item Stripe/Fake subscriptions.
- `Items` is operator-only and may expose add/remove/update-item controls, but must stay inside the admin shell with stronger warnings and more visible detail than the quantity flow.
- Admin preview details are expanded by default for supported preview flows.
- Admin Braintree unavailable states must explicitly mention:
  - preview unavailable
  - quantity unsupported
  - multi-item unsupported through Accrue
  - `:plan_resolver` requirement when swap is blocked by setup

### Portal workflow

- Portal subscription detail gains a self-serve **Change plan** entry point when the subscription is eligible.
- If the subscription is a simple single-item Stripe/Fake subscription, the same area may also show a **Change quantity** control.
- Portal must never expose broad item add/remove editing in this phase.
- Portal complex or multi-item subscriptions show an operator handoff panel instead of editable catalog controls.
- Portal preview details are collapsed by default behind a single disclosure row labeled **View estimate details**.
- Portal Braintree path is bounded:
  - allow direct plan swap only when the contract supports it
  - no preview affordance
  - no quantity control
  - no `:plan_resolver` terminology in customer copy

### Preview card family

- Preview UI uses a shared summary/detail component family across admin and portal.
- Summary-first content order is fixed:
  1. estimated immediate charge or credit
  2. next renewal amount
  3. effective timing or current-period impact
  4. preview disclaimer
- Detail region lists invoice-style lines from `UpcomingInvoice.lines`.
- Summary row labels must use outcome language, never raw API option names.
- Preview disclaimer text is always visible without disclosure.
- Final invoice language is forbidden; the label must say `Preview`, `Estimate`, or `Estimated`.

### Quantity interaction

- Quantity change is the lightest editable subflow.
- Prefer a minus button, inline numeric field, and plus button on portal; admin may use numeric input plus explicit update action.
- Quantity cannot drop below `1`.
- The preview CTA is disabled until the entered quantity differs from the current value.
- If the subscription shape is not single-item, show a non-editable explanation instead of a broken numeric control.

### Item-edit interaction

- Item edits are admin-only in this phase.
- Each item row must show price reference, quantity, and pending mutation intent.
- Add/remove actions require explicit row-level confirmation before the shell-level final confirm.
- Because item editing is higher risk, admin must show detail-expanded preview by default whenever preview is supported for the resulting mutation.

### Unavailable and setup states

- Unavailable states live inline in the workflow shell exactly where the user would expect the control or preview.
- Use warning styling, not hidden branches.
- Each unavailable state must answer two questions:
  - why this action is unavailable
  - what the user should do next
- Admin next steps may point to setup or operator workflow.
- Portal next steps may point to contacting support or managing the change through the account team/host app.

### Feedback and pending states

- Preview request pending state keeps the form visible and replaces the primary CTA label with `Loading preview...`.
- Commit pending state replaces the primary CTA label with `Applying change...`.
- On success, keep the shell mounted long enough to show the resulting state and success flash, then refresh the subscription summary.
- Validation errors render inline at field level plus a shell-level summary if the mutation cannot proceed.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Admin primary CTA | `Preview change` for Stripe/Fake preview-supported steps; `Apply change` for bounded Braintree direct swap |
| Portal primary CTA | `Preview change` for Stripe/Fake eligible self-serve flows; `Change plan` for direct bounded Braintree swap |
| Admin empty/unavailable heading | `This change isn't available for this subscription` |
| Admin empty/unavailable body | `Check the provider support, subscription shape, and required setup. Braintree swaps require :plan_resolver; quantity and multi-item changes are unsupported through Accrue.` |
| Portal empty/unavailable heading | `This change needs help from your team` |
| Portal empty/unavailable body | `This subscription can't be changed here. Contact support or manage the update in your account's billing workflow.` |
| Preview summary charge label | `Estimated charge` |
| Preview summary credit label | `Estimated credit` |
| Preview renewal label | `Next renewal` |
| Preview disclaimer | `Preview only — final billed amount may vary slightly.` |
| Portal error state | `We couldn't preview that change. Refresh and try again. If it still fails, contact support.` |
| Admin error state | `We couldn't apply that change. Review the provider requirements and try again.` |
| Destructive confirmation | `Remove item`: `Remove this item from the subscription? This changes the active billing setup immediately after confirmation.` |

Additional copy rules:

- Portal copy must stay product-facing and must not mention `:plan_resolver`, raw capability labels, or internal facade names.
- Admin copy may mention `:plan_resolver` and explicit provider constraints.
- Raw enum labels such as `create_prorations` or `always_invoice` must not appear in portal copy. Admin may surface them only as humanized labels.
- `Preview unavailable` copy must appear where the preview card would normally appear, not as distant page prose.

Primary labels by surface:

- Admin plan subflow, Stripe/Fake: `Preview plan change`
- Admin quantity subflow, Stripe/Fake: `Preview quantity change`
- Admin items subflow, Stripe/Fake: `Preview item changes`
- Admin Braintree swap: `Apply plan change`
- Portal plan flow, Stripe/Fake: `Preview change`
- Portal quantity flow, Stripe/Fake: `Preview quantity change`
- Portal Braintree swap: `Change plan`

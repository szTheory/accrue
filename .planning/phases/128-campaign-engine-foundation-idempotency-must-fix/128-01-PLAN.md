<objective>
Add a config-driven, NimbleOptions-validated multi-step dunning cadence under the existing `:dunning` key, with a default journey shipped ON by default (opt-out), two-layer validation (intra-list `{:custom}` + cross-field boot raise), and three namespaced accessors. This is the boot-time foundation every downstream task reads (DUN-01).

Purpose: The campaign worker, the pure resolver, and the webhook gate all consume `Accrue.Config.dunning_campaign_steps/0` and `dunning_campaign_enabled?/0`. The cross-field boot validator guarantees the final notice precedes the sweeper's grace→terminal action (`last_step.after_days <= grace_days`), so the cadence can never silently mis-fire.
Output: A modified `accrue/lib/accrue/config.ex` and a new test file `accrue/test/accrue/config_dunning_campaign_test.exs`.
</objective>

<interfaces>
<!-- Step keyword shape (D-04) — load-bearing contract consumed by Plans 03/05/06. -->
Each step is a keyword list: `[after_days: <non_neg_integer>, key: <atom>, template: <module/atom>]` — all three required.
- `after_days` is ABSOLUTE from campaign start, strictly increasing across the list, unique.
- `key` is required and load-bearing (becomes the `step_key` Oban-unique arg in DunningStep; a positional index would break uniqueness on reorder).
- `template` is an email module atom (e.g. `Accrue.Emails.InvoicePaymentFailed`).

Default journey `@default_dunning_steps` (D-01):
  step 1: [after_days: 0,  key: :reminder,        template: Accrue.Emails.InvoicePaymentFailed]
  step 2: [after_days: 5,  key: :action_required, template: Accrue.Emails.DunningActionRequired]
  step 3: [after_days: 12, key: :final_notice,    template: Accrue.Emails.DunningFinalNotice]

Accessors exported for downstream (D-07):
  dunning_campaign/0          -> keyword list (campaign config with own nested default)
  dunning_campaign_enabled?/0 -> boolean
  dunning_campaign_steps/0    -> [] when disabled, else the configured steps
</interfaces>

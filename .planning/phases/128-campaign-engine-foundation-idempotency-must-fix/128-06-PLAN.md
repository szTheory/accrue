<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stripe webhook → reducer → DB | `invoice.payment_failed` may re-fire concurrently/repeatedly; the reducer crosses into a DB write that elects the campaign start. Concurrent/duplicate webhooks are the threat. |
| recovery webhook → cancel query | A recovery transition triggers a bulk job cancel; a stale/out-of-order recovery must not cancel the wrong campaign. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-128-14 | Tampering / race (TOCTOU on first transition) | `maybe_bump_past_due_since/2` elector | mitigate | Concurrent `invoice.payment_failed` webhooks racing the first-transition anchor are resolved by the atomic `update_all WHERE is_nil(dunning_campaign_started_at)` (D-09) — DB-level exactly-one-winner, NOT advisory Oban unique. count==1 enqueues day-0; count==0 no-ops. Proven by the concurrent race test. |
| T-128-15 | Tampering (campaign restart/orphan/duplicate) | repeated failure webhooks in-window | mitigate | A later failure in the same window finds the anchor set -> count==0 -> no second campaign start (D-09); the day-0 step's D-16 unique is a second backstop. |
| T-128-16 | Tampering (stale recovery cancels fresh campaign) | `maybe_finalize_dunning_campaign/2` cancel query | mitigate | `Oban.cancel_all_jobs` is keyed on `campaign_started_at` (anchor value at recovery), so an out-of-order recovery for an old campaign cannot cancel a fresh re-lapse campaign's steps (D-12, Pitfall 3). Per-step cancel-guard (Plan 05) re-checks live state as backstop. |
| T-128-17 | DoS-adjacent (webhook hot-path SLO <100ms p99) | elector on the webhook path | mitigate | The elector is a single PK-indexed `update_all` (no held lock, no extra round-trips); the campaign enqueue is async via `Oban.insert`; no synchronous email send on the webhook path (RESEARCH Security Domain). |
| T-128-18 | DoS / cost (double day-0 email) | D-15 gate | mitigate | When the campaign is enabled the standalone `:invoice_payment_failed` dispatch is SKIPPED (REPLACE, not additive) so only campaign step-1 sends day-0 (Pitfall 2). |
| T-128-SC | Tampering | npm/pip/cargo installs | n/a | No package installs (Oban/Ecto already in mix.lock). |
</threat_model>

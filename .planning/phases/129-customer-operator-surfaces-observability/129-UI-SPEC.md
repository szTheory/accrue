# Phase 129 — UI Design Contract

> Visual and interaction contract for the two visual surfaces in Phase 129.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope of this contract

Phase 129 ships **two** visual surfaces over the Phase-128 dunning campaign engine. The third
deliverable (DUN-08 observability — ledger events + telemetry + recovered-vs-lost fold) is
**non-visual** and is out of UI-SPEC scope except where it feeds these surfaces.

| Surface | Req | Package | File | Render kind |
|---------|-----|---------|------|-------------|
| Customer recovery banner | DUN-06 | `accrue_portal` | `lib/accrue_portal/live/subscription_live.ex` (render region ~:153, before the first `portal-card`) | Conditional `<section class="portal-card">` in the existing LiveView render tree (D-09). No new route, no new layout slot. |
| Admin read-only dunning-state panel | DUN-07 | `accrue_admin` | `lib/accrue_admin/live/subscription_live.ex` (new `ax-card`, clone of related-billing :175-217 / timeline :449-460) | Read-only `<article class="ax-card">` (D-12). No actions, no mutations. |

**This phase invents no new design language.** Both packages already ship a mature, in-tree design
system. This contract **extracts the real tokens/classes** each surface must reuse and forbids any new
visual vocabulary. The portal and admin systems are *separate and intentionally different* (portal =
public-facing customer chrome; admin = operator dashboard chrome). Each surface obeys its own
package's system — they are documented separately below.

## Design System

> Two distinct, pre-existing in-tree design systems. NOT a shadcn / React / Vite project — the shadcn
> gate is **not applicable** (no `components.json`; the stack is Elixir/Phoenix/LiveView with
> `Phoenix.Component`/`~H` server-rendered templates). No component registry of any kind. No
> third-party blocks → registry vetting gate not run (nothing to vet).

| Property | accrue_portal (DUN-06) | accrue_admin (DUN-07) |
|----------|------------------------|------------------------|
| Tool | none (hand-authored CSS) | none (Tailwind preset + hand-authored `ax-*` CSS) |
| Preset | not applicable | `accrue_admin/assets/tailwind_preset.js` (token→utility map) |
| Component library | none — server-rendered `~H` `<section class="portal-*">` | none — server-rendered `~H` `<article class="ax-*">` + local function components (`KpiCard`, `TaxOwnershipCard`, `Timeline`) |
| Stylesheet (source of truth) | `accrue_portal/priv/static/accrue_portal.css` | `accrue_admin/assets/css/app.css` + `accrue_admin/assets/css/theme.css` |
| Theming | host-supplied brand CSS (`brand_css_path`) defines `--accrue-*`; package CSS consumes the tokens | `html.accrue-admin` scope; semantic `--ax-*` tokens + light/dark/system via `data-theme`; host brand injects `--ax-accent` (`layouts.ex:73`) |
| Icon library | none — text + emoji-free copy only | none — `.ax-status-dot` (CSS dot) is the only "icon"; no icon font |
| Font | `system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` (`accrue_portal.css:5`) | `--ax-font-sans: system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` (`theme.css:7`); `--ax-font-mono` for payloads |

**Hard rule for this phase:** the banner reuses existing `portal-*` classes; the panel reuses existing
`ax-*` classes. **Do not author new CSS, new tokens, or new utility classes.** If a needed treatment
(e.g. a warning-tone banner) is not expressible with an existing class, prefer the closest existing
class over inventing one; any genuinely unavoidable new class is a contract deviation that must be
flagged to the checker, not added silently.

## Spacing Scale

Both systems are on a 4px base. The contract for **new markup** must use only the tokens below.

### accrue_admin — `--ax-space-*` (theme.css:9-14)

| Token | Value | px | Usage in the dunning panel |
|-------|-------|----|-----|
| `--ax-space-xs` | 0.25rem | 4px | `.ax-eyebrow` bottom margin, chip/badge inner padding |
| `--ax-space-sm` | 0.5rem | 8px | `.ax-stack-sm` is `gap: var(--ax-space-md)`; sm reserved for tight rows |
| `--ax-space-md` | 1rem | 16px | default stack gap inside the card (`.ax-stack-md` / row spacing) |
| `--ax-space-lg` | 1.5rem | 24px | card internal padding rhythm |
| `--ax-space-xl` | 2rem | 32px | between-card gap (`.ax-page` / `.ax-stack-xl`) |
| `--ax-space-2xl` | 3rem | 48px | major section breaks (not needed by this panel) |

Radii: `--ax-radius-sm` 0.75rem (12px) · `--ax-radius-md` 1rem (16px) · `--ax-radius-lg` 1.5rem (24px).
The new `ax-card` inherits card radius from the existing `.ax-card` rule — do not set radius inline.

### accrue_portal — literal px in `accrue_portal.css`

The portal stylesheet predates a tokenized scale and uses **literal px values that are NOT all on the
8-point grid**. The banner must match the *existing* portal card it sits beside — it must NOT introduce
a fresh 8-point rhythm that visually clashes. The banner reuses `.portal-card` verbatim, so it inherits
these values automatically:

| Element (existing class) | Value | On 8-pt grid? |
|--------------------------|-------|---------------|
| `.portal-card` padding | 28px | no (registered exception) |
| `.portal-card` border-radius | 18px | no (registered exception) |
| `.portal-card` margin-bottom | 18px | no (registered exception) |
| `.portal-shell` padding | 32px 20px 64px | partial |
| `.portal-actions` / `.portal-nav` gap | 10px | no (registered exception) |
| button `padding` | 0 16px | yes |
| button `min-height` | 40px | yes |

**Exceptions (registered, intentional — do NOT "fix"):** the portal card's `28px / 18px / 18px` and the
`10px` action gap are pre-existing system values. The banner inherits them by reusing `.portal-card` and
`.portal-actions`; it must not override them to chase an 8-point ideal, because that would make the
banner visually inconsistent with every other card on the page. This is the established portal language,
not a defect this phase corrects.

## Typography

Reuse each system's existing type roles. No new sizes, no new weights. Both systems use exactly
**two weights** (400 regular, 600 semibold) and a 1.2/1.5 heading/body line-height split — already
compliant; this phase declares no new type.

### accrue_admin — dunning panel (from `app.css`)

| Role | Class | Size | Weight | Line height | Used for |
|------|-------|------|--------|-------------|----------|
| Card heading | `.ax-heading` | 1.25rem (20px) | 600 | 1.2 | panel title `<h3>` |
| Eyebrow | `.ax-eyebrow` | 0.875rem (14px) | 600 | 1.4 | uppercase kicker above the title |
| Label | `.ax-label` | 0.875rem (14px) | 600 | 1.4 | field labels ("Started", "Next action") |
| Body | `.ax-body` | 1rem (16px) | 400 (`--ax-muted`) | 1.5 | field values, state sentences |
| Status badge text | `.ax-status-badge` + `.ax-label` | 0.875rem (14px) | 600 | 1.4 | "Active" / "Inactive" campaign pill |

### accrue_portal — recovery banner (from `accrue_portal.css` + body defaults)

| Role | Class / element | Size | Weight | Line height | Used for |
|------|-----------------|------|--------|-------------|----------|
| Banner heading | `<h2>` inside `.portal-card` | browser `<h2>` (~1.5rem) | 600 (bold) | default | banner headline |
| Eyebrow (optional) | `.portal-eyebrow` | 0.75rem (12px) | 400 + 0.12em tracking, uppercase | default | optional kicker (`--accrue-cobalt`) |
| Body | `<p>` inside `.portal-card` | 1rem (16px, body default) | 400 | inherited | banner explanation |
| CTA label | `.portal-button-primary` text | `font: inherit` (16px) | 400 | — | "Update your payment method" |

> Body font-size baseline is the browser default (16px) set on `body` (`accrue_portal.css:1-6`); the
> portal does not declare a custom body size, so do not add one. The eyebrow (0.75rem) and the hosted
> label (0.875rem) are the only smaller sizes in the system — reuse them only if needed.

## Color

Both systems are 60/30/10-compliant **as already shipped**; this phase adds no new colors and reuses the
semantic role tokens. The accent (10%) is host-supplied and tightly reserved.

### accrue_admin — `--ax-*` semantic tokens (theme.css)

| Role | Token | Light value | Usage in the dunning panel |
|------|-------|-------------|-----|
| Dominant (60%) | `--ax-base` | `var(--accrue-paper)` (host) | page background behind cards |
| Secondary (30%) | `--ax-elevated` / `--ax-sunken` | `#ffffff` / `#f1f5f8` | the `ax-card` surface (the panel) |
| Accent (10%) | `--ax-accent` | host-injected (`#5D79F6` fallback, `layouts.ex:73`) | **focus ring + active-state only** — NOT used for static panel text |
| Body text | `--ax-muted` / `--ax-primary` | `#5d6a73` / `var(--accrue-ink)` | `.ax-body` values / `.ax-heading` |
| Success (status) | `--ax-success` / `--ax-success-readable` | `var(--accrue-moss)` / `#2f6b4f` | "campaign recovered/inactive-healthy" badge (`.ax-status-badge-moss`) |
| Warning (status) | `--ax-warning` / `--ax-warning-readable` | `var(--accrue-amber)` / `#7a4b00` | "campaign active / dunning in progress" badge (`.ax-status-badge-amber`) |
| Border | `--ax-border` / `--ax-border-strong` | `rgba(36,48,59,.12)` / `.24` | card + badge borders |

**Accent reserved for (admin):** focus-visible rings (`--ax-focus-ring`), the active sidebar/nav pill,
and `--ax-accent-readable` cobalt badge text. The dunning panel is **read-only** — it has no primary
action — so it uses **no accent fill at all**. Campaign state is conveyed by the **status-badge tone**
(amber = active dunning, moss = recovered/inactive, slate = no campaign), never by accent.

### accrue_portal — `--accrue-*` host brand tokens + literal hexes

| Role | Token / hex | Usage in the recovery banner |
|------|-------------|------|
| Dominant (60%) | `body` gradient `#f6f9fb → #eef4f6` | page background (inherited; do not change) |
| Secondary (30%) | `.portal-card` `rgba(255,255,255,.92)` | the banner surface |
| Accent / primary action (10%) | `.portal-button-primary` `#2f6e58` (green) on white | the **single** CTA button — reserved for the "Update your payment method" action |
| Body text | `var(--accrue-ink)` | banner heading + body |
| Secondary text | `var(--accrue-slate)` | de-emphasized copy, secondary button text |
| Eyebrow accent | `var(--accrue-cobalt)` | optional `.portal-eyebrow` kicker |
| Attention/error surface | `.portal-inline-error` `rgba(180,35,24,.06)` bg, `#8f2018` text, `#b14f2d` help | reuse ONLY if the banner needs an error-toned variant; default banner is a neutral `.portal-card` |

**Accent reserved for (portal):** the green `.portal-button-primary` is reserved for the **primary
positive action** only — here, the recovery CTA. The banner must surface **exactly one** primary CTA
(the update-payment-method link styled as `.portal-button-primary`); any secondary link uses
`.portal-button-secondary` (neutral grey). Do not introduce a second green button.

**Banner tone decision:** the recovery banner is **attention, not error**. Use a neutral `.portal-card`
container with a clear heading + the green primary CTA — this matches the portal's existing "card =
section" language and avoids the alarmist red `.portal-inline-error` treatment (which is reserved for
hard failures like a declined card-add submission). Set `role="alert"` (or `role="status"`) on the
`<section>` for assistive-tech without changing the visual tone.

## Copywriting Contract

**Hard requirement (D-13):** every operator string in the **admin panel** MUST route through
`AccrueAdmin.Copy` (add defs to `copy/subscription.ex` or a new `AccrueAdmin.Copy.Dunning` submodule,
`defdelegate` in `copy.ex`, call as `Copy.dunning_*()` in the template). A hardcoded operator string in
the admin template is a contract violation. The **portal** banner strings route through the existing
`AccruePortal.Copy` module the same way every other portal string does (see
`subscription_live.ex` — all visible text is `Copy.subscription_*()`).

The copy below is the **prescribed default wording**. Exact function names are planner's discretion
(per CONTEXT "Claude's Discretion"); the *strings* are the contract.

### accrue_portal — recovery banner (DUN-06)

| Element | Copy | Notes |
|---------|------|-------|
| Banner heading | `Your payment didn't go through` | plain, non-alarmist, customer voice |
| Banner body | `We couldn't process your most recent payment. Update your payment method to keep your subscription active.` | states the problem + the fix; no jargon ("dunning", "campaign", "past_due" never appear) |
| Primary CTA | `Update payment method` | verb + noun; matches the `card_expiring_soon.ex` email CTA wording verbatim so banner + email never diverge (a stated phase goal) |
| Provider-aware CTA target | Braintree → `<base>/payment-methods/new`; Stripe/others → `<base>/payment-methods` (in-portal list) or host-supplied update-PM URL | resolved off `@subscription.processor`, mirroring `card_expiring_soon.ex` `@update_pm_url`; the Stripe destination is a planner-discretion item (research A4 — default to the in-portal list) |
| Visibility gate | render when `Subscription.past_due?/1` OR `Subscription.dunning_campaign_active?/1` is true | D-10; no banner otherwise |

**Empty / non-applicable state:** there is no banner when the customer is not past-due. The "empty
state" of this surface is its **absence** — the banner simply does not render. (Verified by a render
test: a non-past-due subscription shows no `data-role` banner element.)

**Error state:** if the provider CTA cannot be resolved (no recognized processor / no destination), fall
back to the in-portal `/payment-methods` list rather than rendering a dead or absent link. The banner
never shows a broken href.

**Destructive actions:** none. The banner is a single positive CTA; no cancel/delete/confirm.

### accrue_admin — read-only dunning-state panel (DUN-07)

| Element | Copy (default wording — route via `Copy.dunning_*`) | Notes |
|---------|------|-------|
| Eyebrow | `DUNNING` | uppercase kicker (matches `.ax-eyebrow` convention) |
| Panel title | `Dunning campaign` | `<h3 class="ax-heading">` |
| Active-state badge (true) | `Active` | `.ax-status-badge .ax-status-badge-amber` (warning tone = in-progress recovery) |
| Inactive-state badge (false, never ran) | `No active campaign` | `.ax-status-badge .ax-status-badge-slate` |
| Recovered/closed badge (optional) | `Recovered` | `.ax-status-badge .ax-status-badge-moss` if the panel reflects a closed-recovered state |
| Started-at label | `Started` | `.ax-label`; value = `format_datetime(@subscription.dunning_campaign_started_at)` |
| Current-step label | `Current step` | `.ax-label`; value = resolved step key (e.g. `reminder` / `action_required` / `final_notice`) |
| Next-action label | `Next scheduled action` | `.ax-label`; value from the pure resolver `Accrue.Dunning.Campaign.next_step/3` (D-14) |
| Next-action value (pending) | `<step_key> in <human duration>` (e.g. `final_notice in 3 days`) | from `{:next, step, schedule_in}`; humanize `schedule_in` |
| Next-action value (done) | `Journey complete — awaiting grace/terminal sweep` | from `:done` |
| Empty state (no campaign) | `This subscription has no active dunning campaign.` | shown in `.ax-body` when `dunning_campaign_active?/1` is false; the panel still renders (read-only state surface), it does not disappear |
| Step history (optional) | reuse `Events.timeline_for("Subscription", id)` filtered to `dunning.*` types | D-13; render through the existing `Timeline` component if history is shown |

**Empty state heading / body:** `No active dunning campaign` / `This subscription has no active dunning
campaign.` — the admin panel is a *state surface*, so it always renders (unlike the portal banner) and
shows this empty state when no campaign is running.

**Error state:** if `next_step/3` cannot resolve (e.g. config steps unavailable), show
`Next action unavailable` via Copy rather than crashing the LiveView; the rest of the panel still
renders from already-loaded subscription state.

**Destructive actions:** **none — by contract.** DUN-07 is read-only (D-12). The panel MUST contain no
`phx-click`/`phx-submit`, no `<button>`, no `<form>`, no action controls. A render test asserts
`refute has_element?(view, "[data-role='subscription-dunning-state'] button")`.

## Accessibility & Interaction Notes

- **Portal banner:** `role="alert"` (or `role="status"`) on the `<section>` so screen readers announce
  the recovery prompt; the CTA is a real `<a href>` (keyboard-focusable, not a JS-only handler). Focus
  ring is the portal default. Single primary CTA — no competing actions.
- **Admin panel:** read-only, so no interactive a11y surface beyond the existing card; the status badge
  carries a visible text label (not color-only) so campaign state is conveyed without relying on the
  amber/moss tone. The `.ax-status-dot` is decorative.
- **Both:** copy never leaks internal terms (`dunning`, `campaign`, `past_due`, `step_key`) to the
  customer surface; the admin surface may use operator terms ("dunning campaign", "step") since it is
  operator-facing and routes them through Copy.

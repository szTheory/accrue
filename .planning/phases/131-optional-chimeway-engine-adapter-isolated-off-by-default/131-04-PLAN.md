## RESEARCH OVERRIDE — stop_conditions does NOT exist in Chimeway 1.0.0

CONTEXT.md D-06 references `stop_conditions: [%{type: :signal_received, ...}]` on wait steps. A full
grep of Chimeway 1.0.0's source returned ZERO matches — that DSL is from a STALE guide
(`Chimeway.Workflow` behaviour) that does not exist in the 1.0.0 lib. The executor MUST NOT emit
`stop_conditions` anywhere. For v1.40 (email-only, `:immediate` orchestration), the recommended path
is to OMIT the optional `workflow/2` callback entirely (RESEARCH Pattern 4 + Critical Notes 1-2):
with `orchestration/2 -> {:ok, :immediate}` and no `workflow/2`, `Chimeway.trigger/3` delivers the
email immediately, creates no WorkflowRun, and `Signal.track("payment_recovered")` routes to zero
runs (a safe no-op) — cancel-on-recovery is already guaranteed by Accrue's anchor-clear preventing
future `start_campaign` calls (the built-in Engine.Oban path's Oban cancel is the Accrue-side
guarantee on the default path).

## Verified Chimeway 1.0.0 API (use these EXACT signatures)

- `Chimeway.trigger(notifier, params, opts)` — opts MUST include BOTH `idempotency_key:` AND
  `tenant_id:` (missing either returns `{:error, :missing_idempotency_key}` / `{:error, :missing_tenant_id}`).
  Returns `{:ok, result}` | `{:duplicate, event}` | `{:error, reason}`.
- `Chimeway.Signal.track(tenant_id, actor_id, event_name, payload)` — argument order is
  `(tenant_id, actor_id, event_name, payload)`, NOT `(actor_id, tenant_id, ...)`. Returns
  `{:ok, signal}` | `{:error, reason}`.
- `Chimeway.Notifier` REQUIRED callbacks (only 4): `notification_key/0`, `version/0`,
  `recipients/1`, `build/2`. Optional: `channels/2`, `rendering/2`, `delayed_fallback_channels/2`,
  `orchestration/2`, `workflow/2`.

# Phase 214.2: Close gap: SYNC-02/DOCS-03 — surface advisory entitlement diagnostics - Context

**Gathered:** 2026-07-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the remaining v1.58 operator-observation flow: wire the already-persisted Stripe
advisory entitlement summary into the existing AccrueAdmin customer-detail **Access and
entitlements** disclosure, through a consumer-shaped core diagnostic seam, and prove the
end-to-end write → read → display path without allowing advisory data to influence a grant.

This phase also closes the directly related DOCS-03 truth identified by the milestone audit:
replace the two stale pre-2.x pagination statements and extend the existing package-doc
contract so the corrected completeness story cannot regress. It may reconcile current
planning status after verification, but dated Phase 213/214/214.1 evidence remains unchanged.

This phase does **not** add a new admin room or route, redesign customer detail, add a manual
refresh action, touch `accrue_portal`, define a Stripe↔local authorization crosswalk, invent
a freshness SLA, change sync writers/order, change grant semantics, add a migration or
dependency, or expose Stripe Feature catalog authoring. The local plan→feature map remains
the sole Accrue grant authority.

</domain>

<decisions>
## Implementation Decisions

The user selected all three gray areas and asked three specialist research agents to make
one decisive, coherent recommendation package. The decisions below incorporate the local
prompt corpus, the ratified newer Brand DNA, current AccrueAdmin design contracts, idiomatic
Elixir/Phoenix/Ecto package boundaries, and lessons from successful billing and observability
systems.

### Canonical access versus advisory observation

- **D-01:** Keep one existing **Access and entitlements** disclosure and render two explicitly
  named groups in answer-first order: **Accrue access (canonical)** first, then **Stripe
  observation (advisory)**. Do not add a peer tab, room, route, dashboard, or navigation item.
- **D-02:** The customer summary-list **Access** headline continues to describe only local
  resolved access. Stripe cache presence, absence, incompleteness, or failure must never
  change that headline or any result from `Admin.resolve_for_customer/1`.
- **D-03:** Do not compute or display `match`, `mismatch`, `in sync`, `healthy`, `drift`, or any
  other cross-model verdict. Local plans/features/quantities and Stripe lookup keys are not a
  defined one-to-one model; a derived verdict would manufacture authority and false assurance.
  Local catalog drift (`unmapped_price_ids`) remains the existing, separately named **Plan
  mapping** diagnostic.
- **D-04:** Lead the advisory group with the persistent boundary sentence **“Stripe advisory
  snapshot — does not change access.”** Labels and supporting copy use **observed**,
  **recorded**, **snapshot**, **source**, and **completeness**; they never use grant/deny
  language for Stripe data.
- **D-05:** The primary operator JTBD is: support opens one customer while investigating
  “they paid but are blocked,” sees the canonical local access answer, then sees what Stripe
  was last observed to report, when and through which path, without learning database or
  webhook implementation details. The return is faster diagnosis with no temptation to use
  the advisory cache as authorization.

### Core-to-admin diagnostic contract

- **D-06:** Add one internal, read-only consumer contract on
  `Accrue.Entitlements.Admin`: `diagnostic_for_customer/1`. It composes the existing local
  resolver diagnostic with the optional advisory snapshot and is the sole core-to-admin read
  seam used by CustomerLive. `accrue_admin` must not query `EntitlementSummary`, call
  `StripeSync.summary_for_customer/1` directly, or interpret provider JSON. — **Reversibility:
  costly** — this becomes a cross-package core/admin contract with tests and downstream call
  sites, even if it remains an internal (`@doc false`) API.
- **D-07:** Return a typed, consumer-shaped Elixir diagnostic value with independent `local`
  and `stripe_advisory` branches. Do not return an Ecto schema, changeset, `Repo` result, or
  raw Stripe payload as the presentation contract. Normalize source atoms, timestamps,
  completeness, counts, and feature lookup keys inside core.
- **D-08:** Preserve partial diagnosability: local resolution failure and advisory read/decode
  failure are separate branch states so one failure does not erase truthful data from the
  other. CustomerLive contains unexpected failures and renders Copy-backed unavailable copy;
  it does not crash or convert an advisory failure into a local fail-closed grant statement.
- **D-09:** The advisory path performs at most one row lookup by the already owner-scoped
  customer ID during mount/refresh and never performs processor/network I/O. When
  `stripe_native_sync` is disabled, preserve the config contract’s fully inert behavior: do
  not query the advisory table, even if an old row could remain from a previously enabled
  configuration.
- **D-10:** Provenance is `Pull refresh` only when the trusted `_accrue.source == "pull"`
  stamp says so, `Webhook` only when the webhook event watermark establishes it, and
  `Source unavailable` otherwise. Never infer provenance from timestamps or payload shape.

### Visible detail and evidence depth

- **D-11:** In the primary advisory group show a compact state, entitlement count, absolute
  UTC observation time when available, source, completeness, and a sorted preview of Stripe
  entitlement `lookup_key`s. Do not show Stripe entitlement object IDs, Ecto fields, event
  watermarks, or the provider payload in the primary disclosure.
- **D-12:** Cap only the rendered lookup-key preview at **8** items, followed by **“+N more”**.
  Never truncate the diagnostic value or stored evidence. An empty observed list is
  **“0 entitlements observed,”** not “no snapshot” and not “no access.”
- **D-13:** Put full normalized advisory evidence—and, only where the existing Raw data
  contract already permits it, the stored provider payload and event watermark—inside the
  customer page’s existing lazy **Raw data** section. Reuse `JsonViewer`; do not add a second
  raw/debug disclosure inside Access and entitlements. Preserve existing redaction and
  escaping rules and expose no card/payment PII.
- **D-14:** Reuse `Detail.detail_field_list`, `StatusBadge`, `JsonViewer`, the existing native
  `<details>/<summary>` structure, the `ax-*` token system, and `AccrueAdmin.Copy`. Do not add
  a new shared component or author with Tailwind utilities. The layout must remain compact,
  responsive at 360px, theme-correct in light/dark/system, keyboard readable, and legible
  without color.

### Diagnostic state model and microcopy

- **D-15:** Model these distinct advisory states; never collapse absence into an empty
  entitlement list:
  - `disabled` — **Not enabled.** “Stripe advisory sync is off for this host. Local access
    above is unchanged.” Neutral.
  - `not_observed` — **No snapshot yet.** “No advisory snapshot has been recorded for this
    customer.” Neutral.
  - `recorded` — **Snapshot recorded.** “Observed {absolute UTC timestamp}.” Neutral; this
    asserts recording, not freshness or agreement.
  - `age_unknown` — **Snapshot time unavailable.** “This advisory snapshot has no recorded
    observation time.” Neutral.
  - `incomplete` — **Incomplete snapshot.** “This webhook snapshot contains only the first
    reported entitlements. Local access above is unchanged.” Warning.
  - `unavailable` — **Snapshot unavailable.** “We couldn’t load the Stripe advisory snapshot.
    Local access above is unchanged.” Error.
- **D-16:** Do not emit a `stale` state from a hard-coded UI age. Staleness exists only if a
  future host-owned freshness policy supplies an explicit threshold; then the copy may say
  **“May be out of date”** and name the threshold breach. Until then, show the absolute
  observation time and let the operator judge it.
- **D-17:** State is conveyed by exact text plus semantic badge/icon treatment, never color
  alone. Use Moss only for an actual success fact—not merely “a row exists”; Amber for known
  incomplete or future policy-defined stale data; Slate/Ink for neutral states; danger/error
  treatment only for a read failure. Do not use `role="status"` for the static mount result;
  reserve live-region semantics for a future in-place LiveView state change.
- **D-18:** All new operator strings live in `AccrueAdmin.Copy`. Voice is measured, exact,
  native, durable: state the fact, clarify consequence, and give a next action only when one
  exists. No apology, hype, “source of truth” repetition, backend terms such as cache row/jsonb,
  or false recovery action—the phase intentionally has no refresh button.

### Verification and documentation truth

- **D-19:** Add focused core tests for the diagnostic contract’s disabled/no-I/O,
  not-observed, empty-observed, complete pull, incomplete webhook, unknown-source/time, and
  error branches. Add CustomerLive tests for the same visible states, the 8-item preview, Raw
  data evidence, accessible non-color labels, and unchanged local Access headline.
- **D-20:** Add one integration test that exercises a real advisory writer → persisted row →
  `diagnostic_for_customer/1` → CustomerLive display. Include a deliberately contradictory
  local/Stripe fixture and assert that local grants/headline remain unchanged and no
  match/mismatch verdict appears.
- **D-21:** Correct the stale `lattice_stripe >= 1.2` pagination language in
  `EntitlementSummary` moduledoc and `guides/telemetry.md`. The current truth is that the
  client-backed pull exhaustively streams active entitlements while webhook summaries may be
  incomplete; both remain advisory. Extend `verify_package_docs.sh` and its existing
  ROOT_DIR-backed negative-fixture family rather than adding a verifier or CI lane.
- **D-22:** Close with focused core/admin tests, the package-doc verifier, entitlement-sync
  isolation verifier, warnings-as-errors compilation, and the relevant admin accessibility/
  browser contract already used for customer detail. After phase verification, run Phase 213
  validation and an independent v1.58 milestone re-audit; this phase must not rewrite the
  historical `gaps_found` audit or self-declare the milestone passed.

### the agent's Discretion

- Exact name and nested shape of the typed diagnostic value, provided D-06..10 remain
  recognizable and no persistence/provider representation crosses into `accrue_admin`.
- Exact field-list grouping and Copy function names within the existing disclosure.
- Exact safe normalized payload shape placed in existing Raw data.
- Exact stable `data-role`/`data-ax-*` selectors used by focused LiveView and browser tests.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `Admin.resolve_for_customer/1` already owns the local canonical diagnostic and unmapped-price
  evidence; compose it rather than reimplementing the fold.
- `StripeSync.summary_for_customer/1` already proves the one-row lookup, while `Reconcile`
  stores count, sorted-comparable feature/lookup-key pairs, source, time, completeness, and
  watermark evidence.
- CustomerLive already has the correct one-page home, a contained `:error` pattern, local-only
  Access headline, native disclosure, and lazy `JsonViewer` raw section.
- `Detail.detail_field_list`, `StatusBadge`, `JsonViewer`, and `AccrueAdmin.Copy` cover the
  presentation without a new component family.

### Established Patterns

- Core owns billing semantics; companion admin consumes a narrow read seam. The host continues
  to own auth, tenant scope, routes, runtime configuration, and plan semantics.
- Local projection and provider evidence are labeled separately; primary pages answer first and
  reveal raw/debug material later.
- Copy is centralized; UI uses `ax-*` tokens, semantic text plus color, system/light/dark themes,
  controlled operator density, and stable explicit test selectors.
- Pay/Cashier-style consumer ergonomics are preferred over mirroring the provider API; the
  dj-stripe/full-mirror maintenance footgun is explicitly avoided.

### Integration Points

- `Entitlements.Admin.diagnostic_for_customer/1` → local resolver result + optional single
  advisory-row projection.
- CustomerLive mount/refresh → one diagnostic call → unchanged local headline + layered Access
  disclosure + normalized Raw data evidence.
- Pull/webhook writer → `EntitlementSummary` → diagnostic projection → visible customer detail
  integration test.
- Corrected schema/telemetry wording → existing package-doc verifier + ROOT_DIR negative fixture.

</code_context>

<specifics>
## Specific Ideas

- Example primary ordering: **Accrue access (canonical)** — Active plans, Granted features,
  Seats & limits, Grace, Plan mapping; then **Stripe observation (advisory)** — state badge,
  “3 entitlements observed,” lookup keys, “Observed 2026-07-31 18:22 UTC,” “Pull refresh,”
  “Complete.”
- A contradictory fixture is intentional acceptance evidence: local grants may say `reports`
  while Stripe observes `priority-support`; both render, no mismatch badge appears, and local
  access remains unchanged.
- Design pillars applied here: usefulness/clarity, information architecture and consistency,
  accessibility, responsive density, theme fidelity, performance, resilience, security/privacy,
  auditability, testability, and maintainer DX.

</specifics>

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Canonical access versus advisory observation

- **D-01:** Keep one existing **Access and entitlements** disclosure and render two explicitly named groups in answer-first order: **Accrue access (canonical)** first, then **Stripe observation (advisory)**. Do not add a peer tab, room, route, dashboard, or navigation item.
- **D-02:** The customer summary-list **Access** headline continues to describe only local resolved access. Stripe cache presence, absence, incompleteness, or failure must never change that headline or any result from `Admin.resolve_for_customer/1`.
- **D-03:** Do not compute or display `match`, `mismatch`, `in sync`, `healthy`, `drift`, or any other cross-model verdict. Local plans/features/quantities and Stripe lookup keys are not a defined one-to-one model; a derived verdict would manufacture authority and false assurance. Local catalog drift (`unmapped_price_ids`) remains the existing, separately named **Plan mapping** diagnostic.
- **D-04:** Lead the advisory group with the persistent boundary sentence **“Stripe advisory snapshot — does not change access.”** Labels and supporting copy use **observed**, **recorded**, **snapshot**, **source**, and **completeness**; they never use grant/deny language for Stripe data.
- **D-05:** The primary operator JTBD is: support opens one customer while investigating “they paid but are blocked,” sees the canonical local access answer, then sees what Stripe was last observed to report, when and through which path, without learning database or webhook implementation details. The return is faster diagnosis with no temptation to use the advisory cache as authorization.

#### Core-to-admin diagnostic contract

- **D-06:** Add one internal, read-only consumer contract on `Accrue.Entitlements.Admin`: `diagnostic_for_customer/1`. It composes the existing local resolver diagnostic with the optional advisory snapshot and is the sole core-to-admin read seam used by CustomerLive. `accrue_admin` must not query `EntitlementSummary`, call `StripeSync.summary_for_customer/1` directly, or interpret provider JSON. — **Reversibility: costly** — this becomes a cross-package core/admin contract with tests and downstream call sites, even if it remains an internal (`@doc false`) API.
- **D-07:** Return a typed, consumer-shaped Elixir diagnostic value with independent `local` and `stripe_advisory` branches. Do not return an Ecto schema, changeset, `Repo` result, or raw Stripe payload as the presentation contract. Normalize source atoms, timestamps, completeness, counts, and feature lookup keys inside core.
- **D-08:** Preserve partial diagnosability: local resolution failure and advisory read/decode failure are separate branch states so one failure does not erase truthful data from the other. CustomerLive contains unexpected failures and renders Copy-backed unavailable copy; it does not crash or convert an advisory failure into a local fail-closed grant statement.
- **D-09:** The advisory path performs at most one row lookup by the already owner-scoped customer ID during mount/refresh and never performs processor/network I/O. When `stripe_native_sync` is disabled, preserve the config contract’s fully inert behavior: do not query the advisory table, even if an old row could remain from a previously enabled configuration.
- **D-10:** Provenance is `Pull refresh` only when the trusted `_accrue.source == "pull"` stamp says so, `Webhook` only when the webhook event watermark establishes it, and `Source unavailable` otherwise. Never infer provenance from timestamps or payload shape.

#### Visible detail and evidence depth

- **D-11:** In the primary advisory group show a compact state, entitlement count, absolute UTC observation time when available, source, completeness, and a sorted preview of Stripe entitlement `lookup_key`s. Do not show Stripe entitlement object IDs, Ecto fields, event watermarks, or the provider payload in the primary disclosure.
- **D-12:** Cap only the rendered lookup-key preview at **8** items, followed by **“+N more”**. Never truncate the diagnostic value or stored evidence. An empty observed list is **“0 entitlements observed,”** not “no snapshot” and not “no access.”
- **D-13:** Put full normalized advisory evidence—and, only where the existing Raw data contract already permits it, the stored provider payload and event watermark—inside the customer page’s existing lazy **Raw data** section. Reuse `JsonViewer`; do not add a second raw/debug disclosure inside Access and entitlements. Preserve existing redaction and escaping rules and expose no card/payment PII.
- **D-14:** Reuse `Detail.detail_field_list`, `StatusBadge`, `JsonViewer`, the existing native `<details>/<summary>` structure, the `ax-*` token system, and `AccrueAdmin.Copy`. Do not add a new shared component or author with Tailwind utilities. The layout must remain compact, responsive at 360px, theme-correct in light/dark/system, keyboard readable, and legible without color.

#### Diagnostic state model and microcopy

- **D-15:** Model these distinct advisory states; never collapse absence into an empty entitlement list:
  - `disabled` — **Not enabled.** “Stripe advisory sync is off for this host. Local access above is unchanged.” Neutral.
  - `not_observed` — **No snapshot yet.** “No advisory snapshot has been recorded for this customer.” Neutral.
  - `recorded` — **Snapshot recorded.** “Observed {absolute UTC timestamp}.” Neutral; this asserts recording, not freshness or agreement.
  - `age_unknown` — **Snapshot time unavailable.** “This advisory snapshot has no recorded observation time.” Neutral.
  - `incomplete` — **Incomplete snapshot.** “This webhook snapshot contains only the first reported entitlements. Local access above is unchanged.” Warning.
  - `unavailable` — **Snapshot unavailable.** “We couldn’t load the Stripe advisory snapshot. Local access above is unchanged.” Error.
- **D-16:** Do not emit a `stale` state from a hard-coded UI age. Staleness exists only if a future host-owned freshness policy supplies an explicit threshold; then the copy may say **“May be out of date”** and name the threshold breach. Until then, show the absolute observation time and let the operator judge it.
- **D-17:** State is conveyed by exact text plus semantic badge/icon treatment, never color alone. Use Moss only for an actual success fact—not merely “a row exists”; Amber for known incomplete or future policy-defined stale data; Slate/Ink for neutral states; danger/error treatment only for a read failure. Do not use `role="status"` for the static mount result; reserve live-region semantics for a future in-place LiveView state change.
- **D-18:** All new operator strings live in `AccrueAdmin.Copy`. Voice is measured, exact, native, durable: state the fact, clarify consequence, and give a next action only when one exists. No apology, hype, “source of truth” repetition, backend terms such as cache row/jsonb, or false recovery action—the phase intentionally has no refresh button.

## Summary

The missing flow is not a writer, schema, or new Stripe integration: pull and webhook writers already converge on one advisory `EntitlementSummary` row, while CustomerLive currently renders only the local `{resolved, unmapped}` diagnostic. [VERIFIED: codebase grep] Implement one `@doc false` `Accrue.Entitlements.Admin.diagnostic_for_customer/1` projection that invokes the existing local fold and, only when `Accrue.Config.stripe_native_sync?/0` is true, reads that one row and normalizes it into an independent advisory branch. [VERIFIED: codebase grep]

The UI should consume that projection once during the existing synchronous mount/refresh lifecycle, preserve `access_headline/1` as a function of the local branch alone, and append a second, advisory-only group to the existing disclosure. [VERIFIED: codebase grep] A mounted `:disabled`, `:not_observed`, or empty-observed state is meaningful and must remain distinct; Stripe documents that list responses are paginated and webhook summary arrays can contain at most ten entries, so `truncated`/`has_more` must communicate incompleteness rather than authorization. [CITED: https://docs.stripe.com/billing/entitlements?dashboard-or-api=api]

**Primary recommendation:** Add a core-owned, typed two-branch diagnostic projection; make CustomerLive a pure renderer of it; pin the no-I/O/default-off and never-a-grant behavior with focused and integration tests; and ratchet the two stale pagination statements through the current docs verifier. ### Pattern 1: Consumer-shaped two-branch projection

**What:** Return a named map or struct whose `:local` branch contains the existing local resolver output plus unmapped IDs and whose `:stripe_advisory` branch is one of explicit presentation-safe state values. [VERIFIED: codebase grep]

**When to use:** Always use it for CustomerLive’s entitlement diagnostic; do not expose an Ecto schema, Repo tuple, changeset, or provider payload across the package boundary. [VERIFIED: codebase grep]

**Recommended shape:**

```elixir
# Source: existing core boundaries in accrue/lib/accrue/entitlements/admin.ex
%{
  local: {:ok, %{resolved: resolved, unmapped_price_ids: unmapped}},
  stripe_advisory: %{
    state: :recorded | :incomplete | :age_unknown | :not_observed | :disabled | :unavailable,
    entitlement_count: non_neg_integer(),
    lookup_keys: [String.t()],
    observed_at: DateTime.t() | nil,
    source: :pull | :webhook | :unavailable,
    completeness: :complete | :incomplete | :unknown,
    raw: map()
  }
}
```

`local` and `stripe_advisory` must be independently failure-contained so an advisory decode/read failure does not replace an otherwise correct local answer. [VERIFIED: codebase grep]

### Pattern 2: Explicit config gate before read

**What:** Check `Accrue.Config.stripe_native_sync?/0` before calling `StripeSync.summary_for_customer/1`; disabled returns the normalized `:disabled` state without a repo query. [VERIFIED: codebase grep]

**When to use:** Every invocation of `diagnostic_for_customer/1`; preserve the existing fully inert default-off contract even if historical rows exist. [VERIFIED: codebase grep]

### Pattern 3: Render facts, not a reconciliation verdict

**What:** Render canonical fields first, then a visible advisory boundary sentence, state badge, count, sorted preview, source/time/completeness, and only then lazy normalized raw evidence. [VERIFIED: codebase grep]

**When to use:** The existing `<details data-ax-drill-section="access-entitlements">`; no new tab, route, refresh action, or separate raw disclosure. [VERIFIED: codebase grep]

### Anti-Patterns to Avoid

- **Provider-shaped admin contract:** Do not pass `EntitlementSummary.data` or a schema to HEEx; provider JSON and watermark interpretation then leak across package boundaries. [VERIFIED: codebase grep]
- **Cross-model comparison:** Do not synthesize mismatch, agreement, freshness, health, or drift; local feature names and Stripe lookup keys have no defined crosswalk. [VERIFIED: codebase grep]
- **Row-exists equals success:** An empty observed list is `0 entitlements observed`; an incomplete webhook row is warning evidence, not a successful grant. [CITED: https://docs.stripe.com/billing/entitlements?dashboard-or-api=api]
- **Async/network expansion:** Do not refresh or call `Processor` from CustomerLive; this diagnostic read is database-only. [VERIFIED: codebase grep]
- **Live-region overuse:** Do not apply `role="status"` to the static mount result or disclosure content; WCAG’s status-message guidance is aimed at qualifying content changes, and an expanded disclosure is explicitly outside that scope. [CITED: https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html]

## Common Pitfalls

### Pitfall 1: Disabled mode still queries stale advisory data

**What goes wrong:** A previous enabled deployment can leave a row that CustomerLive reads even after hosts disable the feature. [VERIFIED: codebase grep]

**How to avoid:** Return `:disabled` before any advisory seam/repo call; test SQL telemetry or an equivalent seam assertion. [VERIFIED: codebase grep]

### Pitfall 2: Partial data hides a valid canonical answer

**What goes wrong:** A rescue around the whole composed diagnostic converts an advisory-row decode failure into the existing local fail-closed screen. [VERIFIED: codebase grep]

**How to avoid:** Contain local and advisory errors separately; local error retains advisory observation if available, advisory error retains local diagnostic. [VERIFIED: codebase grep]

### Pitfall 3: Claiming an incomplete webhook summary is current or complete

**What goes wrong:** The UI treats a webhook list as exhaustive or derives freshness from its timestamp. [CITED: https://docs.stripe.com/billing/entitlements?dashboard-or-api=api]

**How to avoid:** Map `truncated` / `has_more` to `:incomplete`, never emit a hard-coded `:stale`, and show an absolute UTC observation timestamp only when recorded. [VERIFIED: codebase grep]

### Pitfall 4: Untrusted provenance inference

**What goes wrong:** UI infers pull from timestamp or payload shape and presents it as fact. [VERIFIED: codebase grep]

**How to avoid:** Use only the `_accrue.source == "pull"` stamp for pull, the event watermark for webhook, and otherwise `Source unavailable`. [VERIFIED: codebase grep]

### Pitfall 5: Documentation changes that are not regression-protected

**What goes wrong:** The two stale `lattice_stripe >= 1.2` claims are manually corrected but future edits restore them. [VERIFIED: codebase grep]

**How to avoid:** Add positive current-truth and negative stale-wording checks to the existing script; mutate a covered target under `ROOT_DIR` in the existing verifier test family. [VERIFIED: codebase grep]

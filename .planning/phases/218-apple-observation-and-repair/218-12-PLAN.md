## Planning gates

- Gap root cause: execution miss plus missing caller policy. The private config declares `verification_time`, but Plan 218-11 left it unwired, retained a first-root-only helper, and provided no delayed-record source for the intended instant.
- Authoritative timestamp policy: direct purchase/restore and live NotificationPlug verification use the current UTC clock when `verification_time` is nil/`:current`; delayed reconciliation uses each independently signed transaction/renewal JWS's own `signedDate`, never receipt time, page time, outer-notification time, checkpoint time, or another record's claim. The payload value is provisional for certificate evaluation, is accepted only as an integer millisecond Unix instant no later than current UTC plus five minutes of clock skew, must fall within every path certificate's validity window, and becomes authoritative only when that same JWS's pinned-chain ES256 signature and application claims succeed. A host-supplied `%DateTime{}` remains a trusted deterministic/replay override and must be valid UTC; any other value closes as `invalid_certificate_time`.
- Compatibility boundary: nil remains an intentional current-clock default for existing host configurations and NotificationPlug. No production path silently selects a historical signed timestamp; only Reconciliation.Admission opts into `:signed_date` per D-10/D-11.
- Assumption — AAPL-02 idempotency/concurrency: verification is a pure adapter call with immutable config and no process or database state. This plan makes the historical-valid case repeatable and concurrent under test rather than introducing a lock.
- Assumption — AAPL-04 idempotency/concurrency: checkpoint serialization and observation identities remain owned by existing reconciliation/database code; this verifier change only makes delayed evidence admissible at the intended time.
- Identity-model delta: none. No lineage, account, ownership, provider identity, or public outcome shape changes.
- API coverage: preserve `COVERAGE.md`; no capability changes, only repair of the existing x5c trust-root/certificate-time `INTEGRATE` row.
- Schema-push detection: not applicable; no ORM schema or migration file is modified.
- Reversibility: local private verifier/test changes behind the stable behaviour are reversible; no checkpoint is warranted.

## Trust Boundaries

| Boundary | Description |
|---|---|
| host verifier config -> OTP PKIX | The host selects current, signed-date, or fixed policy and pinned roots; only reconciliation selects signed-date. |
| unverified JWS payload -> resolved certificate instant | A candidate `signedDate` influences PKIX only under reconciliation policy and must be bounded, then authenticated by the same JWS before any facts leave Production. |
| JWS x5c -> bounded verified facts | Provider-controlled certificate bytes must not select their own trust anchor or bypass path/purpose/signature checks. |
| historical evidence -> reconciliation | Delayed signed facts may be processed only if valid at the explicit policy instant. |

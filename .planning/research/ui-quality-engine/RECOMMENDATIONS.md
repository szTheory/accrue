**Source baseline:** `891ed451b16905ea4a71d6b3653310202bb10b5e`.
**Owner intent:** [durable direction](../../notes/2026-10-26-ui-storybook-quality-direction.md).
**Navigation:** [inventory](INVENTORY.md), [composition](ARCHITECTURE.md), [scenarios](SCENARIOS.md), [design and verification](DESIGN-AND-VERIFICATION.md), [milestone and rolling roadmap](MILESTONE-PROPOSAL.md), [adversarial review](ADVERSARIAL-REVIEW.md).

## Recommendation

Make Storybook the fast, human-readable review index of **real production compositions and reachable situations**. Begin with the existing subscription job, repair the copied/metadata-only examples, and demonstrate the full loop from realistic data through shared rendering, mechanical checks, bounded design review, and a mounted application journey. Expand only after that slice produces useful UI improvements at an affordable recurring cost.

The composition tree is **components → groups → areas → sections → pages per job**. It is a navigation and reuse model, not a requirement to manufacture five abstraction layers for every screen. Stories at different levels must call the same rendering owners that the application uses. A story count, metadata marker, screenshot baseline, or green axe result is not proof of a composed screen's usefulness.

This proposal follows the owner's explicit strategy request for quality of existing UI. It does not reopen new billing features, the deferred diagnostic rooms, a rebrand, or the parked paid critic. It preserves the separate HIGH-priority event session-timezone correctness issue.

## Decisions and tradeoffs

| Decision | Why this is the best fit here | Rejected alternative / cost |
|---|---|---|
| Repair one subscription vertical slice first. | A copied detail story and metadata-only group story are concrete defects in the quality process; a real job provides an end-to-end value test. | A repository-wide extraction or weeks of quality infrastructure before improving a visible task. Later surfaces wait for demonstrated value. |
| Extend the existing registry with scenario and composition metadata. | Keep component owners and existing coverage contracts; add reachable situation, actor/job, source owner, tier, and interaction lane. | A second handwritten component inventory or metadata-only claims of coverage. Registry extensions require migration of their consumers. |
| Generate a variation-aware manifest from the installed PhoenixStorybook API. | Existing discovery finds story pages, not a guaranteed enumeration of isolated variations. Deterministically reconcile discovered routes, variation IDs, and registry membership. | Hand-maintained URL lists or importing JavaScript Storybook APIs that PhoenixStorybook does not implement. Unknown/uncovered variations fail visibly. |
| Extract presentation where a real seam exists. | Keep LiveView mount/params/events, authority, loading, streams, hooks, and lifecycle in their actual owners. Reuse presentational HEEx with plain assigns; retain stateful components where statefulness is meaningful. | One giant props bag, a new generic view-model framework, heavy DB mocks, or stateless rewrites solely for stories. Page-level purity is not an end in itself. |
| Keep static stories and mounted behavior as complementary lanes. | Stories make visual states fast and reproducible; mounted tests establish current permissions, route/patch behavior, focus, hooks, async completion, and persisted effects. | Pretend a disabled button fixture proves authorization or a disconnected banner proves reconnection behavior. Avoid duplicating every persistence test in the browser. |
| Isolate the existing lab before making it the review entry. | Its bootstrap is DB-backed and includes reset routes. Use a separate loopback port and disposable DB/namespace, explicit process identity, and no accidental server reuse or shared fixture resets. | Calling the entire existing host DB-free, or pointing an interactive reviewer at the same mutable server used by a test run. DB-free describes presentation rendering; bootstrap cost is measured separately. |
| Reuse scenario definitions, with separate adapters. | Plain domain-valid data can feed stories, test factories, and guarded seeds. Clock/IDs are explicit; DB setup stays in adapters. | A universal fixture engine, dependencies on a host Repo from a component story, or moving all seeds at once. Share semantics first, not every factory implementation. |
| Use adopter profiles only when they exercise distinct classes. | Separate the product adopting Accrue from the engineer, vendor operator, and customer actor. Keep the existing Cadence world and held-out fixtures intact. | Seven decorative fictional companies, combined permissions, invented provider capabilities, or a new independent world per story. |
| Keep current brand and token ownership. | Brand JSON already exists; Admin implementation scales and Portal host theming have distinct owners. Extend checks at those owners. | Duplicating all scales in JSON, Tailwind namespace resets, or a new visual identity under a testing milestone. |
| Mobile-first means layout and task access, including component container widths. | Test narrow contexts, wrapping, preserved identities, money, actions, menus and disclosures across both themes and breakpoint boundaries. | Five screenshots as proof of all widths, or hiding essential facts to make overflow tests pass. |
| Keep new gates focused and measured. | Reuse Playwright, axe, copy/token checks and Linux baselines; test all changed/affected scenarios with a stable representative smoke set. | Every story × every width × every preference on every PR. Full sweeps remain scheduled/on demand, with known counts and sharding. |
| Prove CI admission in the first slice. | Existing browser-workflow path filters omit root `storybook/`; proposed scenario roots need coverage too. Add classifier/trigger contracts for stories, shared scenarios, registry, manifests and tokens before trusting consumer selection. | A perfect impact selector that never runs because its workflow did not start. Negative controls distinguish unrelated changes from required paths. |
| Review design in bounded batches using incumbent standards. | One assessment, one correction batch, one confirmation per coherent slice unless a named defect justifies reopening. Findings name the owning tier. | Autonomous critic convergence, aesthetic numeric scores as acceptance, new paid services, or automation claiming taste. |
| Preserve the component kitchen's current proof role. | Historical contracts explicitly retain it as the deterministic second renderer. Storybook can be the preferred review entry without removing that proof. | Deleting the kitchen merely because the methodology prefers one inventory. Retire only after a separately approved evidence-preserving migration. |

## Story and scenario contract

Each retained situation identifies: stable ID; section and job; actor and billed entity; adopter profile when relevant; renderer owner; composition tier; ordinary or stress purpose; capability/permission inputs; expected visible outcome; source fixture; and static versus mounted proof ownership. Generate route/variation metadata rather than duplicating it manually. An entry may point to an existing fixture module and a constructor; it need not repeat the entire domain record.

Use meaningful equivalents: new account vs filtered no results; one vs a page and page-boundary state; supported pending vs confirmed outcome; incomplete evidence vs failed action; read-only actor vs revoked action; long real identifiers and international names vs nonsense strings. Only include loading, disconnection, provider differences, or pagination where that owner actually exposes them. Empty subscription *collections* belong in list stories; a fabricated empty subscription record does not belong in a detail story.

Domain-invalid inputs belong in explicitly labelled validation/negative tests, not realistic screen fixtures. Privacy/adversarial tests may deliberately use hostile strings but must state that purpose. Existing unknown-history/provider records can be legitimate visible states even if current form builders cannot create them; reachability evidence is broader than a grep of today's callers.

Fixture invariants cover closed enums and supported capability combinations; valid object relationships and owner identity; currency/minor units and coherent totals; state-dependent optional fields; chronology and cancellation/recovery periods; stable reference time; and distinct actor permissions. Assert these before rendering and after seed-adapter persistence where relevant. Keep ordinary reviewer data plausible and held-out stress data isolated; never seed real personal data, secrets, live instruments, or production URLs.

Curate through a reachability ledger: situation → production owner or supported historic state → contract → story/test. Add, merge, move, or remove with an explicit reason. Preserve a negative regression if its protected behavior still matters. No automatic deletion based only on no current caller or similar screenshots. Track uncovered jobs and deliberately excluded states, not just stories per component.

## First working example

For “understand this subscription and take the safe next action,” use the real status/identity primitives, compose the summary and action area, then the owning detail page and list-to-detail journey. Show a complete active subscription first. Add a scheduled cancellation, an explicitly incomplete-evidence case, a genuinely supported restricted action, and a plausible narrow-width/long-name case from the actual contract. Add mutable/async failure states in the mounted lane where the behavior is real.

For the adjacent list job, render the actual filter/search/toolbar/table/pagination group. Separate new-account, no-results, one-row, multiple-page, last-page, pending search and failed search only where the real subscriptions owner provides those states. Do not manufacture backend capability to satisfy a generic checklist.

Stories, production rendering, and mounted tests should agree on the same state inputs and visible labels. A story-specific fake action may demonstrate presentation, but must be visibly categorized as presentation evidence; it cannot claim a working billing operation. Supported actions remain guarded in the real application independently of presentation.

## Verification layers adapted to Accrue

| Layer | Adopt or extend | What it establishes / limitation |
|---|---|---|
| L1: source and scenario contracts | Existing tokens, CSS boundaries, copy inventory and registry checks; add fixture invariants and manifest reconciliation. | Deterministic scope and consistency. Check token roles/allowed consumers, not all foreground/background combinations or every computed value without context. |
| L2: rendered sweep | Existing browser/axe harness; add variation isolation, narrow/container widths, theme coverage and reachable-state assertions. | No unexpected runtime errors, page overflow, broken essential text/actions, applicable axe violations and named focus/target failures. Axe `incomplete` is an explicit unresolved observation requiring automated follow-up or a scoped reviewed disposition; it is neither a pass nor automatically a proved defect. |
| L3: selected visual regression | Existing pinned Linux screenshot lane; add only key states justified by changed compositions. | Approved visual stability at recorded source/assets/browser/viewport/theme. It cannot certify realism, usability, or visual excellence. Masks cover only volatile regions and are excluded from aesthetic judging. |
| L4: bounded design review | Reuse design/voice guidance, historical findings and owner examples; agent review within the session is advisory. | Specific evidence about hierarchy, redundancy, affordances, typography and job coherence that numerical checks miss. No paid CI critic or revival of the parked ratchet. |
| L5: optional owner taste and strategic decisions | Keep scoped decisions with evidence and rationale. | Product judgment and preferences, not recurring manual UAT for mechanically provable behavior. A prior rejection suppresses only the same contextual finding; changes to state, source, theme or consequence can invalidate it. |

A reproducible finding records situation/variation URL, source and served assets, viewport and container width, theme, motion preference, browser, relevant locale/timezone, expectation, actual evidence, and owning tier. Record only environment dimensions that affect the finding; do not force a new evidence database for every assertion.

The current test-lab server starts TestRepo/Oban/Fake and is not a DB-free bootstrap. Publish one explicit safe launch command with its disposable database, distinct loopback port and process identity. Refuse an unexpected existing process instead of silently reusing it. Interactive review and reset-capable mounted test runs must not share that mutable server/database; the existing reset routes are test authorities, not general preview controls. Prove this with a negative control that a normal mounted-test reset cannot change the review session's data. DB-free component rendering remains valuable even when the endpoint boots infrastructure. Do not introduce a separate server framework merely to remove that one-time bootstrap cost.

**Provisional performance targets, not measurements:** aim for preview response under 10 seconds warm where feasible, focused local checks under 60 seconds, no more than three minutes of additional warm browser execution and five minutes of incremental CI critical-path cost. Measure actual scenario counts, startup and per-cell cost in the first slice before freezing the budget. If startup dominates, reuse the existing browser job; if coverage exceeds budget, shard or move broad sweeps without dropping changed-scenario checks. Avoid a second full application boot on the PR critical path just to run a small sweep.

Sample widths include 320, 375, 768, 1280 and 1440 CSS px, plus existing 1024 coverage and each relevant breakpoint immediately below/at/above. Assess real container widths and resize transitions. Every changed composition gets both themes and its relevant narrow boundary. Full reference-width sweeps cover the retained manifest outside the fast subset. Reduced motion targets actual animated owners; normal motion still has explicit behavior checks. Text resize at 200% is a useful check distinct from true browser zoom and 320 CSS px reflow; do not claim conformance from a root-font multiplier alone.

Apply WCAG thresholds with their scope and exceptions: normal text 4.5:1, large text 3:1, essential non-text indicators 3:1, and the WCAG 2.2 target-size minimum of 24 CSS px or its documented spacing/equivalent exceptions. Prefer comfortable touch hit areas for primary controls rather than treating the minimum as the design target. Effective color compositing and actual adjacent surfaces matter; disabled, decorative, alpha, host-accent and focus states cannot be decided by a global raw-token Cartesian matrix. Brand contrast math can supplement existing axe/rendered checks, not replace them.

## Design rubric and accountability

“Machine” below means an executable assertion for a specified property; “advisory” means bounded evidence-based design review; “owner” is optional taste/strategy input. The entire aesthetic claim is never assigned to a machine alone.

| Owner request | Machine evidence | Advisory review | Owner boundary |
|---|---|---|---|
| Light and dark both look intentional; restrained color. | Effective contrast, state cues, theme switching, asset/token roles. | Palette balance, emphasis, depth and harshness in both themes. | Changing brand identity or subjective preference. |
| Professional typography. | Loaded fonts, scale ownership, essential text visibility, resize and number formatting. | Rhythm, wrapping, density, optical hierarchy and prose vs ID roles. | New typographic identity. |
| Clear, elegant hierarchy. | Landmark/headings/name structure and essential task presence. | Answer order, grouping, competing emphasis and whitespace. | A consequential change in product priorities. |
| No redundant content. | Named duplicate-label/content regressions where mechanically definable. | Repeated facts, over-explanation and unnecessary chrome. | Whether a fact is useful to a real actor when evidence is inconclusive. |
| Happy paths and power users. | Task completion, shortcuts where already supported, disclosure and context preservation. | Scan efficiency, discoverability and investigation depth. | New task/capability or navigation strategy. |
| Consistent user-facing language. | Existing copy owner/inventory, locked wording and accessible-name checks. | Specific action/outcome wording, tone and vocabulary consistency. | Legal or deliberately locked wording changes. |
| Realistic personas and data. | Fixture invariants, capability/authority matrix and seed parity. | Plausible volumes, timing, failure narratives and tasks. | Actual external adoption claims require evidence. |
| Coherent journey and navigation. | Route/patch/back/filter/context invariants, active item, fresh permission checks. | Natural progression, destination labels and perceived continuity. | Removing an adopter-visible surface. |
| Mobile-first responsive. | Relevant narrow/container widths, breakpoint edges, reflow, targets, focus and zoom checks. | Composition, reading order and touch ergonomics. | New interaction model where user expectations are consequential. |
| Least surprise and reusable patterns. | Shared rendering and interaction contracts. | Affordance/behavior match; one consistent pattern per job. | Strategic exceptions with a recorded reason. |

## Conflicts with the supplied methodology and dispositions

The methodology is a reusable proposal, not a replacement for repository decisions. These are the applicable conflicts found; no current owner decision is silently overridden.

1. **Planning-only vs milestone invocation.** Methodology: “Do NOT, in this session” → “open or modify a milestone.” The initiating request is `$gsd-new-milestone` and the owner asks for a “rolling milestone roadmap.” **Disposition:** finish the research and reviewable proposal first; keep canonical milestone state untouched until the workflow's summary confirmation. Record this as a proposal, not a completed milestone opening.
2. **One renderer vs retained kitchen.** Methodology: “Any second inventory ... gets ported, then retired.” Phase 200 `200-CONTEXT.md` D-10: “Storybook is the human-facing design lab; `/dev/components` is the deterministic second renderer.” **Disposition:** make Storybook the review entry, preserve the kitchen and its tests. Later retirement requires evidence parity and explicit amendment of the retained-renderer decision.
3. **Token centralization.** Methodology: “Keep one source of truth for tokens, e.g. the brandbook.” `brandbook/tokens/README.md`, D-11: “The admin `--ax-*` tokens ... are the authoritative implementation SSOT”; additional brand-scale properties “would create a parallel layer that drifts.” **Disposition:** preserve the existing brand/implementation split and drift checks. No Tailwind reset or new canonical token file.
4. **AI judge machinery.** Methodology suggests an “LLM design judge” with calibration and repeated pairwise passes. `PROJECT.md` keeps “parked paid-AI ratchet revival” out of scope and records bounded review: “one batched assessment, one correction batch and one confirmation per coherent slice unless a named defect justifies reopening.” **Disposition:** advisory, in-session review using existing rubric/history; no new evaluator, keys, service, convergence loop, or scoring gate. Pairwise/calibration tooling is deferred until repeated concrete review failures justify it.
5. **Screenshot human gate.** Methodology labels L3 diffs “accepted by a human” and proposes an owner layer. `CLAUDE.md`: “post-hoc human verification and manual UAT are not completion gates.” **Disposition:** fresh executable acceptance and evidence-reviewed, intentional baseline changes; optional owner taste review, never recurring mandatory visual UAT replacing tests.
6. **Demo host access.** Methodology asks that scenarios be reachable from every story host, including a demo app. Current host intentionally disables dev routes and its asset contract preserves that boundary. **Disposition:** keep the existing test review endpoint for the initial slice; design an explicit dev/test-only opt-in harness later, with separate authority and package checks. No silent canonical-host mount flip.

The methodology's blanket style bans, universal state lists, per-PR full Cartesian sweep, identical navigation ARIA snapshots, and automatic global suppressions are also revised as feasibility/false-positive risks, rather than treated as locked requirements. Navigation has legitimate route-specific active state; assert stable structure plus correct local state. No loading story is required for a synchronous component. Contextual technical terms remain allowed for engineering investigation.

## Sources and evidence limits

Repository-specific evidence and source locations are in the three focused research files and inventory. Three researchers covered architecture/security, personas/domain data, and design/CI/accessibility; a separate adversarial review challenges this synthesis. Stop further fan-out unless it identifies a missing decision that changes scope, sequence, or acceptance.

Primary-source comparisons support patterns, not adoption of another framework:

- [Storybook: building pages and screens](https://storybook.js.org/docs/writing-stories/build-pages-with-storybook) describes presentational-page and connected-component approaches and their tradeoffs. This is conceptual precedent; use the installed PhoenixStorybook APIs, not JavaScript CSF tooling.
- [GOV.UK: using styles, components and patterns](https://design-system.service.gov.uk/get-started/) emphasizes evidence about when patterns were tested and testing them in their actual service context. Accrue must validate its own billing jobs.
- [DTCG 2025.10](https://www.designtokens.org/tr/2025.10/) is an interchange specification already reflected in Accrue's brand layer; it does not require replacing implementation token ownership.

This session inspects source and selected committed light/dark subscription screenshots; it does not boot the application, run UI suites, measure timing, establish current rendered defects, or certify accessibility. The inspected goldens contain synthetic sparse data and timestamp masks, demonstrating why baseline stability is distinct from fixture realism and design quality. These are candidates for fresh assessment in the first slice, not a current-source visual verdict.

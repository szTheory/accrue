# v1.32 Research: Braintree Parity Gaps

**Goal:** Expand the Braintree integration (v1.31 "thin slice") to achieve deeper feature parity with Stripe for production usage, adhering to Accrue's "direct gateway" explicit-capability strategy.

## Context from v1.31
v1.31 delivered the "Gateway subscription core":
- Customer create / retrieve / update
- Payment-method vault acquisition (via Braintree Hosted Fields)
- Direct subscription creation (`Accrue.Billing.subscribe/3`)
- Webhook verify / parse
- Webhook-backed local subscription convergence

The following were explicitly deferred in v1.31:
- `Accrue.Billing.create_checkout_session/2` parity
- `Accrue.Billing.create_billing_portal_session/2` parity
- Advanced Payment Method CRUD
- Subscription mutation (plan swap, quantity, pause, resume)
- Refunds, Coupons, Promotion Codes, Metering, and Connect.

## Gaps for Production Readiness (v1.32 Focus)

To bring Braintree to the "same level of support as Stripe" for real-world production usage, the following capabilities are the highest priority gaps:

1. **Subscription Mutation Lifecycle:** 
   Production apps need to upgrade/downgrade plans and change seat quantities.
   - Target: `subscription.update`, `subscription.pause`, `subscription.resume` parity.

2. **Payment Method Management:** 
   Customers need to add new cards, delete old ones, and change their default payment method.
   - Target: Full CRUD parity on the `payment_methods` capability.

3. **Billing Portal Parity (Self-Serve UX):** 
   Stripe has a hosted billing portal. Braintree does not. Accrue must either provide a robust first-party self-serve UI component for Braintree customers (a "Local Portal") or explicitly document how to build one.
   - Target: Clarify `billing_portal_session` semantics for Braintree (likely pointing to a local UI implementation).

4. **Refunds & Prorations:**
   Operators need the ability to issue refunds and handle proration during subscription changes.
   - Target: `charge.refund` parity and webhook convergence for refunds.

## Architectural Recommendations for v1.32 Roadmap

1. **Phase 1: Advanced Subscription Lifecycle & Mutation.** Implement plan swaps, quantity changes, and pause/resume logic for Braintree adapters, alongside the required webhook event parsing to converge these changes locally.
2. **Phase 2: Payment Method CRUD & Operator Admin.** Extend the `AccrueAdmin` UI and the `Accrue.Billing` facade to handle Braintree payment method updates (adding new vaulted methods, deleting, setting default).
3. **Phase 3: Refunds and Invoice Parity.** Implement the Braintree refund flow and ensure the local `Invoice` / `Charge` records correctly project Braintree's transaction statuses.
4. **Phase 4: The "Portal" Question.** Address `create_billing_portal_session/2`. Since Braintree lacks a hosted portal, Accrue must either provide a unified local portal or explicitly document the Braintree local-portal alternative.

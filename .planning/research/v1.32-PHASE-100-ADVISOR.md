# Braintree Billing Portal: Architectural Decision Record (Phase 100)

## Context & The Gray Area
Accrue provides `Accrue.Billing.create_billing_portal_session/2`, which perfectly maps to Stripe's Hosted Billing Portal. Braintree has no hosted equivalent.
**Decision:** How do we handle this API call when the underlying processor is Braintree?

* **Option A: Explicit Documentation (Headless)** - Keep Accrue as a strict API wrapper. Throw an error on Braintree, but provide a comprehensive guide on building a custom local portal using Accrue's primitives.
* **Option B: Unified Local Portal UI** - Ship Phoenix LiveView components within Accrue to provide an out-of-the-box "Stripe-like" portal for Braintree.

---

## Analysis & Trade-offs

### Option A: Explicit Documentation (Headless Backend)
Accrue acts purely as an API layer, returning an explicit error for Braintree and delegating the UI to the host application.

**Pros:**
* **Zero UI Coupling:** Host apps retain 100% control over branding, routing, CSS (Tailwind, Bootstrap, etc.), and frontend tech (LiveView, React, Vue).
* **Architectural Purity:** Accrue remains a true API facade and state-machine, avoiding heavy dependencies like `phoenix_live_view`.
* **Principle of Least Surprise:** Stripe has a portal; Braintree does not. Developers understand gateway limitations.

**Cons:**
* **Developer Friction:** Developers switching from Stripe to Braintree must manually build the UI for managing payment methods and subscriptions.

**Example DX:**
```elixir
case Accrue.Billing.create_billing_portal_session(customer) do
  {:ok, session} -> redirect(conn, external: session.url)
  {:error, %Accrue.APIError{code: :unsupported_by_gateway}} -> 
    # Braintree flow: fallback to custom local portal
    redirect(conn, to: ~p"/settings/billing")
end
```

### Option B: Unified Local Portal UI (LiveView Engine)
Accrue ships drop-in LiveView components to emulate a hosted portal.

**Pros:**
* **True Parity:** Absolute feature parity across gateways.
* **Developer Ergonomics:** Drops a fully functional billing UI into any Elixir app with minimal code.

**Cons:**
* **Scope Creep & Maintenance:** Shipping an opinionated UI is notoriously difficult (e.g., handling dark mode, custom domains, varying Phoenix versions).
* **Security Surface:** Accrue would have to render and manage Braintree's Drop-in UI or Hosted Fields securely.
* **Lock-in:** Requires the host application to use LiveView.

**Example DX:**
```elixir
# router.ex
forward "/billing", Accrue.Web.Portal, otp_app: :my_app
```

## Ecosystem Idioms & Lessons Learned

### Idiomatic Elixir / Phoenix
The Elixir ecosystem strongly favors **composability over configuration**. Libraries like `Pow` (authentication) and `Oban` (background jobs) historically provided web UIs but kept them strictly separated (`Oban.Web` is a separate package, Pow generates templates into the host app). Pluggable, headless cores are idiomatic. Shipping a mandatory UI in a core backend library violates the ecosystem's separation of concerns.

### Lessons from Other Languages
* **Ruby on Rails (`Pay` gem):** `Pay` is a massive success. It acts exactly like Accrue (a backend wrapper for Stripe/Braintree/Paddle). It explicitly **does not** ship a UI. It provides the database models and webhooks, leaving the view layer to the developer. This kept `Pay` maintainable and universally adoptable.
* **Laravel (`Cashier` vs `Spark`):** Laravel Cashier is headless and free. Laravel Spark is a paid, full-stack billing UI. Spark has historically struggled with customization (switching from Vue to Blade, dealing with Tailwind versions), proving that billing UIs are highly subjective and brittle.

**What they did right:** Headless wrappers (Pay, Cashier) succeeded by providing rock-solid webhook handling and unified APIs without dictating the frontend.

**Footguns to avoid:** Forcing a CSS framework or JavaScript framework onto the host app for billing.

## One-Shot Recommendation

**We must proceed with Option A (Explicit Documentation).**

Accrue must remain a headless backend facade. Introducing LiveView components into `Accrue.Billing` would fundamentally change the library's architecture, pull in massive dependencies, and create a maintenance nightmare for edge-case styling requests.

To deliver excellent DX while remaining headless:
1. **Explicit Error:** `create_billing_portal_session/2` should return a clear, documented error when used with Braintree: `{:error, %Accrue.APIError{code: :unsupported_by_gateway, message: "Braintree does not support hosted billing portals..."}}`.
2. **First-Class Guide:** We must write an exhaustive guide (`guides/braintree-local-portal.md`) showing exactly how to build the required LiveView UI using Accrue's existing `Accrue.Billing` functions (adding cards via Braintree Hosted Fields, swapping plans, etc.).
3. **Symmetry:** By providing the exact recipes, we bridge the DX gap without taking on the UI maintenance burden. This respects the Elixir idiom of headless cores while honoring the developer's need for a smooth implementation path.

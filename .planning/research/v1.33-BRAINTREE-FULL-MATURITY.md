# Research Summary: Accrue v1.33 Braintree Full Maturity

**Domain:** Billing Abstraction / Payment Gateways
**Researched:** Current Date
**Overall confidence:** HIGH

## Executive Summary

Reaching "full maturity" parity with Stripe for our Braintree integration requires addressing five major gaps. While Braintree and Stripe often handle basic subscriptions and payments similarly, they diverge heavily on hosted UIs, metered billing, and marketplace routing.

For features like Checkout and Customer Portal, Braintree simply does not offer hosted equivalents; Accrue will need to build its own first-party local UIs. For Metered Billing and Connect, Braintree lacks the native APIs Stripe has, requiring Accrue to either build aggregation engines (for metered billing) or integrate entirely new products like PayPal Hyperwallet (for Connect).

## Key Findings

**Stack:** Phoenix LiveView for Local UIs; Hyperwallet (PayPal) for payouts.
**Architecture:** Accrue must move from being a pure API wrapper to providing stateful aggregation and hosted UI components.
**Critical pitfall:** Attempting to force Braintree into Stripe's Connect model; Hyperwallet is a fundamentally different architecture.

## Detailed Gap Analysis & Architectural Approaches

### 1. `Accrue.Billing.create_checkout_session/2` Parity
**Stripe:** Fully hosted checkout page (`checkout.stripe.com`).
**Braintree:** No hosted checkout offering. Relies on Hosted Fields embedded in the merchant's site. (Drop-in for Web is deprecated 2025-07-14 and unsupported 2026-07-14 per PayPal/Braintree's deprecation notice — Phase 101 ships on Hosted Fields, NOT Drop-in.)
**Architectural Approach:**
We must build an "Accrue Checkout" local UI. `create_checkout_session/2` for Braintree generates an internal session token and returns a URL to a Phoenix LiveView-based checkout page hosted by the host app (mounted via the `Accrue.Portal` router pipeline shipped in the new sibling `accrue_portal` Hex package). This page renders Braintree Hosted Fields (field-by-field iframe injection via Braintree's JS SDK), collects the payment method nonce, and maps it back to the Accrue Checkout Session lifecycle.

### 2. Coupons and Promotion Codes
**Stripe:** First-class `Coupon` and `PromotionCode` objects that can be applied to Checkouts and Subscriptions.
**Braintree:** Uses `Discounts` (which reduce cost) and `Add-ons` (which increase cost) attached to plans or directly to subscriptions. There is no concept of a "Promo Code" that a user types in to dynamically fetch a discount.
**Architectural Approach:**
Accrue must maintain a local database of "Promotion Codes" that map to Braintree "Discounts". When a user enters a promo code in the Accrue Checkout, Accrue validates it locally and, upon subscription creation, applies the corresponding Braintree Discount ID.

### 3. Metered Usage Support
**Stripe:** Native `MeterEvent` API where you report usage and Stripe calculates the bill dynamically.
**Braintree:** No native metered billing for subscriptions.
**Architectural Approach:**
Accrue already has a `report_usage/3` footprint. To support Braintree, Accrue must implement its own Metering Engine (likely via an Oban worker).
*Option A (Manual Sales):* Accrue aggregates usage in the database and creates a separate `Transaction.sale` against the vaulted payment method at the end of the month.
*Option B (Dynamic Add-ons):* Accrue dynamically updates a specific "Usage Add-on" on the Braintree Subscription right before the billing cycle renews.
*Recommendation:* Option A is safer as it avoids race conditions with Braintree's subscription lifecycle.

### 4. Connect (Marketplace / Split Payments)
**Stripe:** Stripe Connect handles pay-ins, KYC, split payments, and payouts via a unified API.
**Braintree:** Braintree Marketplace is functionally deprecated for new integrations. PayPal dictates using Braintree for pay-ins and **PayPal Hyperwallet** for payouts.
**Architectural Approach:**
Achieving Connect parity with Braintree means integrating a completely separate system (Hyperwallet). This is a massive scope increase. Accrue would need to abstract both Braintree and Hyperwallet under an `Accrue.Connect` namespace, handling the transfer of funds between the two. This may be a candidate for explicit capability rejection if the scope is too large.

### 5. First-Party Local Portal UI
**Stripe:** Fully hosted Customer Portal (`billing.stripe.com`).
**Braintree:** No hosted portal. As documented in v1.32, we rejected the capability temporarily.
**Architectural Approach:**
Similar to Checkout, Accrue must ship a LiveView-based `Accrue.Portal` that host applications can mount in their router. It will need views for:
- Viewing active subscriptions
- Updating/Vaulting Payment Methods (via Braintree Hosted Fields)
- Viewing Invoice/Transaction history
- Canceling subscriptions

## Implications for Roadmap (v1.33)

Based on research, suggested phase structure for v1.33:

1. **Phase 1: Accrue Portal Foundation & Checkout** - Build the Phoenix LiveView infrastructure for `Accrue.Portal` to solve both Checkout Session and Customer Portal gaps.
2. **Phase 2: Coupon/Discount Mapping** - Implement the local promotion code resolution layer that maps to Braintree Discounts.
3. **Phase 3: Metering Engine** - Build the local aggregation engine to support `report_usage` and execute manual vaulted charges for Braintree.
4. **Phase 4: Connect Spike/Decision** - Deeply investigate Hyperwallet and decide whether to implement it or explicitly document Connect parity as a non-goal for Braintree.

# Phase 101 Area A — Portal Package Home + Phase 100 Reconciliation

**Advisor:** GSD discuss-phase research, gray area A
**Phase:** v1.33 / 101 — "Accrue Portal Foundation & Checkout"
**Date:** 2026-05-01
**Confidence:** HIGH on package-home recommendation; MEDIUM on reconciliation wording (depends on whether the user wants to softly retract D-08 or carve a named exception)

## TL;DR Recommendation

**Ship `Accrue.Portal` as a NEW sibling package `accrue_portal` (third package in the monorepo).** It hard-deps `phoenix_live_view ~> 1.1`, mounts via `accrue_portal/2` router macro mirroring the `accrue_admin/2` shape, and sits namespaced as `Accrue.Portal.*` (under the `Accrue` umbrella, like `Accrue.BillingPortal` already is). **Phase 100 D-01 is narrowed, not reversed**: `accrue` core stays headless (no LiveView routes, no controllers — only `Phoenix.Component` HEEx for emails/PDF, which is already there); `accrue_portal` is the explicit, named UI-shipping seam. `braintree-local-portal.md` becomes a "build-your-own" alternative cross-linked from the new portal docs as the documented escape hatch for hosts that don't want LiveView.

## Cross-package analogues

- **Pay (Rails)** — Headless backend wrapper, no `app/views/` or `app/controllers/` for billing UI. Hosts (or starter kits like Jumpstart) own the view layer entirely. **Lesson:** Pay's adoption-velocity and longevity come precisely from refusing to ship UI. Accrue must not lose that property.
- **Laravel Cashier** — Ships some Blade views (invoice receipt, generic payment confirmation). The customization story is `php artisan vendor:publish`, which forks the views into the host app and "you own the upgrade burden forever." Filament's Dan Harrin documented this as a footgun. **Lesson:** if Accrue ships UI, do NOT use a "publish-into-host" pattern — keep views in the package and let the host override via slot/component injection.
- **Bling + Bankroll (Elixir)** — Same author ships two packages: `bling` (headless Stripe wrapper, registers two routes via `bling_routes/1`) and `bankroll` (prebuilt subscription-management UI built on Bling). **Lesson:** This is the precedent we should copy verbatim. `accrue` = bling, `accrue_portal` = bankroll. The split has been validated by an active Elixir billing library author.
- **Spree → Solidus** — Spree shipped `spree_frontend` / `spree_backend` / `spree_api` as separate gems precisely to allow API-only hosts to escape the frontend churn. Solidus forked partly because frontend coupling made Spree unmaintainable. **Lesson:** keep the UI gem optional from day one; do NOT make it a transitive dep of core.
- **Oban + Oban Web** — Oban Web was a paid product, then open-sourced in 2025, ships as a separate Hex package, requires explicit `oban_web_routes/1` mount. Pretty much every production Oban deployment uses Oban Web, but Oban core does not depend on it. **Lesson:** "almost everyone uses both" is NOT a reason to merge them. Optional UI compounds.
- **Phoenix + Phoenix.LiveDashboard** — LiveDashboard is shipped *with* a fresh Phoenix install but is a separate Hex package and hard-removed from prod by default (`if Mix.env() == :dev`). **Lesson:** when a UI is "obviously useful," ship it separately and let the host decide environment-gating. We can mirror this — Phoenix's installer scaffolds add `accrue_portal` to deps but commented out.
- **Stripe.js / Stripe Elements vs. `lattice_stripe`** — Stripe themselves separate the JS/UI bundle (Stripe.js, Elements, Checkout) from the API client (Stripe Ruby/Node/etc.). The JS bundle is loaded from `js.stripe.com`, never bundled into the API client. **Lesson:** even Stripe doesn't ship UI in the API library. Accrue should not either.
- **Lago (open-source billing)** — Ships `lago-api` (Rails backend) and `lago-front` (Vue frontend) as separate repos and separate Docker images. **Lesson:** even when both are first-party and lock-stepped at release, the separation lets ops teams scale them independently and lets API-only consumers ignore the UI entirely.

## Phase 100 reconciliation move

**Pick: NARROW D-01.** D-01 was written with "Accrue" meaning "the `accrue` core package." The deferred-rejection in 100-CONTEXT.md only rejected putting the portal into `accrue_admin` — it did not consider a third sibling package, because Phase 100's gray area was binary (core vs. admin). v1.33 introduces a third option that the Phase 100 advisor never evaluated. This is not a reversal; it is a refinement under new information (the v1.33 BRAINTREE-FULL-MATURITY research, which documents Braintree's complete absence of hosted UI as a structural-not-tactical gap).

D-08's "explicit error + documentation recipe" precedent is preserved as the **default behavior of `accrue` core** (the Braintree processor still returns `{:error, %Accrue.APIError{code: :unsupported_by_gateway}}` from `Accrue.Billing.create_billing_portal_session/2`), and the recipe doc remains valid for any host that prefers to hand-roll. `accrue_portal` is positioned as the **first-party, opt-in, batteries-included alternative** for hosts that want the recipe pre-built.

**Amended D-01 wording for Phase 101 CONTEXT.md to cite:**

> **D-01 (amended, v1.33-101):** The `accrue` core package must remain a headless backend facade — no LiveView routes, no controllers, no end-user-facing UI. First-party UI for end-user-facing billing flows (checkout, customer portal) is shipped in the dedicated sibling package `accrue_portal`, which hosts opt into explicitly. The "explicit error + documentation recipe" pattern (D-03/D-04/D-05) remains the contract for hosts that decline `accrue_portal`.

Add a one-line note to PROJECT.md "Constraints" or wherever package list lives:

> Monorepo packages: `accrue` (core, headless), `accrue_admin` (operator UI), `accrue_portal` (end-user billing UI). Only `accrue` is required.

## Concrete artifact lock-ins

- **Package name:** `accrue_portal` (snake_case Hex name; `AccruePortal.*` OTP app + `Accrue.Portal.*` public namespace under the umbrella). See namespace note below.
- **Mix.exs deps additions in `accrue_portal/mix.exs`:**
  - `{:accrue, "== <same version>"}` — exact version match like `accrue_admin` does
  - `{:phoenix, "~> 1.8"}`
  - `{:phoenix_live_view, "~> 1.1"}`
  - `{:phoenix_html, "~> 4.2"}`
  - `{:plug, "~> 1.16"}`
  - `{:jason, "~> 1.4"}` (for Drop-in client_token JSON)
  - Dev/test: `{:lazy_html, ">= 0.1.0", only: :test}`, `{:plug_cowboy, "~> 2.7", only: :test}`, `{:ex_doc, "~> 0.40", only: [:dev, :test], runtime: false}`, `{:credo, "~> 1.7", only: [:dev, :test], runtime: false}`, `{:dialyxir, "~> 1.4", only: [:dev, :test], runtime: false}`
  - **NOT** added: `:lattice_stripe` or `:braintree` directly — those reach the portal through `Accrue.Billing` / `Accrue.Processor` only. Portal stays processor-agnostic, with adapter-specific UI bits (Drop-in script tag, Stripe Elements config) gated by `Accrue.Processor.capabilities/1` checks at render time.

- **Release-please config delta needed:** YES, but trivial. Add a third package to `release-please-config.json`:
  ```json
  "accrue_portal": {
    "component": "accrue_portal",
    "release-type": "elixir",
    "package-name": "accrue_portal",
    "changelog-path": "CHANGELOG.md",
    "include-component-in-tag": true
  }
  ```
  And add `"accrue_portal"` to the `linked-versions` `components` array. Verify with a dry-run that `accrue_portal--release_created` output naming works (Release Please v4 prefix change documented in CLAUDE.md).

- **Namespace:** `Accrue.Portal.*` (NOT `AccruePortal.*` for public modules). Justification:
  - Phoenix convention is one OTP app + one public namespace prefix; `accrue_admin`'s OTP app is `:accrue_admin` but it uses `AccrueAdmin.*` because it is *adjacent* to Accrue (operator tools), not *part of* Accrue's billing API.
  - The portal IS part of Accrue's billing flow — `Accrue.Billing.create_checkout_session/2` returns a URL into the portal; `Accrue.Portal.Checkout.Session` is the LiveView that fulfills that URL. Mirroring the existing `Accrue.BillingPortal` (Stripe portal facade) namespace keeps the public API coherent.
  - OTP app stays `:accrue_portal` so users can `application: [:accrue_portal]` independently.
  - Internal/private modules can be `AccruePortal.*` (e.g., `AccruePortal.Router`, `AccruePortal.Application`, `AccruePortal.Endpoint.Helper`); public/user-facing modules are `Accrue.Portal.*` (e.g., `Accrue.Portal.Checkout`, `Accrue.Portal.Customer`, `Accrue.Portal.Drop-in`).
  - Precedent: `Phoenix.LiveDashboard` (public) in `:phoenix_live_dashboard` (OTP app).

- **Router macro:** `accrue_portal "/billing", session_keys: [:current_user_id], on_mount: [{MyAppWeb.UserAuth, :ensure_authenticated}]` — mirrors the `accrue_admin/2` shape from `accrue_admin/lib/accrue_admin/router.ex` line-for-line, with these differences:
  - Default `on_mount` hook is `{AccruePortal.AuthHook, :ensure_customer}` instead of `:ensure_admin`
  - No step-up MFA scaffolding (customer flows shouldn't require it by default)
  - Live routes mount end-user views (`Accrue.Portal.CheckoutLive`, `Accrue.Portal.SubscriptionsLive`, `Accrue.Portal.PaymentMethodsLive`, etc.)
  - Same sibling-`live_session` pattern to avoid the nested-`live_session` Phoenix bug

- **Where guide `accrue/guides/braintree-local-portal.md` should be migrated/cross-linked:**
  - **Keep in `accrue/guides/`** as the documented "I don't want LiveView / I'm using Inertia / I'm using LiveSvelte / I'm hand-rolling" recipe. It is the D-03/D-08 honoring contract.
  - **Add cross-link at the top** of that guide: "If you want a first-party batteries-included LiveView portal instead, see `accrue_portal` (added v1.33). This guide remains for hosts that prefer to hand-roll the portal in their own UI stack."
  - **Add reverse cross-link** from `accrue_portal` README: "If you do not want LiveView in your billing path, you can hand-roll the portal using `Accrue.Billing` primitives — see [`accrue/guides/braintree-local-portal.md`](https://hexdocs.pm/accrue/braintree-local-portal.html)."
  - **Update `Accrue.Billing.create_billing_portal_session/2` ExDoc** to mention both paths: "On Stripe → returns Stripe portal URL. On Braintree → returns `{:error, :unsupported_by_gateway}` with a message pointing to (a) the local-portal recipe guide for hand-rolling, OR (b) `accrue_portal` for the batteries-included LiveView portal."

## High-impact fork flag

**HIGH_IMPACT: true**

This decision creates a NEW public Hex package under the v1.33 milestone. Package naming, OTP app name, public namespace, and release-please coupling are all effectively irreversible after the first publish — renaming a published Hex package is messy and breaks every downstream `mix.exs`. The user must personally confirm:

1. **Package name = `accrue_portal`** (vs. `accrue_web`, `accrue_ui`, `accrue_checkout`, `bankroll`-style invented name). My recommendation is `accrue_portal` because v1.33 calls it `Accrue.Portal` everywhere and `_portal` is the most-Googleable suffix for "Stripe billing portal equivalent."
2. **Public namespace = `Accrue.Portal.*`** (vs. `AccruePortal.*`). Disagreeing here is fine but should be locked before any module is written.
3. **Phase 100 D-01 is narrowed, not reversed** — i.e., we are NOT amending PROJECT.md to remove the "headless" identity; we are clarifying that "headless" applies to `accrue` core specifically and that the monorepo now has a named UI-shipping sibling.
4. **Release-please lockstep** — adding a third package to the `linked-versions` group means all three packages release together at v1.33.0. If the user wants `accrue_portal` to ship at `0.1.0` (signaling "young, may iterate") while `accrue` and `accrue_admin` stay at `1.33.0`, that requires breaking the linked-versions group — a separate decision.

If the user disagrees with the package-home recommendation itself (i.e., "no, just put it in `accrue_admin`" or "no, put it in core"), the rest of this advisor's downstream artifacts (mix.exs deps, namespace, router macro, release config) all change. Get sign-off on package home FIRST.

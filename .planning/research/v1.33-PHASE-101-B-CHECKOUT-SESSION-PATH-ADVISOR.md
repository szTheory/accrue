# Phase 101 Area B — `create_checkout_session/2` Braintree Path

## TL;DR Recommendation

**Path 1 (adapter route).** Braintree's `checkout_session_create/2` callback returns a `%Accrue.Checkout.Session{}` whose `:url` points at the host-mounted `Accrue.Portal` checkout LiveView (`/<portal_mount>/checkout/<session_token>`). The Braintree adapter flips its capabilities to `checkout: %{create: true, fetch: true, hosted: true, embedded: false}` and a NEW support label `"first-party local portal"` is added for `:checkout.{create,fetch,hosted}`. `:embedded` is deferred — `:hosted` only in v1.33. Success signal lands as a NEW internal Accrue event `accrue.portal.checkout.completed` projected through the existing webhook/event machinery (not a Braintree webhook — local LV submission triggers Oban "checkout completion" job that builds the synthetic event, mirroring how Stripe's `checkout.session.completed` lands). The same telemetry span `[:accrue, :billing, :checkout_session, :create]` covers both paths because dispatch happens INSIDE `Processor.__impl__()`.

This preserves the v1.32 Phase 100 ADR's spirit (capability-explicit, no silent-success lies) while delivering on v1.33's roadmap promise that "host apps can mount `Accrue.Portal` and route customers through a first-party hosted checkout." The Braintree-served URL is honestly first-party, not impersonating Braintree.com.

## Cross-package analogues

- **Stripe Checkout vs Stripe.js Elements** — Stripe ships TWO products with TWO distinct entry points (`stripe.checkout.sessions.create` for hosted; `stripe.elements()` for embedded), even though both end at the same PaymentIntent. The lesson: the SAME verb returning EITHER `:url` OR `:client_secret` (Accrue's current `:hosted | :embedded` ui_mode model) is already a single verb covering two product surfaces. Path 1 extends that pattern: same verb, the `:url` just points at YOUR domain instead of stripe.com.
- **Pay (Rails)** — `pay.subscribe(plan: ...)` works for Stripe and Braintree but Braintree REQUIRES the host to acquire `payment_method_token` first (Drop-in nonce in the host's own form). Pay does NOT ship a checkout UI — it punts on the page that collects payment data. Path 1 is more ambitious than Pay (we ship the page) but matches Pay's facade-symmetry instinct.
- **Cashier-Braintree** — Historical `Billable::redirectToBilling` exists for Stripe; Cashier-Braintree shipped a `BraintreeController` that mounts a server-rendered checkout page in the host's app. The verb existed but the URL pointed at the host's own controller. Direct precedent for Path 1.
- **Bamboo `SentEmailViewerPlug`** — Bamboo ships an OPTIONAL UI surface as a separate plug the host mounts. Bamboo's CORE API does NOT route through it. Closest precedent for Path 3 — but Bamboo's plug is a debug-only viewer, not production checkout. Different stakes.
- **Phoenix LiveDashboard** — Lives in `phoenix_live_dashboard` package, mounted via `live_dashboard "/dashboard"` macro. Host explicitly opts in. Strong Path 3 precedent — but LiveDashboard is observability, not a payment surface where API symmetry across providers is the headline value prop.
- **Oban / Oban Web** — Same pattern as LiveDashboard: core does jobs, `oban_web` is a separate package with its own mount macro. Oban does not "short-circuit `Oban.insert/2` for some users to render a UI." Strong against Path 2.

## Side-question lock-ins

- **`success_url` / `cancel_url` / `return_url` semantics:** Mirror Stripe exactly. Portal LiveView reads them from the session record and redirects on completion / abandonment. If `nil`, portal renders an in-place "Subscription created" panel (matches Stripe's no-redirect behavior when omitted). NO portal-computed defaults — host owns redirect targets.
- **`ui_mode :hosted`:** Supported in v1.33. URL shape: `https://<host>/<portal_mount>/checkout/<opaque_session_token>` where `<opaque_session_token>` is a 32-byte URL-safe base64 token persisted in a new `accrue_checkout_sessions` table (not the Braintree client token — that's separate, fetched server-side at LV mount).
- **`ui_mode :embedded`:** **Deferred to v1.34+.** Braintree Drop-in CAN run inline, but supporting `:embedded` requires Accrue to ship a JS hook + LV component the host mounts in their own LV. Adds JS bundle distribution complexity. v1.33 capability declares `embedded: false`. Rationale documented in capability label: `"out of slice"`.
- **`operation_id` (idempotency):** The local portal persists the `accrue_checkout_sessions` row keyed by `operation_id` when present. Re-calls with the same `operation_id` return the same session token / URL. Mirrors Stripe's idempotency semantics. Uses existing `Accrue.Processor.Idempotency.subject_uuid(:checkout_session_create, operation_id)` for the row PK so Stripe and Braintree share the same idempotency derivation.
- **Webhook / event surface:** Braintree has no `checkout.session.completed`. The portal LV, on successful Drop-in nonce → subscription create, enqueues an Oban job that writes a synthetic `%Accrue.Webhook.Event{type: "accrue.portal.checkout.completed", source: "accrue.portal", ...}` row. The existing `Accrue.Webhook.DefaultHandler` reduces that into the same downstream projection path as `checkout.session.completed`. Telemetry: `[:accrue, :portal, :checkout, :completed]` (NEW, mirrors Stripe's `[:accrue, :webhook, :checkout, :completed]`). Subscribers attach to BOTH for full coverage.
- **Capability label:** Add row `checkout: %{create: "first-party local portal", fetch: "first-party local portal", hosted: "first-party local portal", embedded: "out of slice"}` REPLACING the current `"Stripe-only"` strings. Add `billing_portal: %{create: "first-party local portal"}` similarly when Phase 100 reverses. The `support_label/1` helper unchanged. New label string acknowledges that the support is real but architecturally different from `"all first-party"` (which means "every adapter implements it the same way against the upstream provider").
- **Braintree adapter capabilities map delta:** Add `checkout: %{create: true, fetch: true, hosted: true, embedded: false}` (between `invoice:` and `webhook:`). Keep `billing_portal: %{create: false}` for v1.33 if Phase 100's reversal is sequenced separately; if Phase 101 ships portal foundation that covers both, flip it to `true` here in lockstep.

## High-impact fork flag

**HIGH_IMPACT: true**

Two reasons the human should personally confirm before Phase 101 plans:

1. **The `"first-party local portal"` support label is a NEW public taxonomy.** Once shipped in `@support_labels`, removing or renaming it later is a breaking change to every host that introspects capabilities (the v1.31/95/96 audit work specifically MADE these labels public). This locks Accrue into a three-tier honesty model (`"all first-party"`, `"first-party local portal"`, `"out of slice"`) for the foreseeable future. Reasonable but worth one explicit nod from the human.

2. **Choosing Path 1 over Path 3 commits the project to symmetry-as-headline-value.** This is consistent with the Pay/Cashier philosophy and the project's Phoenix-idiomatic posture, but it contradicts the v1.32 Phase 100 ADR which chose explicit `:unsupported_by_gateway` for the billing portal. Path 1 here implies Phase 100's decision should ALSO be reversed in Phase 101 (billing portal session create should ALSO route to local portal for Braintree, with the same support label). If the human wants Path 3 for honesty-uber-alles, that's defensible too — but the choice cascades. Specifically: choose Path 1 for checkout, you almost certainly have to flip Phase 100's billing portal verb to Path 1 as well, retroactively undoing the recently-shipped guide `guides/braintree-local-portal.md`. That cross-decision impact is what makes this a fork the human should sign off on, not the agent.

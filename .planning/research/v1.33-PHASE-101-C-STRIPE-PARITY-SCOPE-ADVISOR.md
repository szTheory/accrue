# Phase 101 Area C — Stripe Parity vs Braintree-only Scope

## TL;DR Recommendation

**Pick Scope 1: Braintree-only escape hatch.** `Accrue.Portal` ships as a named, capability-explicit slice that activates only when the configured processor lacks hosted UI. Stripe's `create_checkout_session/2` and `create_billing_portal_session/2` behavior is **unchanged** post-Phase-101 (still return Stripe-hosted URLs). No new public flag is introduced; the existing capability check (`Accrue.Processor.supports?([:billing_portal, :create])`) already encodes the asymmetry, and `billing.ex` already documents it. **No STRATEGY.md amendment is required** — this scope is the literal reading of the existing "checkout and billing portal remain Stripe-first until another first-party processor proves them honestly" line. Scope 3 (opt-in for Stripe) is the runner-up but is explicitly deferred to v1.34+ behind a real customer ask.

## Cross-package analogues

- **Pay (Rails, `pay-rails/pay`):** Backend + emails + a single SCA-handoff `payments#show` page. NO checkout UI, NO billing portal UI shipped. Stripe hosts redirect to Stripe Checkout; Braintree hosts hand-roll. This is the closest precedent to Accrue and points squarely at Scope 1.
- **Laravel Cashier-Stripe vs Cashier-Braintree:** Cashier-Stripe documents Stripe Checkout as the path; Cashier-Braintree (Laravel 5.8 era, now legacy/abandoned) required hand-rolled Blade views — *the host built UI*, not the library. Cashier-Braintree was deprecated in part because no one wanted to maintain that asymmetric UI surface. Direct precedent that Scope 2 leads to abandonment.
- **Lago:** API-first; ships hosted Stripe checkout via Stripe's redirect URL and leaves all customer-portal UX to the host (or Lago's own admin UI). Confirms the "let the hosted processor stay hosted" pattern.
- **Spree / Solidus:** Per-gateway view partials in `lib/views/frontend/spree/checkout/payment/_stripe.html.erb`, `_paypal_braintree.html.erb`. Multiple gateway UIs, never one unified. Same model as Scope 1.
- **Chargebee / Recurly:** Both offer "hosted pages OR in-app components" as a documented per-merchant choice with explicit PCI/wallet tradeoffs. They are the *only* major precedent for Scope 3, but they're SaaS vendors who can amortize the matching docs/support cost across thousands of merchants. Accrue (single-author OSS) cannot.
- **Stripe Checkout vs Elements PCI reality (correction to the input prompt):** Both Stripe Checkout and Stripe Elements qualify for **SAQ-A** when the iframe is built client-side. The PCI delta is therefore not Scope 2's biggest problem — wallet conversion (Link, Apple/Google Pay polish) and Radar hosted-page signals are.
- **Braintree Drop-in deprecation (PayPal/Braintree, 2025-07-14 → deprecated, 2026-07-14 → unsupported for Web):** Phase 101 cannot build on Drop-in long-term. Hosted Fields is the supported path. This is independent of which scope we pick but is load-bearing for Phase 101 implementation.

## Concrete artifact lock-ins

- **Public scope of `Accrue.Portal`:** Braintree-only (capability-gated). Activates whenever `Accrue.Processor.supports?([:billing_portal, :create])` returns `false` (today: Braintree; future: any first-party processor missing hosted UI). Stripe is permanently outside the portal's compile/runtime path.
- **Behavior of `Accrue.Billing.create_checkout_session/2` for Stripe (post-Phase-101):** **Unchanged.** Continues to return a `%Accrue.Checkout.Session{}` with a Stripe-hosted URL (or `client_secret` for `:ui_mode :embedded`). No new `:ui_mode` value introduced.
- **Behavior of `Accrue.Billing.create_billing_portal_session/2` for Stripe (post-Phase-101):** **Unchanged.** Continues to return a Stripe-hosted billing-portal URL via `lattice_stripe`'s `BillingPortal.Session`.
- **Behavior of `Accrue.Billing.create_billing_portal_session/2` for Braintree (post-Phase-101):** Currently returns `{:error, %Accrue.APIError{code: :unsupported_by_gateway}}` directing to `guides/braintree-local-portal.md`. Phase 101 **changes this to return `{:ok, %Accrue.BillingPortal.Session{url: <local-portal-mount-path>, ...}}`** with a host-mount-relative path (or a host-configured base URL). The error path remains for hosts who haven't mounted the portal router pipeline.
- **Behavior of `Accrue.Billing.create_checkout_session/2` for Braintree (post-Phase-101):** Currently raises (no Braintree adapter for checkout). Phase 101 makes it return `{:ok, %Accrue.Checkout.Session{url: <local-portal-mount-path>/checkout/<session_id>, ...}}`.
- **New config flag(s) introduced:** Exactly one — `:portal_mount_path` (string, default `"/accrue/portal"`) so hosts can customize where they mount the portal router. **Do NOT** introduce `:ui_mode :local_portal`; that locks the API surface in a direction we may regret. Capability-gating is sufficient.
- **Underlying Braintree client lock-in:** Phase 101 builds on **Braintree Hosted Fields**, not Drop-in. Drop-in for Web is deprecated 2025-07-14 and unsupported 2026-07-14 per PayPal/Braintree's deprecation notice. (This is an implementation choice, not a scope choice — applies equally to all three scopes — but must be locked at the Phase 101 entry.)
- **STRATEGY.md amendment text (if needed):** **None.** The existing line "checkout and billing portal remain Stripe-first until another first-party processor proves them honestly" is literally satisfied: Stripe stays hosted; Braintree gets a parallel first-party local slice that does NOT change Stripe's experience. Confirm the line stays as-written.
- **Capability map row(s) to add:**
  - `processors.braintree.capabilities.checkout_session.create: :first_party_local_portal` (was: `:unsupported`)
  - `processors.braintree.capabilities.billing_portal.create: :first_party_local_portal` (was: `:unsupported`)
  - `processors.stripe.capabilities.checkout_session.create: :hosted` (already implicit; make explicit)
  - `processors.stripe.capabilities.billing_portal.create: :hosted` (already implicit; make explicit)
  - Add new capability value vocabulary entry: `:first_party_local_portal` with the meaning "served via `Accrue.Portal` mounted in the host router."

## High-impact fork flag

**HIGH_IMPACT: false**

Scope 1 is the literal reading of STRATEGY.md and matches the asymmetry already shipped in `accrue/lib/accrue/billing.ex` (the `unsupported_by_gateway` error path explicitly references `guides/braintree-local-portal.md`). It introduces zero behavior change for Stripe adopters, requires no STRATEGY.md amendment, and locks no new public flag into the v1.x SemVer surface. The user is the sole adopter of v1.32 and the codebase already commits to this asymmetry — confirming Scope 1 is a continuation, not a fork.

The only adjacent fork that *would* be HIGH_IMPACT (and is being explicitly deferred here) is Scope 3's opt-in flag. Surface that as a v1.34+ candidate only if a real Stripe-using host asks for white-labeled checkout. Until then, Stripe-Hosted's free polish (Link, Apple/Google Pay, Radar hosted signals, ~35 locales) is value Accrue cannot match and should not pretend to.

# Phase 101 Area D — Host Mount + End-user Auth Surface

**Confidence:** HIGH on D.1 mount shape; HIGH on D.2 (Pure on_mount with hint hook); MEDIUM on D.3 (URL-token scope deferral may be fork-worthy).

**Assumed package home (from Area A):** new sibling `accrue_portal` package, public namespace `Accrue.Portal.*`. The same recommendations work if the user reverses Area A and places this in `accrue_admin` — see "Concrete artifact lock-ins" for the only field that changes (macro module path).

## TL;DR Recommendation

**D.1 — Macro that mirrors `accrue_admin/2`** (`Accrue.Portal.Router.accrue_portal/2`). One-line mount, same author, same shape, no surprise to anyone reading `AccrueHostWeb.Router`. **D.2 — Pure `on_mount` convention with a host-implemented hook + a published default hook (`Accrue.Portal.AuthHook`) that hosts can swap or wrap.** Do NOT introduce a new `Accrue.Portal.Auth` behaviour — the existing `Accrue.Auth` already covers the "host owns auth" contract, and the customer-portal needs are LV-shaped (`on_mount`), not plug-shaped. **D.3 — Session-resolved customer ONLY in v1.33.** Magic-link / URL-token checkout (the "subscribe via emailed link, user not yet authenticated" flow) is real, but the security surface is too large for v1.33 maturity — defer to v1.34+ with a documented integration recipe in the meantime. This is the ONE high-impact fork below.

## D.1 Comparison Table — Mount API Shape

| Criterion | Macro `accrue_portal/2` (mirror admin) | Plug + manual wiring | Endpoint plug + sub-router |
|---|---|---|---|
| Boilerplate per host | ~3 lines (`import` + `accrue_portal "/billing", on_mount: [...], session_keys: [...]`) | 30-50 lines (pipeline, scope, live_session, 6+ live routes) | ~5 lines but Phoenix-foreign (`forward`-style) |
| Consistency with existing Accrue codebase | IDENTICAL to `accrue_admin/2` (which user already uses in `examples/accrue_host`) | Inconsistent — admin uses macro, portal would not | Inconsistent + introduces a new dispatch model |
| Phoenix-idiomatic | YES — matches `live_dashboard/2`, `oban_dashboard/2`, `mailglass_admin_routes/2` | YES but verbose; what `phx.gen.auth` emits in user code | NO — `forward` to a sub-router is rare for LV; LV expects routes in main router |
| LV nested-session bug exposure | LOW — macro emits exactly ONE `live_session :accrue_portal` block; sibling-scope pattern (mailglass lesson) is host's responsibility, NOT inside the macro | LOW — host writes their own `live_session`, full control | HIGH — `forward` + `live_session` is documented as broken (LV expects routes in main router, see Phoenix.LiveView.Router docs) |
| Compile-time error surface | GOOD — `validate_opts!/2` rejects bad `:on_mount`/`:session_keys` at macro expansion (mirror admin's pattern) | NONE — host gets runtime errors at first request | OK — endpoint plug can validate at init |
| `phx.gen.auth` / Pow / Ueberauth fit | NEUTRAL — macro accepts arbitrary `:on_mount` hooks, host wires their own auth hook | BEST — host builds the entire pipeline so any auth shape works | NEUTRAL — endpoint plug delegates to host hooks, but unfamiliar shape |
| Multi-tenant ergonomics (e.g., scoping by org) | GOOD — extra `on_mount` hooks chain naturally; `session_keys` threads org scope | GOOD — full host control | POOR — endpoint plug is a single dispatch surface |
| Release/SemVer commitment | Macro options become public API and v1.x SemVer-locked | Module names of LVs become public (worse — every LV name is a contract) | Plug options are public + module names |
| User mental model match | Highest — "import + one line" is what they already do for admin | Low — "you have to know LiveView router conventions" | Lowest — "what is this `Accrue.Portal.Endpoint` plug?" |
| Dev/test routes (e.g., dev-only checkout previews) | EASY — admin's `wrap_with_mailglass_dev_routes` shows the sibling-scope pattern works | Manual | Awkward — endpoint plug owns its routing surface |

**Recommendation: Macro.** No genuine alternative. Plug+manual is what the macro expands to; offering both creates two ways to do the same thing. Endpoint plug is a non-starter (`live_session` doesn't compose with `forward`).

## D.2 Comparison Table — Auth Contract

| Criterion | New `Accrue.Portal.AuthHook` BEHAVIOUR | Pure `on_mount` convention (host writes hook) | Magic-link URL-token (hybrid) |
|---|---|---|---|
| Compatibility with existing `Accrue.Auth` | DUPLICATIVE — `Accrue.Auth.current_user/1` already exists; adding `current_customer/1` callback splits the contract | REUSES — host hook calls `Accrue.Auth.current_user(session) \|> Billing.customer/1` (3 lines) | ADDITIVE — works ALONGSIDE either, doesn't replace |
| `phx.gen.auth` ergonomics | OK — host implements behaviour, but `phx.gen.auth` already emits `on_mount` hooks (`{MyAppWeb.UserAuth, :require_authenticated}`) — adding ANOTHER behaviour layer is friction | EXCELLENT — host literally adds 3 lines to their existing `UserAuth.on_mount` to also assign `:current_customer` | EXCELLENT — token verification is one `Phoenix.Token.verify/4` call |
| Pow / Ueberauth fit | Hard-couples portal to `Accrue.Auth` adapter resolution | Decoupled — portal reads `socket.assigns.current_customer`, doesn't care how it got there | Decoupled |
| "Wrong tenant" footgun risk | MEDIUM — behaviour callback `c:current_customer/1` is a single trust boundary; if host's adapter is wrong, ALL portal LVs leak | LOW — Portal LVs MUST also re-validate `subscription.customer_id == socket.assigns.current_customer.id` in queries (defense-in-depth, mandatory regardless) | MEDIUM-HIGH — token in URL leaks via referer headers, browser history; needs short max_age + scope binding |
| Compile-time loud errors for "forgot to wire customer" | GOOD — behaviour misses → compile warning; portal LV mount → raises with adapter name | OK — Portal ships a development-mode `assert_assign!/2` helper called from every LV's `on_mount` chain that raises with a clear "wire `:current_customer` in your on_mount" message at first request | OK |
| Footprint of new public API (SemVer cost) | HIGH — new behaviour module + ≥2 callbacks (`current_customer/1`, optionally `authorized_for?/2`) become v1.x-locked | LOW — portal exposes `Accrue.Portal.AuthHook.on_mount/4` as a default hook hosts can use OR replace; convention is `socket.assigns.current_customer` | MEDIUM — new helper `Accrue.Portal.Token.sign/2` and `verify/2` |
| Composability with admin auth | POOR — two parallel behaviours (`Accrue.Auth` for admin, `Accrue.Portal.AuthHook` for customer) for the same "host owns auth" idea | EXCELLENT — single doctrine: "host writes `on_mount` hook, assigns the right thing" | Orthogonal |
| Boilerplate for a host with `phx.gen.auth` | ~15 lines (impl behaviour + register adapter) | ~3 lines (extend existing `UserAuth.on_mount` by one clause) | ~5 lines for a token-emit helper |
| Multi-tenant fork-protection | Behaviour callback can encode it but invites confusion (is `current_customer/1` org-scoped?) | Host's hook handles it naturally — the host already knows their tenant model | N/A |

**Recommendation: Pure `on_mount` convention** with a SHIPPED default hook `Accrue.Portal.AuthHook` (callback module, NOT behaviour) for the common `phx.gen.auth` case. Hosts in the trivial case write nothing — they pass `[{Accrue.Portal.AuthHook, :ensure_customer}]` and it calls `Accrue.Auth.current_user(session) |> Billing.customer/1` for them. Hosts with non-trivial auth (Pow, Ueberauth, custom org scoping) replace it with their own `on_mount` hook that assigns `:current_customer`. **This is the SAME pattern admin already uses** — `AccrueAdmin.AuthHook.on_mount(:ensure_admin, ...)` is a callback module, not a behaviour. Consistency wins.

**Defense-in-depth (NON-NEGOTIABLE regardless of D.2 choice):** Every Portal LV query MUST scope to `socket.assigns.current_customer.id` — never trust the URL `:id` param alone. E.g. `SubscriptionLive.mount/3` does `Billing.get_subscription_for_customer!(id, socket.assigns.current_customer)` not `Billing.get_subscription!(id)`. Add a `Accrue.Portal.Authorize` LV macro/helper that runs in every Portal LV's `mount` to enforce.

## D.3 Customer Resolution Decision

**v1.33 ships SESSION-RESOLVED ONLY.** The Portal expects `socket.assigns.current_customer` to be a `%Accrue.Billing.Customer{}` (or whatever `Accrue.Customer` shape the schema produces) populated by an `on_mount` hook. The default hook (`Accrue.Portal.AuthHook.on_mount(:ensure_customer, ...)`) reaches `Accrue.Auth.current_user(session) |> Accrue.Billing.customer(:lazy_create)` to produce it. If `current_user` is nil, the hook redirects to a configurable `:unauthenticated_path` (default `"/"`).

**URL-token / magic-link checkout flow is DEFERRED to v1.34+.** Three reasons: (1) v1.33 success criterion #2 is a hosted checkout URL, but that URL can be reached by a logged-in user (the common case for "upgrade plan" clicks from an authenticated dashboard) — the magic-link case is a nice-to-have, not on the critical path. (2) Token-in-URL has nontrivial security surface (referer leakage, browser history, replay, scope-binding) that wants careful design — not last-week-of-phase-101 design. (3) Stripe's analogue (Customer Portal) is itself a token URL Stripe issues; we can defer because hosts have a workaround: their own `/checkout/start?token=...` controller in their own router that verifies the token and then `Plug.Conn.put_session(:user_token, ...)` before redirecting into the Portal at `/billing/checkout/:price_id`. Document this in the portal install guide.

**Routes that use session-resolved customer in v1.33:**
- `live "/", Accrue.Portal.Live.HomeLive, :index` — landing page (subs + PMs + recent invoices)
- `live "/subscriptions", Accrue.Portal.Live.SubscriptionsLive, :index`
- `live "/subscriptions/:id", Accrue.Portal.Live.SubscriptionLive, :show` (cancel + swap_plan)
- `live "/payment-methods", Accrue.Portal.Live.PaymentMethodsLive, :index` (add via Drop-in, set default, delete)
- `live "/checkout/:price_id", Accrue.Portal.Live.CheckoutLive, :new` (Drop-in for new sub)
- `live "/invoices", Accrue.Portal.Live.InvoicesLive, :index` (txn history)

All routes require `socket.assigns.current_customer`. None accept a URL-token in v1.33.

## Cross-package analogues

- **`phoenix_live_dashboard.live_dashboard/2`** — macro inside a host-defined `scope`, accepts `:on_mount`, threads custom session via `__session__`. Exact pattern Accrue.Portal should clone. No auth behaviour; access control is a passed callback.
- **`oban_web.oban_dashboard/2`** — same macro shape. Adds `:resolver` option pointing at an `Oban.Web.Resolver` BEHAVIOUR (10 callbacks: `resolve_user/1`, `resolve_access/1`, etc.). Heavy contract. Lesson: behaviours buy you a lot when the dashboard has many resolution surfaces (per-user refresh rates, per-user access levels, per-user instance lists). Accrue.Portal has ONE resolution surface (current customer). Don't pay the behaviour tax.
- **`mailglass_admin.mailglass_admin_routes/2`** — sibling project, same author. Already mounted as a SIBLING scope in `accrue_admin/router.ex` to dodge the nested `live_session` bug. Direct precedent for the macro shape AND the sibling-mount workaround.
- **`accrue_admin.accrue_admin/2`** — the closest precedent. Behaviour: `Accrue.Auth` (existing). Hook: `AccrueAdmin.AuthHook` (callback module, not a behaviour). Defaults: `[{AccrueAdmin.AuthHook, :ensure_admin}]`. Threads session via `__session__/3`. Exactly mirror this; rename `:ensure_admin` → `:ensure_customer`.
- **`phx.gen.auth`** — emits `MyAppWeb.UserAuth.on_mount(:require_authenticated, ...)` etc. Hosts already have an `on_mount` chain for their auth. Portal's "pass `:current_customer` via on_mount" is a one-clause extension — no extra behaviour to learn.
- **Pow** — `Pow.Phoenix.Routes` is overrideable per-host but it's a ROUTES behaviour, not an auth behaviour. Pow's auth is plug-based (`pow_routes()` macro + plugs). Lesson: routes behaviours (overriding Accrue.Portal's URL paths) are NOT v1.33 scope — defer.
- **Pay (Rails)** — `Pay::Engine` mounts in host `routes.rb`, controllers use Devise's `current_user`. Pay's `BillableController` calls `current_user.payment_processor` to get the customer. Host owns auth; Pay reads from it. Same model as Accrue.
- **Laravel Cashier** — Routes are `->middleware(['auth'])` and use `$request->user()`. Cashier doesn't ship a portal UI — it redirects to Stripe Customer Portal via `redirectToBillingPortal()`. Different model: Cashier hands off to a Stripe-hosted page; Accrue.Portal is the local equivalent of THAT hosted page. Not a useful precedent for THIS decision (D.2) — useful precedent for "hosts own auth," yes.
- **Stripe Customer Portal** — Stripe issues a short-lived URL after the host calls `BillingPortal.Session.create` with the host-authenticated `customer_id`. Stripe trusts the host's session creation, not the URL holder long-term. Different threat model: Stripe issues the URL, Accrue.Portal IS the URL — we don't need URL tokens to delegate trust because we're inside the host's session.

## Concrete artifact lock-ins

- **Macro name:** `Accrue.Portal.Router.accrue_portal/2` (ALT: `AccrueAdmin.Router.accrue_portal/2` if Area A is reversed and portal lives in admin package)
- **Default `on_mount`:** `[{Accrue.Portal.AuthHook, :ensure_customer}]`
- **New behaviour module:** NONE. Do not create `Accrue.Portal.Auth`. Reuse `Accrue.Auth` for `current_user/1`; reuse `Accrue.Billing.customer/1` for the customer lookup.
- **New callback module (NOT behaviour):** `Accrue.Portal.AuthHook` with:
  - `on_mount(:ensure_customer, params, session, socket) :: {:cont, socket} | {:halt, socket}` — calls `Accrue.Auth.current_user(session)`, then `Accrue.Billing.customer(user, :lazy_create_if_missing)`, assigns `:current_user` and `:current_customer`. On `nil` user, halts and redirects to configured `:unauthenticated_path`.
  - `on_mount(:ensure_customer_no_create, params, session, socket)` — same but does NOT lazy-create; halts with `:not_found` if the user has no Customer record. Used by routes that should never create a stub Customer (e.g., invoice list).
- **Required `socket.assigns` keys after on_mount:** 
  - `:current_user` — host's user struct/map (whatever `Accrue.Auth.current_user/1` returns)
  - `:current_customer` — `%Accrue.Customer{}` (or whatever Customer schema is — confirm against `accrue/lib/accrue/billing.ex`)
  - `:accrue_portal_session` — the threaded host session map (mirror of admin's `:accrue_admin_session`)
- **Pipeline plugs (`pipeline :accrue_portal_browser`):**
  - `:fetch_session`
  - `:protect_from_forgery`
  - `Accrue.Portal.CSPPlug` (mirror admin's CSP plug; needed because Drop-in injects iframes — CSP must allow Braintree's CDN)
  - `Accrue.Portal.BrandPlug` (mirror admin's brand plug for theming)
- **Live session id:** `:accrue_portal` (distinct from `:accrue_admin` so the two CAN co-exist in the same router without nesting — mirror Phase 88 mailglass lesson)
- **Threaded session keys:** `[:user_token]` by default (matches `phx.gen.auth` and `examples/accrue_host`); host can override via `:session_keys` macro option, identical to admin
- **URL-token verification helper (DEFERRED to v1.34+):** `Accrue.Portal.Token.sign(customer_id, purpose, opts)` and `verify(token, purpose, opts)` — designed but NOT shipped in v1.33. Document the placeholder shape in the portal guide so hosts know it's coming.
- **Sibling-scope pattern to avoid nested live_session:** YES — Portal's `accrue_portal/2` macro emits ONE `live_session :accrue_portal` block. If a host also mounts `accrue_admin/2` in the same router, the two live in SIBLING scopes (not nested) by virtue of being separate macro invocations at the top level. Document explicitly: "Mount `accrue_admin "/admin"` and `accrue_portal "/billing"` as sibling top-level scopes — never nest one inside the other."
- **Route prefix collision avoidance:** Portal's default mount path `/billing` MUST be documented as conflict-prone with `accrue_admin "/billing"` in `examples/accrue_host`. Recommend `accrue_admin "/admin/billing"` going forward and update the example. (NOTE: existing host example uses `accrue_admin "/billing"` — that's a real path collision the user will hit.)
- **CSRF for Drop-in checkout:** Phoenix `protect_from_forgery` + Braintree Drop-in's iframe model needs documented CSP `frame-src` + `script-src` allowlists. Out of scope for THIS area but flagged for area B/C.

## High-impact fork flag

**HIGH_IMPACT: true — but for D.3 only, not D.1/D.2.**

D.1 (macro) and D.2 (no new behaviour, reuse `Accrue.Auth` + `on_mount` convention) are uncontroversial — they mirror existing Accrue patterns and any other choice would be inconsistent with `accrue_admin`. No need to surface.

**D.3 IS a fork worth surfacing:** the recommendation to DEFER URL-token / magic-link checkout to v1.34+ trades v1.33 phase-completion confidence (smaller surface) against v1.33 marketing story ("subscribe via emailed link" is a real common SaaS flow that competitors offer). If the user wants the magic-link flow IN v1.33:

- Add `Accrue.Portal.Token` module (`sign/3`, `verify/3` wrapping `Phoenix.Token` with mandatory short max_age + purpose-binding)
- Add `Accrue.Portal.AuthHook.on_mount(:ensure_customer_via_token, ...)` variant
- Add `live "/checkout/:token/:price_id", Accrue.Portal.Live.TokenCheckoutLive, :new`
- Document the security model (max_age <= 30min, single-purpose tokens, post-redemption invalidation, no PII in token payload)
- Add property tests for token expiry and scope binding
- Adds 1-2 plans of work to Phase 101

**The user should personally confirm:** "v1.33 ships session-resolved only; magic-link checkout deferred to v1.34+ with documented host-side workaround" — yes/no? If no, expand Phase 101 scope. The rest of D is low-risk to commit without confirmation.

# Accrue v1.35 Decision Memo: Braintree webhook and operator maturity

## 1. Short thesis

This is a **good v1.35 candidate if the milestone is framed narrowly as supportability closure for the shipped Braintree slice**, not as another abstract "maturity" sweep.

Accrue already shipped the hard capability work in **v1.31-v1.33**: Braintree subscription creation and mutation, webhook normalization, payment-method CRUD, local checkout and portal, local promotion mapping, and local metered renewal settlement. The next likely source of maintainer pain is no longer missing core API surface. It is **operator confidence when Braintree goes wrong**: understanding webhook truth, replaying safely, explaining gateway-specific behavior, and keeping docs/telemetry/admin UX aligned with the actual dual-provider contract.

For an **Elixir/Phoenix/Plug/Ecto billing library plus companion admin**, that direction is idiomatic. The natural shape is: webhook-first state convergence, durable local rows, Oban-backed replay/recovery, telemetry for low-cardinality ops signals, and a LiveView admin for forensic inspection. Accrue is already built that way. The opportunity is to make the Braintree half of that story as legible and low-surprise as the Stripe-first half.

Recommendation: **do it if scope is constrained to webhook truth, operator ergonomics, and proof-lane/documentation parity for the existing Braintree slice.**

## 2. Pros

- **High leverage on real production risk.** After v1.33, the most dangerous failures are replay, drift, stale local state, and ambiguous operator recovery, not missing "happy path" billing verbs.
- **Strong fit with PROC-08's north star.** A dual-provider core is not credible if only the Stripe path feels operable under incident pressure.
- **Idiomatic Elixir architecture.** Oban-backed async dispatch, Ecto durability, Plug verification, and LiveView inspection/replay surfaces are the right tools for this problem.
- **Improves principle of least surprise.** Braintree is already provider-honest in checkout, portal, and metering. A maturity milestone can make those differences easier to explain and support rather than hiding them.
- **Supportability beats breadth.** This avoids the ActiveMerchant trap of chasing ever more gateway breadth while operator burden quietly rises.
- **Good timing after v1.31-v1.33.** The processor surface is now broad enough that the next defects are likely to be integration and recovery defects, which are cheaper to address before more scope lands.
- **Concrete repo gaps exist.** `accrue/guides/webhooks.md` is still Stripe-only in setup examples, `accrue/guides/operator-runbooks.md` is mostly Stripe-centric with only limited Braintree depth, and `accrue/guides/telemetry.md` still reflects Stripe-shaped examples and attributes in places even though Braintree is now first-party.

## 3. Cons / risks

- **"Maturity" is scope-creep bait.** Without a hard boundary, this can turn into endless polish, generic admin embellishment, or abstraction churn.
- **Lower visible feature excitement.** This is a supportability milestone, not a splashy capability milestone. It is valuable, but less legible to casual adopters.
- **Much of the substrate already exists.** Accrue already has DLQ replay, admin inspection, ops telemetry, and Braintree webhook normalization. If the milestone does not target the remaining sharp edges precisely, it risks feeling incremental.
- **Risk of over-generalizing webhook semantics.** Stripe and Braintree event models differ. Forcing a too-generic event abstraction would create surprise and weaken diagnostics.
- **Potential diversion from fresh adoption work.** If the main bottleneck after v1.34 is actually adoption DX or first-user proof rather than Braintree incident handling, this could be the wrong next bet.
- **Testing cost can be deceptively high.** Operator maturity work often requires proof across docs, admin UI, replay paths, and failure simulations, which can sprawl unless explicitly capped.

## 4. Ecosystem / precedent lessons

### Pay (Rails)

What it got right:

- Supports multiple processors, but **says plainly that providers differ** and warns complex users not to expect deep cross-provider sameness.
- Ships **provider-specific webhook endpoints and event names** instead of pretending every webhook lifecycle is identical.
- Keeps the shared surface useful, but not magical.

What Accrue should learn:

- Keep the facade **capability-explicit and provider-honest**.
- Preserve **gateway-specific truth at the boundary**, then normalize only where local domain semantics are truly shared.
- Do not hide Braintree differences behind Stripe-shaped copy or docs.

Footgun to avoid:

- Pay's openness to multiple processors works because expectations are modest. Accrue should not imply stronger parity than it can operate safely.

Sources:
- https://github.com/pay-rails/pay
- https://raw.githubusercontent.com/pay-rails/pay/main/docs/7_webhooks.md

### Laravel Cashier

What it got right:

- Treats **webhooks as authoritative subscription truth**.
- Admits the redirect after checkout is not the source of truth; the webhook path is.
- Offers an opinionated billing UX by narrowing itself to Stripe rather than flattening semantics across many gateways.

What Accrue should learn:

- Lean harder into **webhook-centric state machines** and communicate that clearly in Braintree docs and operator tooling.
- Optimize for "what is the subscription truth right now?" instead of "what did the client think happened?"

Footgun to avoid:

- Cashier can rely on Stripe-specific assumptions because it is Stripe-only. Accrue cannot carry those assumptions forward into dual-provider docs, telemetry examples, or admin copy.

Sources:
- https://laravel.com/docs/cashier
- https://github.com/laravel/cashier-stripe

### ActiveMerchant

What it got right:

- Proved the value of a unified payment facade for basic operations.

What Accrue should learn:

- Broad gateway abstraction quickly becomes **lowest-common-denominator API design**.
- Support burden grows faster than surface area because every gateway edge case leaks into operations.

Footgun to avoid:

- Do not spend v1.35 inventing a more abstract webhook/operator layer just because multiple processors now exist.
- Prefer **explicit processor-aware operator UX** over false uniformity.

Source:
- https://github.com/activemerchant/active_merchant

### Webhook-ops products like Hookdeck

What they get right:

- Treat webhook systems as **operational infrastructure**, not a controller callback.
- Prioritize **queueing, issue surfacing, replay, filtering, and observability**.
- Recognize that operator trust comes from being able to inspect, recover, and explain.

What Accrue should learn:

- The admin should help an operator answer three questions fast:
  1. What failed?
  2. Is local state safe?
  3. What is the safe next recovery action?

Footgun to avoid:

- Fancy forensic UI without crisp recovery guidance. Raw payload visibility is useful, but actionability matters more.

Source:
- https://hookdeck.com/

## 5. Fit with Accrue strategy and current repo state

This direction fits the active strategy **well**, but only in its narrow form.

Why it fits:

- `.planning/STRATEGY.md` defines success as a **credible production billing platform** across `Fake`, `Stripe`, and `Braintree` for the named slice.
- v1.32 and v1.33 already moved Braintree from thin slice to real first-party support.
- `accrue/lib/accrue/webhook/default_handler.ex` already does the right thing architecturally: normalized Braintree event handling, canonical refetch, shared projection, and metered renewal hooks.
- `accrue/lib/accrue/webhooks/dlq.ex`, `accrue/lib/mix/tasks/accrue.webhooks.replay.ex`, and `accrue_admin` webhook LiveViews already provide the operator substrate.
- `accrue/guides/operator-runbooks.md` and `accrue/guides/telemetry.md` already establish an ops philosophy centered on low-cardinality signals and ordered triage.

Why it is not automatically the right next milestone:

- The repo already has a lot of the machinery. So the milestone only makes sense if it closes the remaining **truth-alignment gaps**:
  - Braintree webhook setup and verification still are not as first-class in docs as Stripe.
  - Operator docs remain heavily Stripe-shaped.
  - Telemetry examples and attribute language still show Stripe-first drift in places.
  - Admin replay/inspection may be generic enough for correctness, but not yet optimized for **Braintree-specific diagnosis**.

My judgment:

- This is **more of a consolidation milestone than a capability milestone**.
- That is strategically sound right after v1.33, because PROC-08 now risks death by support burden more than by missing happy-path verbs.
- It should not reopen processor breadth or new business-domain scope.

## 6. Recommended scope if chosen

Keep scope to **existing Braintree slice operability**:

1. **Braintree webhook contract parity**
   - Publish the supported Braintree webhook kinds, the normalized local event mapping, and the intentionally ignored kinds.
   - Make webhook setup docs first-party for both Stripe and Braintree, not Stripe with implicit extension.

2. **Operator runbook parity**
   - Add Braintree-specific incident playbooks for subscription drift, dead-lettered webhook recovery, checkout completion ambiguity, and metered renewal settlement recovery.
   - Distinguish "safe replay" from "needs manual inspection first."

3. **Telemetry and observability truth pass**
   - Remove Stripe-only assumptions from public telemetry docs where Braintree is now supported.
   - Add clear processor-aware dashboard/alert recommendations for webhook DLQ, replay, missing object IDs, metered renewal repair, and payment-method-blocked settlement.

4. **Admin UX for recovery**
   - Make webhook list/detail views explicitly processor-aware.
   - Surface failure classification and the recommended next action, not just payloads and statuses.
   - Link webhook rows to affected subscription/customer/renewal records where possible.

5. **Proof lane hardening**
   - Add deterministic Braintree webhook/replay proof for the supported slice.
   - Verify docs, telemetry catalog, admin replay flow, and runbook language in the same milestone.

Explicitly out of scope:

- New billing primitives
- New processor support
- Hyperwallet / Connect reopening
- FIN-03 finance exports
- Broad webhook platform ambitions unrelated to the shipped Braintree slice

## 7. Recommendation score

**8/10**

Rationale:

- **+3** because it directly strengthens the weakest part of a newly expanded dual-provider system: incident handling and operator trust.
- **+2** because it is highly idiomatic for Accrue's Elixir/Phoenix/Plug/Ecto architecture and uses substrate the repo already has.
- **+2** because there are visible repo-state gaps between the claimed Braintree support level and the docs/runbook/telemetry/operator ergonomics.
- **+1** because it reduces future support drag before more scope lands.
- **-2** because "maturity" can sprawl and because much of the core machinery is already shipped, so the milestone must stay narrow to be worth it.

If you want a one-line call: **yes, this is a strong v1.35 direction, but only as "Braintree operability closure" rather than "more parity."**

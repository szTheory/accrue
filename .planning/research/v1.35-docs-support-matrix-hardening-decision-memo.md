# Accrue v1.35 Candidate Direction Memo: docs/support-matrix hardening

Researched: 2026-05-06
Confidence: HIGH for local-state assessment, MEDIUM-HIGH for ecosystem precedent

1. Short thesis

`docs/support-matrix hardening` is a credible and strategically idiomatic next milestone for Accrue after v1.31-v1.33, but only if it is treated as product-contract hardening rather than a generic docs sweep. The current repo already has a support-contract mismatch: `.planning/processor-support-matrix.md` and strategy docs say Braintree checkout and billing portal are first-party with provider-honest local UI, while `accrue/README.md` still says `Accrue.Billing.create_checkout_session/2` and `Accrue.Billing.create_billing_portal_session/2` remain Stripe-only.

That kind of mismatch is not cosmetic in a billing library. It changes what adopters think is safe to build against, increases maintainer support load, and undercuts the whole "capability-explicit" posture PROC-08 was opened to establish. As a next milestone, this is stronger than another small runtime feature if the goal is to make the dual-provider story legible, supportable, and unsurprising before broadening scope again.

2. Pros

- It directly hardens the public contract at the moment Accrue has the most risk of accidental false parity. v1.31-v1.33 expanded Braintree from a thin slice to a meaningful first-party surface; docs now need to tell the same truth everywhere.
- It is highly idiomatic for an Elixir/Phoenix/Ecto library with adapters. Ecto, Plug, and Rails adapter-style systems succeed by making the supported surface explicit and documenting where behavior is adapter-specific instead of pretending sameness.
- It improves developer ergonomics more than it sounds. In payments, the "what exactly works on this provider?" question is often more important than one extra helper API.
- It supports principle of least surprise. If `create_checkout_session/2` exists, the docs must plainly say whether Braintree returns a local URL, a hosted provider URL, or a typed unsupported error.
- It reduces support cost. Good support matrices turn future GitHub issues into doc references instead of architecture debates.
- It preserves the Stripe-first adoption path while making the Braintree path honest. That aligns with the current strategy instead of fighting it.
- It creates a stable base for any future PROC-08 expansion. Without this, every next provider-touching milestone risks re-litigating semantics.

3. Cons / risks

- It can become a low-signal paperwork milestone if it does not include executable enforcement. A support matrix that is not checked by scripts, docs needles, examples, and package docs will drift again.
- It may feel anticlimactic right after feature-heavy v1.33 and v1.34. If the milestone ships only wording changes, it risks looking like maintainers are avoiding harder product questions.
- It may freeze bad semantics if the team documents unresolved rough edges too early. Hardening should follow real behavior, not invent a neater story than the code supports.
- It can sprawl. "Docs hardening" easily expands into all guides, all READMEs, package docs, example host UX, telemetry docs, verifier scripts, changelog, and support tables.
- It competes with deeper runtime follow-through if there are still material edge cases in the shipped Braintree portal, checkout, or local metering story.

4. Ecosystem / precedent lessons

Pay (Rails) is the closest positive precedent for Accrue's direction. Its README names supported processors, separates processor-specific docs, and explicitly warns that providers differ and complex payments are best kept on one provider. That is the right lesson for Accrue: keep the shared facade, but say where semantics diverge and do not oversell interchangeability. What Pay did right was honest breadth labeling. The footgun it created is the same one it warns about: once many processors are listed under one umbrella, users assume a deeper common contract than really exists.

Laravel Cashier is the clearest lesson in boundary discipline. Modern Cashier is split into separate packages and docs tracks for Stripe and Paddle rather than forcing one fake-neutral billing abstraction across incompatible provider classes. That is exactly the move Accrue has already made in strategy terms by locking Braintree as a Stripe-like direct-gateway target and excluding merchant-of-record pivots. The lesson to copy is provider-track honesty. The footgun to avoid is over-inheriting Stripe vocabulary and letting users believe non-Stripe providers share the same operational path.

Laravel Spark is useful for one specific lesson: when the provider lacks a suitable hosted surface, shipping an isolated first-party billing portal can be the right move because it keeps upgrades and UX supportable. That supports Accrue's Braintree local portal direction. The footgun is that once you own the portal, you also own support for its semantics, auth boundary, route contract, and upgrade story. Docs become part of the runtime contract.

ActiveMerchant is the negative precedent. Its historical value came from broad gateway reach, but the tradeoff was lowest-common-denominator pressure and leaky abstractions across many gateways. Accrue explicitly calls this trap out in strategy, and that is correct. The lesson is not "avoid multi-provider"; it is "avoid vague multi-provider." A support matrix is the antidote only if it is narrow, capability-based, and enforced.

Framework precedent also supports this direction. Ecto documents adapters via explicit behaviours and leaves adapter-specific configuration/capabilities to the adapter layer. Plug exposes generic interfaces but tells users to consult the underlying adapter for exact semantics. Rails' Active Storage succeeds because it documents supported services, service-specific setup, and behavior differences instead of pretending every backend behaves identically. Accrue should copy that posture: common facade, explicit provider truth.

5. Fit with Accrue strategy and current repo state

Fit with strategy is strong. PROC-08's written north star is not "add Braintree features forever"; it is "become a credible production billing platform with Stripe plus one first-party Stripe-like processor on a documented facade." The word documented matters. The strategy also explicitly says unsupported capabilities must fail clearly and early, and that public APIs should carry capability labeling.

Fit with current repo state is also strong because the repo is already showing contract drift:

- `.planning/STRATEGY.md` says checkout and billing portal are first-party with provider-honest implementations.
- `.planning/processor-support-matrix.md` labels both `create_checkout_session/2` and `create_billing_portal_session/2` as `all first-party`, with Braintree returning mounted local URLs.
- `.planning/PROJECT.md` mirrors that shipped story.
- `accrue/README.md` still says both APIs remain Stripe-only.

That mismatch means the next maintainer or adopter cannot reliably answer a basic API support question from the package landing page alone. For a billing library, that is too much ambiguity. It also means v1.31-v1.33 delivered real processor work without fully cashing out the supportability gain in the public contract.

The only caveat is sequencing relative to v1.34. If there is still unresolved churn from the Rendro-default invoice docs transition, a broad docs milestone could overload maintainers. But the processor-support mismatch is sharp enough that it justifies a bounded hardening milestone anyway.

6. Recommended scope if chosen

Choose this milestone only if the scope is tight and enforcement-oriented:

- One support SSOT for processor capability labels, with package docs and planning docs forced to agree.
- Package-facing README correction first, especially the current Stripe-only claim in `accrue/README.md`.
- Public API matrix for every processor-touched billing facade entry, with one label vocabulary only: for example `all first-party`, `staged first-party target`, `out of slice`, `unsupported`.
- Provider-honest semantics docs for checkout and billing portal:
  Stripe = upstream hosted URL
  Braintree = mounted local `Accrue.Portal` URL
  Fake = deterministic proof helper
- First Hour, host README, and any portal guide updated so the first-user path explains the provider difference without making Braintree feel second-class or mysterious.
- Verifier/script coverage that fails if support-matrix needles drift across README, guides, and planning mirrors.
- A short "capability rules" guide for contributors so future phases do not reintroduce false parity language.

Do not make v1.35 a general prose cleanup. Do not reopen refunds, advanced subscription mutation, Connect, or new provider classes. Do not rewrite the whole docs site. The milestone should be about making the shipped dual-provider contract obvious, consistent, and enforceable.

7. Recommendation score

8/10

This should be v1.35 if the decision is between "broaden the dual-provider surface again" and "make the shipped dual-provider core genuinely supportable." The repo has enough shipped processor surface now that contract drift is a real product risk, not a polish issue. I would not score it higher than 8 because docs-only milestones are easy to bloat and can feel thin unless they ship hard enforcement plus a visibly clearer public story. If scoped as support-contract hardening with executable drift checks, it is the right next move.

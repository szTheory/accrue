# Accrue v1.35 Decision Memo: Portal and Checkout Refinement

Researched: 2026-05-06
Confidence: MEDIUM-HIGH

## 1. Short thesis

`Portal and checkout refinement` is a credible and fairly idiomatic next milestone for Accrue, but only if "refinement" means **contract hardening, docs/support truth, host integration ergonomics, and user-facing failure clarity** rather than mostly visual polish.

Accrue already spent v1.31-v1.33 earning the right to have a provider-honest portal/checkout story. The immediate opportunity is to turn that shipped surface into a lower-surprise, lower-support-cost, more obviously adoptable product lane. That is strategically stronger than expanding breadth again right away. The risk is that a vague refinement milestone devolves into cosmetic portal work while leaving the real maintainer pain untouched.

## 2. Pros

- **Best leverage on recent investment.** v1.31-v1.33 built the dual-provider processor core, Braintree checkout, local portal, local promotions, and local metering. Refinement compounds that investment instead of opening a new abstraction front before the current one fully settles.
- **Improves least surprise at the exact seam where adopters feel the product.** Checkout and self-serve billing are where library promises become user-visible behavior. Small ambiguities here create outsized support cost.
- **Matches Accrue’s stated strategy.** `STRATEGY.md` explicitly says checkout and billing portal are part of the first-party surface and should be provider-honest. A refinement milestone is the natural follow-through on that choice.
- **High support ROI.** Current repo state already shows contract drift between code, tests, README, host docs, and guides. Fixing that drift is maintainership work, not vanity work.
- **Good fit for a Phoenix companion app model.** Mounted LiveView surfaces, router macros, host-owned auth, and Ecto-backed read models are idiomatic ways to ship a companion UI in Elixir without hiding where host ownership begins.
- **Lets Accrue differentiate from “thin wrapper” libraries.** Pay and Cashier are strong on developer convenience, but they benefit from upstream hosted surfaces on Stripe/Paddle. Accrue can win by making the local-first Braintree path unusually clear and low-friction for Phoenix teams.

## 3. Cons / risks

- **Refinement is easy to scope poorly.** If the milestone becomes "make the portal nicer," it burns a milestone on polish while leaving the public contract, setup friction, and failure semantics under-specified.
- **Can distract from the library core if UI scope expands.** The Elixir value is not building a mini-SaaS frontend framework. The risk is growing `accrue_portal` into an opinionated product surface that increases CSS, auth, accessibility, and browser-maintenance burden.
- **Two truths are inherently harder to explain.** Stripe uses hosted upstream checkout/portal. Braintree uses mounted local UI. That is the right honest design, but it creates documentation and support complexity that needs careful wording.
- **Portal work can create hidden support obligations.** Every mounted UI feature adds expectations around theming, branding, auth hooks, CSP, accessibility, browser behavior, and upgrade stability.
- **There is already evidence of drift.** Today the shipped implementation appears ahead of several docs:
  - `accrue/README.md` still says checkout and billing portal remain Stripe-only.
  - `examples/accrue_host/README.md` and `examples/accrue_host/docs/adoption-proof-matrix.md` repeat the same outdated claim.
  - `accrue/guides/braintree-local-portal.md` now mixes the packaged `accrue_portal` story with older “Accrue remains headless” language.
- **UI/UX refinement without stronger proof can backfire.** If copy, recovery flows, and operator guidance improve visually but test coverage does not cover the new states, supportability gets worse, not better.

## 4. Ecosystem / precedent lessons

### Stripe hosted checkout + hosted portal

What Stripe gets right:

- Stripe’s own docs keep pushing teams toward hosted surfaces for low-complexity, low-maintenance paths: Checkout is the recommended low-code path and the customer portal is a hosted self-serve surface.
- Stripe makes cancellation, invoice access, payment method updates, and promotion codes feel like configuration decisions rather than app-building work.

What Accrue should learn:

- Hosted surfaces are attractive because they reduce maintenance burden, not because “hosted” is inherently better.
- When a processor already owns a good UX surface, the library should not fight it. Accrue is right to keep Stripe on upstream hosted pages.
- The footgun is configuration drift: your own `portal_configuration_checklist.md` is correct that default portal settings can undermine dunning and retention if left loose. Refinement should continue treating operational defaults and cancellation semantics as first-class product concerns, not doc afterthoughts.

What to avoid:

- Do not promise identical behavior across Stripe and Braintree checkout/portal flows.
- Do not bury critical behavior behind dashboard toggles, optional guide footnotes, or processor-specific tribal knowledge.

Sources:
- https://docs.stripe.com/payments/checkout
- https://docs.stripe.com/customer-management
- https://docs.stripe.com/no-code/customer-portal

### Laravel Cashier

What Cashier gets right:

- Very strong developer ergonomics on the happy path. The API shape is compact and memorable.
- Cashier leans into hosted/provider-native surfaces rather than pretending every flow belongs in the app.
- Stripe checkout and promotion-code enablement are straightforward, which reduces accidental complexity.

What Accrue should learn:

- The best abstraction is often a narrow facade plus explicit provider docs.
- Checkout helpers should feel obvious from the host app’s point of view: one or two verbs, clear return/cancel semantics, clear webhook expectations.

Footgun to avoid:

- Cashier’s multi-provider story historically teaches the same lesson Accrue already wrote down in strategy: if the abstraction implies sameness where processors differ, adopters eventually hit surprising edge cases. Accrue should keep the current capability-explicit posture and refuse false parity.

Sources:
- https://laravel.com/docs/12.x/billing
- https://laravel.com/docs/9.x/cashier-paddle

### Pay (Rails)

What Pay gets right:

- Pay openly supports multiple processors but explicitly warns that providers function differently and that complex users are often better off sticking to one provider.
- That candor is a strength. It protects trust.

What Accrue should learn:

- Keep telling the truth in one sentence, everywhere: “same facade, provider-honest behavior, bounded parity.”
- Support breadth only works when docs constantly restate where semantics diverge.

Footgun to avoid:

- Do not let the public surface outrun the support matrix. If README and guides imply one thing while the code does another, you lose the main advantage of the explicit-support strategy.

Source:
- https://github.com/pay-rails/pay

### ActiveMerchant and broad gateway abstraction

What ActiveMerchant did right:

- It proved that a unified API over many gateways is possible and useful.

What it teaches Accrue to avoid:

- Breadth creates lowest-common-denominator pressure.
- The more gateways you normalize, the more you either flatten important differences or leak provider-specific exceptions through the abstraction.
- That is exactly the trap Accrue has been trying to avoid with the bounded dual-provider strategy.

Implication for v1.35:

- Refining the already-shipped portal/checkout surface is strategically healthier than adding another major capability slice right now.

Source:
- https://github.com/activemerchant/active_merchant

### Phoenix / LiveView precedent

What Phoenix gets right:

- Mountable router scopes are idiomatic in Phoenix and libraries do not need to know their final mount prefix.
- LiveView’s security model is explicit that authn/authz must be enforced both in Plug pipelines and LiveView mount hooks.

What Accrue should learn:

- `accrue_portal` is an idiomatic Phoenix shape when it behaves like a mounted subsystem, not a magical black box.
- Refinement should prioritize auth hook clarity, session contract clarity, wrong-tenant proof, CSP, and host-owned theming/auth boundaries.

Sources:
- https://hexdocs.pm/phoenix/Phoenix.Router.html
- https://hexdocs.pm/phoenix_live_view/security-model.html

## 5. Fit with Accrue strategy and current repo state

This direction fits Accrue well if it is framed as **“make the first-party portal/checkout story production-clear and support-cheap”**.

Why it fits:

- `STRATEGY.md` already locks checkout and billing portal into the first-party surface for PROC-08.
- v1.32 and v1.33 moved these flows from “unsupported” to “provider-honest supported,” especially for Braintree.
- The public billing facade already documents Braintree routing through the mounted local portal in `accrue/lib/accrue/billing.ex`.
- The Braintree adapter and tests already prove the local URL/session behavior.

Why this is probably the right time:

- v1.34 was PDF-focused and did not materially reduce portal/checkout support debt.
- The repo now shows a classic post-expansion pattern: the implementation has advanced faster than the docs and host-facing story.
- That is the right moment for a consolidation milestone before taking on new processor or finance scope.

Current state signals that argue for refinement:

- **Contract drift:** code and tests say Braintree portal/checkout are real first-party local flows; several docs still say Stripe-only.
- **Narrative drift:** the Braintree local portal guide still contains pre-v1.33 “headless only” reasoning.
- **Surface complexity:** local portal setup depends on `portal_base_url`, `portal_mount_path`, auth plugs/hooks, CSP, and mounted routes. That is acceptable, but only if setup and failure modes are exceptionally clear.
- **Supportability opportunity:** the current product already has the right typed-failure posture (`:unsupported_by_gateway`, config errors, discount drift handling). Refinement can make those paths more discoverable and better documented rather than inventing new billing semantics.

Net judgment:

This is more idiomatic for Accrue than another round of processor capability expansion right now. For an Elixir/Phoenix billing library with a companion app, a mounted LiveView-first self-serve surface is a sensible differentiator. But it only remains idiomatic if Accrue keeps the portal small, explicit, well-tested, and host-owned at the boundaries.

## 6. Recommended scope if chosen

If v1.35 is this milestone, scope it as **portal/checkout contract refinement**, not generic polish.

Recommended in-scope work:

1. **Public contract truth pass**
   - Fix all stale README, host README, proof-matrix, and guide language that still says Stripe-only.
   - Rewrite `braintree-local-portal.md` to choose one truth: packaged mounted portal first, hand-rolled escape hatch second.
   - Add one canonical “provider behavior table” for checkout and portal.

2. **First-hour / host integration ergonomics**
   - Make `portal_base_url`, `portal_mount_path`, and mount/auth requirements impossible to miss.
   - Add a single install-to-working-flow path for Braintree local checkout and portal.
   - Ensure example-host proof includes the mounted portal story clearly, even if still Fake/hermetic.

3. **Failure-state UX and operator guidance**
   - Audit customer-visible copy for expired sessions, missing mount/config, discount drift, payment-method failures, and subscription completion failures.
   - Tighten operator docs around remediation, telemetry event names, and expected recovery steps.

4. **Proof and supportability**
   - Add or tighten regression coverage around doc-backed setup paths, wrong-tenant denial, expired checkout sessions, redirect paths, and portal mount/config failures.
   - Add verifier needles for the new provider-honest wording so this drift does not recur.

5. **Minimal UI cleanup only where it serves clarity**
   - Improve copy, affordances, and state transitions where current UX is ambiguous.
   - Keep theme/styling ambitions narrow. No large visual redesign.

Recommended out of scope:

- New processor capability slices
- Large new `accrue_portal` product surfaces
- Heavy theming system work
- Marketplace / Connect reopening
- Finance/export work
- Broad mobile/responsive redesign unless specific correctness issues are found

## 7. Recommendation score

**8/10**

Rationale:

- **Why not lower:** This is strategically coherent, fits the active PROC-08 track, and addresses the exact layer where recent Braintree work can either become trustworthy or become a long-tail support burden.
- **Why not higher:** The milestone is only strong if tightly scoped around contract truth, ergonomics, and supportability. If defined vaguely, it could collapse into UI polish and feel small relative to a full milestone.

My recommendation is to choose this as **v1.35** only if the milestone brief explicitly says:

> Refine the first-party checkout and portal surface for provider-honest clarity, host integration ergonomics, and supportability after the v1.31-v1.33 Braintree expansion.

If the team actually wants new billing capability rather than consolidation, this should not be the next milestone. But if the goal is to make PROC-08 feel durable and adopter-ready, this is the right next move.

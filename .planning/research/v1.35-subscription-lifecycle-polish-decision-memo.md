# Accrue v1.35 Candidate Memo: Subscription Lifecycle Polish

## 1. Short thesis

`subscription lifecycle polish` is a credible next milestone for Accrue v1.35, but only if "polish" means narrowing semantic drift, tightening cancellation and change-management behavior, and making provider differences unsurprising. It should not mean reopening broad new lifecycle primitives. Accrue already ships substantial lifecycle capability. The next win is making Stripe and Braintree lifecycle behavior easier to understand, safer to operate, and more coherent across facade, portal, docs, and companion app surfaces.

This is idiomatic for an Elixir/Phoenix/Plug/Ecto billing library plus companion app. Phoenix contexts reward explicit verbs, typed failures, and local state that answers product questions cheaply. Accrue already follows that shape with `cancel/2`, `cancel_at_period_end/2`, `resume/2`, `pause/2`, `unpause/2`, local projection, and webhook-backed convergence. A polish milestone fits that architecture better than another abstraction pass.

The main caution is prioritization. If v1.35 becomes "let's smooth every provider difference until it feels identical", it will recreate the exact lowest-common-denominator trap the project has already warned against. The milestone only makes sense if it sharpens honesty and predictability rather than hiding divergence.

## 2. Pros

- Reinforces Accrue's strongest product promise: "billing state, modeled clearly." Lifecycle edges are where clarity is won or lost.
- Improves first-user confidence more than another backend-only slice. Cancellation, resumption, downgrade timing, grace periods, and portal behavior are the questions SaaS teams hit immediately.
- Fits the current repo better than large new capability work. v1.31-v1.33 already built the hard processor foundation; polish now harvests that investment.
- Reduces support load. Clear lifecycle semantics and provider-honest copy prevent "why did cancel behave differently on Braintree?" tickets.
- Strengthens the companion app story. A billing library plus admin/portal package should feel safe around churn, plan changes, and payment recovery, not just technically complete.
- Creates room for better docs-driven adoption. Hosted portal and local portal flows are easier to trust when cancellation timing, retention posture, and post-webhook state are explicit.
- Aligns with successful precedent: Rails Cashier/Pay-style libraries feel productive when the common path is simple and lifecycle edge cases are documented, named, and testable.

## 3. Cons / risks

- "Polish" can become a vague sinkhole. Without hard boundaries it turns into endless copy, UX, and semantics cleanup with weak release impact.
- There is real risk of re-abstraction pressure. Trying to make Stripe and Braintree lifecycle feel identical will push Accrue toward misleading sameness.
- Some provider differences are irreducible. Stripe supports reversible `cancel_at_period_end`, portal-native cancellation reasons, retention coupons, and hosted plan switching. Braintree does not match that model one-for-one.
- User-facing polish is harder to verify than processor plumbing. The milestone needs explicit acceptance criteria, not "docs and UX feel better".
- It may undershoot momentum if the release is mostly documentation or admin cleanup without at least one visible behavior improvement.
- The repo already carries multiple lifecycle surfaces: billing facade, admin, portal, guides, support matrix, testing guide, host example. A shallow pass that updates only one or two will worsen drift.

## 4. Ecosystem / precedent lessons

### Pay (Rails)

What Pay gets right:

- It supports multiple processors, but says plainly that processors differ and that complex flows are best kept on one provider.
- Its subscription docs treat state sync and webhook truth as core, and explicitly suggest manual sync when the UI may be ahead of webhook processing.
- It uses clear subscription helper methods like `cancel`, `cancel_now!`, `resume`, `on_grace_period?`, and `paused?`, which lowers cognitive load.

What to learn:

- Keep the shared surface narrow and ergonomic.
- Give developers escape hatches for stale lifecycle views and operator repair.
- Put provider caveats in the primary docs, not buried ADRs.

What to avoid:

- Pay's processor matrix is useful, but some behaviors still vary sharply by provider. Accrue should avoid implying a method name guarantees the same commercial effect everywhere.
- Pay's Braintree swap story is a good warning: its docs admit Braintree swaps are implemented by cancel-and-recreate. Accrue should keep this level of semantic honesty whenever behavior is emulated rather than native.

### Laravel Cashier and Spark

What Cashier/Spark get right:

- Cashier is opinionated and Stripe-specific enough to be ergonomic. It leans on Stripe's hosted portal instead of rebuilding everything.
- Spark turns lifecycle management into a coherent companion-app surface: plans, invoices, payment methods, and billing navigation are packaged together.
- Stripe-hosted portal guidance is simple because lifecycle options are configured at the source of truth.

What to learn:

- Hosted portal where available is a leverage multiplier. Let the provider own UI complexity when the provider is actually good at it.
- Companion-app polish matters. A billing library becomes much more adoptable when the default UI path is understandable and well-bounded.

What to avoid:

- Cashier's ergonomics come partly from being Stripe-first. Accrue should not generalize Stripe-only affordances into fake cross-provider promises.
- Spark works because it narrows the provider story. Accrue must preserve explicit capability labels when the portal surface differs by provider.

### ActiveMerchant

What it got right:

- Massive gateway reach and a stable abstraction proved the demand for a common payment facade.

What to avoid:

- This is the canonical warning for Accrue. Broad gateway sameness creates pressure toward least-common-denominator APIs and lots of "works, except on gateway X" behavior.
- Subscription lifecycle polish should not widen supported processor breadth or introduce generic lifecycle APIs that hide commercial differences.

### Stripity Stripe-style boundary

What it gets right:

- It stays a low-level Stripe client, not a billing product. That boundary prevents semantic overreach.

What to learn:

- Accrue should keep a strict seam between processor client truth and Accrue billing semantics.
- When a processor cannot do something cleanly, typed failure is better than pseudo-support.

What to avoid:

- Do not let lifecycle polish become an excuse to stuff raw provider quirks straight into the public facade. The facade should stay business-meaningful, but not dishonest.

### Hosted portal lesson

- Stripe's customer portal exposes plan switching, quantity updates, cancellation reasons, retention coupons, invoice history, and configurable downgrade timing directly in the provider UI.
- Braintree does not offer an equivalent first-party hosted self-serve portal in the docs reviewed here. That makes Accrue's mounted local portal the right strategic move for Braintree, but it also means Accrue now owns clarity, copy, and safety for those lifecycle flows.

Bottom line from precedent:

- The best libraries either stay narrow and low-level, or they offer a sharp, opinionated lifecycle surface with explicit provider boundaries.
- The bad outcome is pretending all processors share the same lifecycle semantics.

## 5. Fit with Accrue strategy and current repo state

This direction fits Accrue's stated strategy if it is framed as semantic consolidation inside the existing `gateway subscription core`, not as new parity expansion.

Current fit signals:

- `STRATEGY.md` already says Accrue should learn from Pay and Cashier while avoiding the ActiveMerchant trap.
- v1.32 and v1.33 shipped the difficult processor work: mutation support, webhook convergence, payment method CRUD, refund convergence, first-party Braintree checkout/portal, discount mapping, and local metering.
- The public lifecycle facade is already rich: `cancel/2`, `cancel_at_period_end/2`, `resume/2`, `pause/2`, `unpause/2`, `swap_plan/3`, `update_quantity/3`, and local predicates such as `canceling?/1` and `paused?/1`.
- The repo has clear evidence that lifecycle behavior is now spread across code, admin, portal, tests, and guides. That is precisely when a polish milestone becomes justified.

Current drift signals that argue for polish:

- `accrue/lib/accrue/billing_portal.ex` still describes the portal as Stripe-hosted, which is no longer the full truth after v1.33's Braintree local portal work.
- `accrue/guides/braintree-local-portal.md` still demonstrates immediate cancellation as the primary self-serve path, while the Stripe portal checklist strongly warns against easy immediate cancel and recommends end-of-period cancellation plus retention posture.
- Braintree intentionally rejects `cancel_at_period_end`, scheduled cancellation, pause collection, and provider-side resume semantics in the adapter. That is acceptable, but it means the public lifecycle story now needs stronger capability-driven guidance and UX copy.
- The support matrix still contains historical staged-target language around cancellation semantics that can confuse what is shipped versus what is intentionally unsupported.

Strategic conclusion:

`subscription lifecycle polish` is a good fit only if the milestone is framed as "make the shipped lifecycle contract unsurprising across providers". It is a weak fit if framed as "finish lifecycle parity".

## 6. Recommended scope if chosen

Recommended v1.35 scope:

1. Lifecycle contract audit and doc correction
   - Reconcile ExDoc, guides, support matrix, and companion-app copy with actual shipped provider behavior.
   - Remove stale Stripe-only wording where Braintree local portal now exists.
   - Publish one lifecycle truth table covering:
     - immediate cancel
     - end-of-period cancel
     - scheduled cancel
     - resume pending cancel
     - pause/unpause
     - plan swap / downgrade timing
     - quantity changes
     - where each behavior is native, emulated, unsupported, or host-owned

2. Cancellation-policy hardening
   - Make end-of-period cancellation the documented and UI-default recommendation wherever Accrue owns the UX.
   - Preserve immediate cancel, but demote it behind explicit copy because it is a footgun for revenue recovery and user clarity.
   - Mirror Stripe portal lessons in the Braintree local portal copy: cancellation reason capture, retention prompts, and clear access-end timing even if some data stays local rather than provider-native.

3. Capability-first lifecycle UX
   - Ensure portal/admin/facade errors and copy clearly say what happens on each provider instead of generic "unsupported" language.
   - Prefer typed capability messaging like "Braintree cannot resume a provider-canceled subscription; create a new subscription" over abstract processor errors.

4. Staleness and supportability improvements
   - Add or standardize a post-portal/post-checkout lifecycle refresh pattern where user-facing screens can safely converge after redirect before webhook lag resolves.
   - Tighten testing guidance and host-example patterns for lifecycle assertions around grace periods, cancellation visibility, and state convergence.

5. One visible companion-app improvement
   - Ship at least one concrete UX improvement in `accrue_portal` or `accrue_admin`, such as a unified lifecycle status panel with "active / canceling / paused / past due / ended" language and explicit next-step actions.

Explicitly out of scope:

- New processor integrations
- Broad new lifecycle primitives
- Braintree fake parity that invents provider capabilities
- Merchant-of-record or finance-system expansion
- Reopening Hyperwallet / marketplace questions

## 7. Recommendation score

**8/10**

Rationale:

- **Why not 9 or 10:** the risk of a vague, low-signal "polish" milestone is real, and some lifecycle divergence is structural rather than fixable.
- **Why still high:** the repo is exactly at the point where semantic consolidation will pay off. v1.31-v1.33 shipped the processor-heavy work; v1.34 was unrelated invoice infrastructure. The next milestone can turn the dual-provider core from technically capable into reliably understandable.
- **What would make it a 9:** writing the milestone as a bounded lifecycle-clarity release with 3-5 sharp deliverables, at least one user-visible portal/admin improvement, and a single lifecycle SSOT document that every surface points at.
- **What would make it a 5:** treating it as open-ended cleanup or trying to erase provider differences.

## 0. Executive Summary (the chosen direction, up front)

1. **Adopt `{:phoenix_storybook, "~> 1.2", only: [:dev, :test]}`.** Deps tree is already satisfied (phoenix `~> 1.8`, LiveView `~> 1.1`/`1.2`, elixir `~> 1.15` floor — accrue_admin is on `~> 1.19`). The only new dev/test transitive packages are `makeup_eex`, `makeup_html`, `mdex` (markdown/syntax for the Storybook UI itself) — none reach a host runtime.

2. **Mount via the existing `dev_routes?` gate using the exact sibling-scope pattern already proven for Mailglass** in `AccrueAdmin.Router` (lines 107–138). Storybook routes are emitted at macro-expansion time only when `dev_routes?` is true, so the `import PhoenixStorybook.Router` directive never compiles into a host `:prod` build. This is the leak-proof pattern; do NOT mount Storybook inside the `:accrue_admin` `live_session` (Storybook emits its own `live_session`, and Phoenix forbids nesting).

3. **Drive stories programmatically from `ComponentRegistry`.** `variations/0` is a plain Elixir function returning a list of `%Variation{}` / `%VariationGroup{}` structs — it can be generated at compile time from `ComponentRegistry.entries/0` (per-family variations from `applicable_states` + `specimens`) and `ComponentRegistry.group_contracts/0` (one story per group). One generator module + ~14 thin family `.story.exs` shims + ~8 group shims replace hundreds of hand-written variations. The registry stays the SSOT; Storybook becomes a *second renderer* of it (the kitchen is the first).

4. **Keep the `/dev/components` kitchen as the registry's regression-test renderer; add Storybook as the human-facing design lab.** Do not delete the kitchen — its rendered HTML backs the Phase-189/190 drift/coverage tests (`data-ax-family`, `data-ax-state`, `data-component-group` locators that Playwright + ExUnit assert against). Storybook is additive; the registry is the shared truth both consume.

5. **Theme/state matrix: enable Storybook's built-in color-mode** (`color_mode: true`) with `color_mode_sandbox_dark_class` wired to accrue_admin's theming — but accept that accrue_admin uses `html.accrue-admin[data-theme="dark"]` (an *attribute* selector on a *class-scoped root*), which Storybook's class-based sandbox does not natively emit. Resolve with a thin sandbox-scoped CSS shim (documented below). This is the one real integration wrinkle; budget a half-day spike.

6. **Forward-only page-level visual QA: EXTEND the existing 21,276-cell baseline, do NOT adopt a SaaS.** The prior milestone already ships a complete Playwright + axe harness (`accrue_admin/e2e/*.spec.js`, `playwright.config.js`) and a cell-schema (`baseline.cells.json`) whose `cell_id` is `{prefix}__{surface}__{mode}__{theme}__{state}__{dimension}` with a `surface_type` discriminator. Add `surface_type: "page-flow"` cells over the ~20 real admin pages (the same machinery the Phase-191 page-flow spec already exercises) and gate with the existing `regressions.ndjson` zero-regression rule. Storybook is **not** the visual-regression engine — it is the design lab; the existing Playwright-over-real-routes harness remains the gate. This honors the maintainer's screenshot+adversarial-judge preference over Percy/Applitools (TOOL-02 deferral).

### 1.2 The dev/test-only mounting pattern (leak-proof)

accrue_admin already has the exact pattern this needs. `AccrueAdmin.Router.accrue_admin/2`:
- computes `dev_routes? = (Mix.env() != :prod)` (overridable via `:allow_live_reload`),
- mounts dev LiveViews (`/dev/components`, `/dev/clock`, …) **inside** an `if dev_routes? do` block within the `live_session`,
- and wraps **Mailglass** dev routes as a **sibling scope** via `wrap_with_mailglass_dev_routes/3` because Mailglass emits its own `live_session` (nested `live_session` is forbidden by Phoenix).

PhoenixStorybook is exactly like Mailglass: `live_storybook/2` emits its own `live_session`. **Copy the Mailglass sibling-scope precedent verbatim.**

#### Backend module — gate behind compilation env

```elixir
# accrue_admin/lib/accrue_admin/dev/storybook.ex
if Mix.env() != :prod do
  defmodule AccrueAdmin.Dev.Storybook do
    @moduledoc false
    use PhoenixStorybook,
      otp_app: :accrue_admin,
      content_path: Path.expand("../../../storybook", __DIR__),
      # accrue_admin ships a COMMITTED, pre-built CSS bundle (priv/static/accrue_admin.css).
      # Point Storybook at the SAME bundle so the lab renders shipped styles, not a Tailwind rebuild.
      css_path: "/<mount>/assets/storybook-css",
      js_path: "/<mount>/assets/storybook-js",
      sandbox_class: "accrue-admin",
      color_mode: true,
      color_mode_sandbox_dark_class: "ax-theme-dark-shim",
      title: "Accrue Admin"
  end
end
```

The `if Mix.env() != :prod do` wrapper mirrors `ComponentRegistry` (line 1) and `ComponentKitchenLive` (line 1) — the module simply does not exist in a host `:prod` compile, so a host that mounts `accrue_admin/2` in prod never references `PhoenixStorybook`.

#### Router — sibling scope, dev-only emission

```elixir
# Add a second wrapper, parallel to wrap_with_mailglass_dev_routes/3:
defp wrap_with_storybook_dev_routes(base_ast, true, mount_path) do
  if Code.ensure_loaded?(PhoenixStorybook.Router) do   # REQUIRED — see §1.4
    dev_ast =
      quote bind_quoted: [mount_path: mount_path] do
        import PhoenixStorybook.Router    # compile-time import — must be inside the true-branch quote only

        scope mount_path do
          pipe_through(:accrue_admin_browser)
          storybook_assets()
        end

        scope mount_path do
          pipe_through(:accrue_admin_browser)
          live_storybook("/dev/storybook", backend_module: AccrueAdmin.Dev.Storybook)
        end
      end

    quote do
      unquote(base_ast)
      unquote(dev_ast)
    end
  else
    base_ast
  end
end

defp wrap_with_storybook_dev_routes(base_ast, _dev_routes?, _mount_path), do: base_ast
```

Then chain it in `accrue_admin/2`, after the Mailglass wrap:

```elixir
    end
    |> wrap_with_mailglass_dev_routes(dev_routes?, mount_path)
    |> wrap_with_storybook_dev_routes(dev_routes?, mount_path)
```

**Why this cannot leak (the three guarantees):**
1. `import PhoenixStorybook.Router` is a compile-time directive. It lives *only* inside the `true`-arm `quote` block, which is only spliced into the host router AST when `dev_routes?` is true **and** the dep is loaded. In a host `:prod` compile (`dev_routes? == false`), the import never executes and `phoenix_storybook` (a `:dev, :test` dep) is correctly absent. This is the documented reason the Mailglass wrap is structured this way (router lines 116–120).
2. The backend module is `if Mix.env() != :prod`-guarded, so it does not compile into a prod release.
3. `storybook_assets()` and `live_storybook/2` are scoped under the host's mount path and `:accrue_admin_browser` pipeline — they inherit the same auth/CSP posture as the rest of the admin and live at `<mount>/dev/storybook`, parallel to `<mount>/dev/components` and `<mount>/dev/mail`.

### 1.3 Pitfalls of dev-only deps in a published Hex package (footguns)

| Footgun | Why it bites | Mitigation |
|---------|-------------|------------|
| **Compile-time `import` outside a dev branch** | `import PhoenixStorybook.Router` at module top-level would run during host `:prod` compile and fail (dep absent). | Keep the import inside the `true`-arm `quote` only (the Mailglass precedent). Never `import` at router module scope. |
| **`@moduledoc`/typespecs referencing a dev-only module** | ExDoc `--warnings-as-errors` (already in accrue_admin docs config) chokes on autolinks to `AccrueAdmin.Dev.Storybook`. | Already covered: `skip_code_autolink_to` in `mix.exs` matches `^AccrueAdmin\.Dev\.` — extend nothing, it's pre-handled. |
| **Story files shipped in the Hex tarball** | `package.files` could sweep `storybook/**/*.story.exs` into the published tarball, bloating it and confusing adopters. | `package.files` in `accrue_admin/mix.exs` is an allowlist (`~w(lib config guides priv/static …)`). `storybook/` is NOT listed → stories are auto-excluded. Keep stories in a top-level `storybook/` dir, NOT under `lib/`. |
| **`content_path` resolving at runtime in prod** | If the backend module compiled in prod, `content_path` would point at a nonexistent dir. | Backend module is env-guarded (does not compile in prod). |
| **Asset pipeline assumes esbuild/Tailwind in the host** | Storybook's default setup wires `assets/js/storybook.js` + a Tailwind `storybook` build profile into the *host* app. accrue_admin has **no Tailwind** and ships a committed CSS bundle (per `accrue_admin CSS bundle rebuild` memory). | Do NOT adopt the host-app asset recipe. Serve Storybook's required JS/CSS from accrue_admin's existing `AccrueAdmin.Assets` controller (the same mechanism already serving `accrue_admin.css`/`.js`). See §4.3. This is the single biggest setup deviation from the docs. |

### 1.4 REQUIRED hardening: guard the Storybook wrap on dep availability (library ≠ app)

This is the crucial library-vs-app distinction the maintainer must not miss. **Mix does not fetch a dependency's `only: [:dev, :test]` deps for a consuming host app** — it only fetches them for the top-level project. So when a host pulls `accrue_admin` from Hex and compiles in its *own* dev env, `phoenix_storybook` is **never downloaded**, yet accrue_admin's `dev_routes?` defaults to `Mix.env() != :prod` = true. Without a guard, the host dev compile would try to `import PhoenixStorybook.Router` and **fail to compile**.

The fix is the `Code.ensure_loaded?(PhoenixStorybook.Router)` guard shown in §1.2: it makes the wrap inert wherever the dep is absent. accrue_admin's own dev/test compiles (where the dep IS present) emit the routes; consumed-from-Hex host dev compiles transparently skip them.

> The Mailglass wrap gets away *without* this guard only because `mailglass_admin` is genuinely present in accrue_admin's dev/test and the demo host wires it explicitly. Storybook needs the `Code.ensure_loaded?/1` belt-and-suspenders. **Encode as a hard acceptance criterion (STY-xx): "a host app dev compile without `phoenix_storybook` succeeds and exposes no `/dev/storybook` route."** Prove it by compiling `examples/accrue_host` and asserting the route is absent.

### 1.5 Decision

**ADOPT `{:phoenix_storybook, "~> 1.2", only: [:dev, :test]}`** with the env-guarded backend module + `Code.ensure_loaded?`-guarded sibling-scope router wrap. Mounting cost is low (the Mailglass precedent is a near-exact template); the one real cost is the asset-serving deviation (§4.3) and the `data-theme` shim (§4).

## 2. Story Authoring — registry-driven generation

### 2.1 How PhoenixStorybook stories work (verified)

A story is a module `use PhoenixStorybook.Story, :component | :live_component | :page`:

| Type | Use for | Key callbacks |
|------|---------|---------------|
| `:component` | Stateless function components (`&Mod.fun/1`) — pulls `@doc` | `function/0`, `variations/0` |
| `:live_component` | `Phoenix.LiveComponent` (stateful) — pulls `@moduledoc` | `component/0`, `variations/0` |
| `:page` | Free-form doc/markdown pages (no single component) | `render/1`, `navigation/0` |

`variations/0` returns a **plain Elixir list** of:
- `%PhoenixStorybook.Stories.Variation{id:, attributes:, slots:, template:, description:}`
- `%PhoenixStorybook.Stories.VariationGroup{id:, variations: [...], description:}` (renders multiple variations in one block — perfect for a state matrix).

Minimal example (verified shape):
```elixir
defmodule Storybook.Button do
  use PhoenixStorybook.Story, :component
  alias PhoenixStorybook.Stories.{Variation, VariationGroup}
  def function, do: &AccrueAdmin.Components.Button.button/1
  def variations do
    [%Variation{id: :primary, attributes: %{variant: "primary"}, slots: ["Save changes"]}]
  end
end
```

### 2.2 Can stories be DRIVEN from `ComponentRegistry`? — YES, feasible and recommended

**`variations/0` is just a function returning a list. Nothing requires the list to be literal.** It can be computed at compile time from registry data. accrue_admin's registry is *purpose-built* for exactly this — it already encodes everything a variation needs:

| Registry field (`ComponentRegistry.entries/0`) | Maps to Storybook |
|---|---|
| `family` | story module (one story per family) |
| `variant` | variation `id` prefix |
| `specimens: [%{label, props, content}]` | one `%Variation{id: label, attributes: props, slots: [content]}` per specimen |
| `applicable_states` | one variation (or a `VariationGroup`) per state — drives the state matrix |
| `na_states` | `description`/note (rendered as "n/a — reason"), or skipped |
| `group_contracts/0` (8 groups) | one `:page`-type or composite story per group |

#### Recommended generator pattern

Create a single compiled module that materializes `variations/0` from a family's registry entries, so each `.story.exs` is a ~5-line shim:

```elixir
# storybook/_support/registry_story.ex (compiled .ex, NOT a .story.exs, NOT under lib/)
defmodule AccrueAdmin.Storybook.RegistryStory do
  alias PhoenixStorybook.Stories.Variation

  @doc "Build variations for a family from ComponentRegistry specimens."
  def variations_for(family) do
    AccrueAdmin.Dev.ComponentRegistry.variants_for(family)
    |> Enum.flat_map(fn entry ->
      Enum.map(entry.specimens || [], fn s ->
        %Variation{
          id: :"#{entry.variant}_#{slugify(s.label)}",
          attributes: s.props,
          slots: List.wrap(s.content),
          description: s.label
        }
      end)
    end)
  end
  # ... slugify/1 ...
end
```

Then each story file is trivial:
```elixir
# storybook/components/button.story.exs
defmodule Storybook.Components.Button do
  use PhoenixStorybook.Story, :component
  def function, do: &AccrueAdmin.Components.Button.button/1
  def variations, do: AccrueAdmin.Storybook.RegistryStory.variations_for("button")
end
```

**Two viable axes for the state matrix** (pick per Phase 193):
- **Variation-per-specimen** (above): mirrors the registry's `specimens` (Default / Long-overflow / Disabled / Loading). Simplest; matches what designers want to *see*.
- **VariationGroup-per-state**: build one `%VariationGroup{}` per entry whose member variations are the applicable states, using the `data-ax-force` attributes the kitchen already uses (`do_render_specimen` forces `hover`/`focus`/`active` via `data-ax-force`). This reproduces the full applicable-states matrix inside Storybook. Recommended for primitives where state coverage is the point (button, input, status).

> The kitchen's `do_render_specimen/4` dispatcher (per-family render logic, ~700 LOC) is essentially a hand-written variation generator already. The registry-driven Storybook generator **subsumes** it: both consume `entries/0`; Storybook's `attributes`/`slots` map directly onto `props`/`content`. You are not writing new specimen logic — you are re-pointing the existing specimen data at a second renderer.

### 2.3 Footguns in story authoring

- **`.story.exs` files are evaluated, not compiled into your app.** They can call into compiled support modules (`AccrueAdmin.Storybook.RegistryStory`, `ComponentRegistry`) but the `.story.exs` itself must stay thin. Put generation logic in a compiled `.ex` under `storybook/_support/` or `lib/accrue_admin/dev/`.
- **Live-reload of `.exs`**: the docs' watcher recipe is for a host app. accrue_admin's own dev server (the E2E server / demo host) needs the `.exs` glob added to live-reload patterns only in *accrue_admin's own* dev config, never in the published package.
- **Slots vs attributes**: components like `Button` take label via slot (`slots: ["Save"]`); form components take everything via attributes (`props`). The registry already distinguishes via `content: nil` (no slot) — map `content: nil` → `slots: []`.
- **Unique DOM ids**: the kitchen namespaces ids per theme column (`"#{theme}-inp-error"`). Storybook renders each variation in isolation, so id collisions are less likely, but registry `specimens` that hardcode `id:` (e.g. `"inp-default"`) will collide if the same family renders twice on one Storybook page — prefer letting the generator suffix ids with the variation id.

### 2.4 Decision

**Generate variations programmatically from `ComponentRegistry`.** One compiled `RegistryStory` generator + ~14 family story shims + ~8 group story shims. The registry remains SSOT; Storybook and the kitchen are two renderers of it. This is the lowest-duplication path and is explicitly enabled by `variations/0` being an ordinary function.

## 3. Migration — kitchen → Storybook

### 3.1 Keep the kitchen. Add Storybook. (do NOT replace)

| Concern | `/dev/components` kitchen | PhoenixStorybook | Verdict |
|---------|---------------------------|------------------|---------|
| **Backs drift/coverage tests** | YES — `data-ax-family`, `data-ax-state`, `data-component-group`, token-visibility, `ax_class` render-coverage assertions (Phase 189/190 ExUnit + Playwright) | No (Storybook DOM is its own structure) | **Keep kitchen** as the test renderer |
| **Designer/human review UX** | Adequate but bespoke | Best-in-class (search, isolation, variation switching, color-mode toggle, doc panels) | **Add Storybook** for human review |
| **State matrix render** | Hand-rolled `do_render_specimen/4` | Registry-driven variations | Both from registry |
| **Maintenance** | ~700 LOC dispatcher | ~20 thin shims + 1 generator | Storybook lighter going forward |

**Why keeping both is not duplication:** they share the registry as SSOT. The kitchen's value is its **stable test locators** that the forward-only gate already depends on — ripping it out would force re-pointing every Phase-189/190 drift test at Storybook's DOM, which is churn with no upside and a regression risk against the zero-regression gate. The marginal cost of keeping the kitchen is ~0 (it's already written and passing).

### 3.2 Migration steps (Phase 193)

1. Add the dep, backend module, asset serving (§4.3), and router wrap (§1.2/§1.4).
2. Write `AccrueAdmin.Storybook.RegistryStory` generator (compiled support module).
3. Generate one `.story.exs` per registry family (14 families with `applicable_states`) + the card/foundation reference families.
4. Generate one story per `group_contracts/0` entry (8 groups) — as `:page` stories embedding the existing `render_group_body/2` markup, OR `:component` stories whose `variations/0` returns one representative composition.
5. Wire color-mode (§4) so light/dark renders match the kitchen.
6. Leave the kitchen and all its tests untouched. Add a small test asserting the Storybook content_path resolves and the backend module compiles (dev/test only).
7. Add the **host-prod/host-dev-absence** test (§1.4).

### 3.3 What NOT to do

- Do not move story files under `lib/` (they'd ship in the tarball and compile into prod).
- Do not delete `ComponentKitchenLive` or its `do_render_specimen/*` clauses until/unless the Phase-189/190 tests are re-homed (they aren't in scope for v1.54).
- Do not let Storybook become the SSOT — the registry stays canonical; if a future contributor edits a specimen, they edit `ComponentRegistry`, and both renderers update.

## 4. Theming & State Matrix — light/dark/system + `data-theme` scoping

### 4.1 The wrinkle: Storybook is class-based, accrue_admin is attribute-based

- Storybook color-mode adds/removes a **class** on the sandbox wrapper: dark → adds `color_mode_sandbox_dark_class`; light → `color_mode_sandbox_light_class` (or none).
- accrue_admin's dark styles are scoped as **`html.accrue-admin[data-theme="dark"] …`** (an attribute selector on the `<html>` root that carries the `accrue-admin` class), per the kitchen comment (lines 184–190) and the `BrandPlug`/theme session plumbing in the router.

So Storybook's `sandbox_class: "accrue-admin"` gets you the base scope, but its dark-class toggle won't satisfy `[data-theme="dark"]` selectors. **You must bridge class → attribute.**

### 4.2 Bridge options (pick one)

**Option A — CSS shim (recommended, lowest risk).** Configure `color_mode_sandbox_dark_class: "ax-theme-dark-shim"` and ship a tiny Storybook-only CSS rule that re-expresses the dark theme under that class. Because accrue_admin's theme tokens are CSS custom properties, the shim is a single selector that mirrors the `[data-theme="dark"]` token block:
```css
/* storybook-only shim — re-scope the dark token set under the sandbox dark class */
.psb-sandbox.accrue-admin.ax-theme-dark-shim { /* same --ax-* dark custom-property values as [data-theme="dark"] */ }
```
Generate this shim from the same source as `theme.css`'s dark block (or `@import` it). Keep it in the Storybook CSS bundle only — never in the shipped `accrue_admin.css`.

**Option B — JS hook to set the attribute.** A Storybook JS hook (registered in `storybook.js`) that observes the color-mode class and mirrors it onto `[data-theme]` on the sandbox element. More moving parts; only choose if the CSS shim can't reach a selector.

**Option C — three explicit variations (light/dark/system) per specimen.** Skip color-mode; render each specimen three times with the theme forced via wrapper markup. Heaviest (3× variations) and doesn't use Storybook's nice toggle. Fallback only.

### 4.3 Asset serving (the no-Tailwind deviation)

accrue_admin ships a **committed, pre-built CSS bundle** (`priv/static/accrue_admin.css`, rebuilt via `mix accrue_admin.assets.build`) and serves it through `AccrueAdmin.Assets` (router lines 52–53). Storybook's default recipe assumes a host esbuild+Tailwind pipeline — **do not adopt it.** Instead:

1. Build a `storybook.css` = the shipped `accrue_admin.css` **+** the dark-shim (§4.2A) **+** Storybook's own required sandbox CSS. Commit it like the main bundle.
2. Build a `storybook.js` = Storybook's required JS (`window.storybook` hooks) — minimal; accrue_admin has no custom hooks the lab needs beyond theme.
3. Serve both from a dev-only `AccrueAdmin.Assets`-style route at the `css_path`/`js_path` the backend module declares. This keeps "lab renders shipped styles" true and avoids introducing Tailwind into a package that deliberately has none.

> This is the single most important setup correction vs. the official guide: **accrue_admin's design SSOT is the committed `ax-*` CSS bundle, not Tailwind.** Storybook must render *that* bundle, or the lab will lie about what adopters see. (See the `accrue_admin CSS bundle rebuild` lesson: editing source `app.css` ships nothing until rebuilt + committed — the same discipline applies to `storybook.css`. Phase 189 already shipped dead CSS by missing this; do not repeat it.)

### 4.4 Decision

**Enable `color_mode: true` + dark-class shim (Option A).** Renders the full light/dark matrix with Storybook's native toggle while honoring accrue_admin's `data-theme` token scoping. "system" is the OS-default fallback (no forced class) — matches the kitchen, which follows the global topbar toggle. State matrix comes from the registry-driven variations (§2.2).

| `accrue_admin/e2e/*.spec.js` + `playwright.config.js` | Playwright (chromium-desktop 1280×900 + chromium-mobile Pixel 5), `mix accrue_admin.e2e.server`, axe a11y (`admin-a11y.spec.js`), page-flow harness (`admin-page-flow-phase191.spec.js` with viewports × states × theme helpers), baseline capture (`admin-baseline.spec.js`) |

**The page-flow Playwright harness already exists** (Phase 191) — it drives real admin routes, sets theme, asserts focus/scroll/pointer/clip across viewports × states. v1.54 needs to **promote its output into scored page-flow cells** and fold them into the same baseline + gate.

### 5.2 How leading teams do idempotent (forward-only) design-system visual QA

| Approach | How it gates regressions | Fit for accrue_admin |
|----------|--------------------------|---------------------|
| **Playwright screenshot snapshots** (`toHaveScreenshot`) | Pixel-diff vs committed PNG baseline; new screenshot must match | Works, but pixel-diffs are flaky across font-rendering/OS and produce noisy regressions; the existing harness deliberately uses **assertions + scored cells**, not pixel-diff, to avoid this |
| **Storybook + Chromatic** (SaaS) | Cloud pixel-diff per story, human approve/reject | **Rejected** — SaaS, paid, exactly the Percy/Applitools class the maintainer deferred (TOOL-02). Also gates *stories*, not real page flows |
| **Storybook + Loki / Playwright-component** (self-host) | Local pixel-diff of stories | Self-hosted, but still pixel-diff of *components/stories*, not page flows; duplicates what the kitchen+registry already prove |
| **axe accessibility snapshots** | a11y violation count must not increase | Already present (`admin-a11y.spec.js`); keep as one dimension, not the whole gate |
| **Cell-baseline + adversarial judge** (the existing approach) | Each (surface × mode × theme × state × dimension) cell scored ≥ baseline; zero regressions in `regressions.ndjson` | **Best fit** — already shipped, forward-only by construction, screenshot+judge friendly, no SaaS |

**Industry note:** the cell-baseline + rubric + adversarial-judge approach is functionally a structured, self-hosted equivalent of "visual review with approval gating" (Chromatic's model) but scored on *design dimensions* rather than raw pixels — which is more robust for a design-system hardening pass where intentional visual change is the goal and pixel-diff would flag every deliberate improvement as a "regression."

### 5.3 Recommended extension: add `surface_type: "page-flow"` cells

Extend the existing schema (no new tooling):

1. **New cell axis value:** `surface_type: "page-flow"` (alongside existing `"component"`, `"group"`). `surface` = the page archetype/route (e.g. `dashboard`, `subscription-detail`, `subscriptions-list`, …).
2. **Enumerate page-flow cells** = `pages (~20) × modes (desktop, mobile) × themes (light, dark) × states (per page: populated, empty, loading, error, long-content) × dimensions (the 12 rubric dims)`. Reuse `admin-page-flow-phase191.spec.js`'s viewport/state/theme helpers as the capture driver.
3. **Score** each cell via the same adversarial multi-lens judge used in v1.53 (screenshot evidence + rubric), writing into an additive page-flow baseline (recommended: sibling `baseline.page-flow.cells.json` so the immutable 187 baseline keeps its provenance; merge at gate time).
4. **Gate:** the existing `regressions.ndjson` zero-regression rule applies unchanged — a page-flow cell scoring below its baseline is a regression and blocks merge. New cells (no prior baseline) establish their own baseline forward-only (you may *raise* a baseline, never lower it).
5. **Keep axe + interaction assertions** (focus/scroll/pointer/clip from the Phase-191 helpers) as evidence feeding the `interaction-integrity`, `focus-semantics`, and a11y-adjacent dimensions — the rubric explicitly says interaction-integrity is scored from live Playwright evidence, screenshots are supporting only.

### 5.4 Footguns / anti-patterns

- **Don't introduce pixel-diff snapshots as the gate.** They'll flag every intentional v1.54 improvement as a regression — the opposite of forward-only design uplift. Score dimensions, not pixels.
- **Don't let Storybook become the visual-regression surface.** Storybook proves *components in isolation*; the page-level gate must run over *real composed routes* (where info-dump density, scroll traps, and overlay defects actually live — the v1.54 goal). Storybook and the page-flow gate are complementary, not substitutes.
- **Don't mutate the 187 baseline in place** without provenance — prefer an additive page-flow baseline file so the 21,276-cell component/group baseline stays auditable and the merge-gate computes the union.
- **Don't double-count overlay tags as dimensions** (the rubric is explicit). Page-flow cells use the same 12 dimensions + overlay tags.
- **Determinism:** the page-flow capture must seed deterministic fixtures (the harness already does via `seedScenarioForSurface`) — non-deterministic data would create phantom regressions. Honor the existing seed-idempotency discipline (and the committed `e2e/generated/copy_strings.json` regen lesson).

### 5.5 Decision

**Extend the existing cell-baseline + Playwright/axe + adversarial-judge harness with `surface_type: "page-flow"` cells over the ~20 real admin routes; gate with the unchanged `regressions.ndjson` zero-regression rule; no SaaS, no pixel-diff gate.** This honors TOOL-02 (screenshot + adversarial judge over Percy/Applitools), reuses Phase-191's page-flow Playwright driver, and keeps the forward-only guarantee intact.

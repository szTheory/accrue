# v1.59 Domain Pitfalls: Account-Scoped Multi-Rail & Offline Entitlements

**Project:** Accrue  
**Domain:** Stripe web billing + Apple IAP account projection + offline study leases  
**Researched:** 2026-07-31  
**Overall confidence:** MEDIUM — the high-impact platform and cryptographic claims are cross-checked against current Apple, Stripe, IETF, and repository sources. Offline-device abuse resistance and App Review outcomes remain host- and release-specific.

## Accepted Risk Contract

The approved policy is **not** “offline payment authority.” It is bounded study continuity: a verified, device-bound ES256 lease has a rolling 30-day revalidation target (shortened by a known earlier end). Once stale, already-downloaded lessons and local progress continue, while new premium downloads and other value-expanding actions wait for reconnection. There is no independent 72-hour cutoff; any explicit signed `exp` is a protocol/provider bound, not a second grace timer.

This deliberately accepts bounded **stale access** after a refund, revocation, expiry, account/device compromise, or missed observation. That is the product tradeoff that avoids connectivity-driven learner lockout. It must be stated plainly in docs, support, finance, and security review: the lease reduces exposure; it cannot instantly revoke an offline device. Provider billing grace is already reflected in the canonical grant bound and must never be followed by an additional stacked offline grace.

## Critical Pitfalls

### 1. Treating Apple JWS as valid because it parses

**What goes wrong:** A client-supplied transaction or notification is decoded without a complete JWS/certificate and context verification, or a valid Apple token for the wrong app/environment is accepted. A sandbox record can then leak into production, another bundle’s evidence can grant access, or a stale/replayed signed payload can overwrite newer state.

**Why it happens:** JWS compact serialization looks self-authenticating; teams validate only the signature or only `x5c`, but not a pinned Apple trust chain, expected ES256 algorithm, certificate purpose/validity, bundle ID, environment, production app Apple ID where applicable, and transaction/notification semantics. Apple explicitly signs transaction and renewal information as JWS and exposes separate Sandbox/Production environments; its server library exists to perform this verification. [Apple App Store Server API](https://developer.apple.com/documentation/appstoreserverapi/), [WWDC23 server library](https://developer.apple.com/videos/play/wwdc2023/10143/)

**Prevention:** Use a maintained, reviewed verifier or a narrow adapter that pins `alg=ES256`, validates the `x5c` chain to Apple roots, rejects unexpected headers/critical parameters, and binds every decoded payload to configured bundle ID + environment (and production app ID if required). Namespace evidence and external IDs by `rail`, `environment`, and configured app identity; never infer environment from an ID alone. Persist enough redacted verification metadata to reproduce the decision, not raw receipt/JWS bodies.

**Warning signs:** Sandbox/production records share a unique key; `bundleId` or environment is absent from a transaction table; verification failures are retried as grants; raw signed payloads appear in logs; a test accepts `none`, HS256, or a wrong-bundle fixture.

**Owner / gate:** Phase 217. Contract fixtures for malformed chain, wrong algorithm, wrong root, wrong bundle, wrong environment, expired certificate, and verified production/sandbox isolation; dependency/SBOM and crypto-advisory gate before release.

### 2. Ownership-confused `appAccountToken` linking and restores

**What goes wrong:** A restore grants an Apple purchase to whichever local account submits it, or support “fixes” an unmatched purchase by email/device/product matching. This creates account takeover or accidental transfer. Conversely, an overly simple uniqueness rule prevents legitimate continuation where Apple’s token state differs across historical transactions.

**Why it happens:** `appAccountToken` is optional at purchase and Apple permits the server endpoint to set/reset it for an original transaction; replacement affects current/future subscription renewals, not past transactions. Family-shared transactions are not supported by that endpoint. A token is a UUID association mechanism, not proof that the current app session owns a pre-existing local account. [Apple `appAccountToken`](https://developer.apple.com/documentation/appstoreserverapi/appaccounttoken), [Set App Account Token](https://developer.apple.com/documentation/AppStoreServerAPI/Set-App-Account-Token)

**Prevention:** Generate the authenticated immutable Accrue account UUID before StoreKit purchase and pass it as `appAccountToken`. On restore, verify server-side evidence first, then atomically bind only if the token equals the authenticated account’s UUID or if an explicit, auditable ownership policy authorizes attachment. An already-bound different account, absent token, family-shared evidence, or conflict goes to quarantined retry/manual support; it never falls back to email, receipt order ID, device, or product ID. Never automatically transfer, merge, refund, cancel, prorate, or migrate cross-rail ownership.

**Warning signs:** “restore to current user” code has no conflict branch; email is queried in restore handlers; token updates are performed without an authenticated account/session; a single original transaction maps to two account IDs; support cannot see why an evidence row was quarantined.

**Owner / gate:** Phase 217. Concurrent restore-to-two-accounts test, missing/mismatched/replaced-token tests, Family Sharing disposition test, no-heuristic static scan, and a support runbook requiring verified evidence plus audit record.

### 3. Trusting notification delivery as current billing truth

**What goes wrong:** Duplicate/out-of-order Apple or Stripe events are reduced as ordered facts, so a late “active” reopens a refunded/revoked grant or an old state overwrites a newer one. A missed event leaves entitlement wrong indefinitely.

**Why it happens:** Delivery is at-least-once and asynchronous. Stripe explicitly documents duplicate Event deliveries and distinct Event objects for the same underlying object/type; Apple notification history describes what Apple attempted to send at the original time, not current state. Existing Accrue ingestion already deduplicates `UNIQUE(processor, processor_event_id)` and uses Stripe watermarks, but those assumptions are Stripe-shaped and unqualified for a second rail. [Stripe webhooks](https://docs.stripe.com/webhooks), [Apple notification history](https://developer.apple.com/documentation/appstoreserverapi/get-notification-history)

**Prevention:** Persist immutable, rail/environment-scoped evidence idempotently; separately reduce into a versioned source grant using provider time/transaction lineage plus a deterministic tie-breaker. Make duplicate ingest an acknowledged no-op, serialize or use compare-and-swap on the source/account projection, and increment account revision transactionally only when effective access changes. Notifications trigger reconciliation; Apple current subscription status/history is repair authority. Preserve a dead-letter/quarantine path rather than converting malformed/unverifiable evidence into a retry storm.

**Warning signs:** reducer ordering uses receipt time only; duplicate metrics are absent; stale update count rises; a notification handler directly changes the lease; replaying the same delivery changes account revision; Stripe/Apple rows use the same bare identifier key.

**Owner / gate:** Phases 216–217. Property tests permuting duplicate/out-of-order events; concurrent reducer tests; fault-injected queue retry/DLQ replay; reconciliation proves refund/revocation wins after a late positive event; dashboards alert on verification, lag, retry, quarantine, and repair backlog.

### 4. Losing or corrupting Apple repair pagination

**What goes wrong:** Repair stores an early `revision`, changes filters mid-stream, treats notification history as current truth, or ignores updated records reappearing in ascending history. It silently misses entitlement changes.

**Why it happens:** Apple history pages contain up to 20 items and require the same query parameters after the first call; Apple says persist the final revision only for ascending history. Transactions can reappear when modified while an ascending scan runs. Notification history has a separate pagination token and only 180 days in production/30 days in sandbox. [Apple transaction history](https://developer.apple.com/documentation/appstoreserverapi/get-transaction-history), [Apple revision](https://developer.apple.com/documentation/appstoreserverapi/revision), [Apple notification history](https://developer.apple.com/documentation/appstoreserverapi/notificationhistoryresponse)

**Prevention:** Model repair runs with a durable cursor, initial filter fingerprint, page count, retry/backoff and completion state; persist a transaction-history revision only after `hasMore=false` under ascending scan. Upsert each signed transaction idempotently because a changed item may reappear. Use Get All Subscription Statuses for current auto-renewable state and transaction history for other product types; notification history is delivery diagnosis/recovery input, not a state reducer shortcut. Handle 429/5xx as bounded retries and alert on stalled cursors.

**Warning signs:** cursor advances per page; first/next request filters differ; repair has no max-page/run budget; notification-history results directly grant access; repair is green only for <20 fixtures; sandbox and production retention are assumed equal.

**Owner / gate:** Phase 217 and 219. Multi-page, reappearing-update, interrupted-resume, expired-token, 429, 500 and 20+ record fixtures; scheduled reconciliation SLO with age/backlog/last-success alert; a sandbox-specific test run.

### 5. Cross-rail projection races and accidental destructive compatibility changes

**What goes wrong:** A rail revocation removes another rail’s valid grant; two writers mint a lease from split-brain state; or implementation “fixes” multi-rail by turning the global processor into a map, changing `customer/1` to a list, or changing default association semantics, breaking existing adopters.

**Why it happens:** Current code intentionally has a process-global `Accrue.Processor`, `Billing.customer/1` and `LocalMap` each query owner with `limit: 1`, and existing `Customer` uniqueness is `(owner_type, owner_id, processor)`. It is usable groundwork but not an account-wide rail projection. The v1.58 `EntitlementSummary` is a Stripe-only advisory cache and must not become a gate.

**Prevention:** Keep legacy default-rail gateway APIs exact: configured `processor`, bare default-rail price aliases, deterministic `customer/1`, gateway `Subscription`, existing guard returns, and advisory `EntitlementSummary`. Add rail registration, qualified product mappings, all-customers/source-grants reads, an account-scoped snapshot, and a dedicated revisioned projection. Projection changes and revision increment belong in one DB transaction with optimistic/concurrency guard. Union effective grants; source revocation retracts only its source. Duplicate equivalent plans do not stack; features union and quantities take max.

**Warning signs:** `customer/1` result becomes nondeterministic; unqualified `price_id` joins cross rail; a Stripe advisory read appears in resolver/guard; snapshot revision changes without grant delta; optimistic-lock failures are swallowed; an Apple source reaches cancel/dunning/proration code.

**Owner / gate:** Phases 215–216. Migration compatibility matrix and compile-time public-API tests; cross-rail union/revocation/concurrency properties; legacy single-processor regression suite; static isolation gate extending `verify_entitlement_sync_isolation.sh`; explicit check that Apple records cannot call Stripe lifecycle mutations.

### 6. Offline lease treated as unrevocable DRM or a generic JWT

**What goes wrong:** A copied lease works on another device, a device clock rollback extends it, a stale positive lease beats a new denial, a token for another purpose/audience is accepted, or a signing-key compromise grants arbitrary access until every client updates.

**Why it happens:** A signed token is portable unless the client enforces device binding and time/revision rules. Secure storage helps but rooted/compromised devices remain in scope. JWT libraries may accept header-selected algorithms or claim types by default. RFC 8725 requires explicit algorithm selection, full crypto validation, issuer/audience checks, explicit typing, and distinct validation rules. [RFC 8725](https://www.rfc-editor.org/info/rfc8725/)

**Prevention:** Issue compact ES256 JWS only through a purpose-specific issuer with fixed `typ`, algorithm allowlist, `kid`, issuer, audience, account opaque subject, device P-256 public-key-thumbprint, account revision, `iat`, `nbf`, `fresh_until`, and hard `exp`. Client verifies all claims, proof-of-possession/device binding, monotonic wall-clock policy and local last-seen revision/time; it must reject unknown `kid`, wrong issuer/audience/type/device, future-not-valid, hard-expired, rolled-back, or superseded lease. Reconnect authenticates account+device, refreshes due rails, compares revision/device status, then atomically replaces cache with fresh allow or signed deny tombstone. Operate key rotation with overlapping public JWKS, bounded retirement, incident revoke/deny procedure, and no PII/receipt/provider payload in token.

**Warning signs:** token payload contains email/receipt/raw claims; accepting any `alg`; token selection is “latest expiry wins” rather than revision/tombstone aware; no `kid`/rotation runbook; device proof is only an identifier; clock changes have no telemetry; stale mode can download premium content.

**Owner / gate:** Phase 218. Cryptographic negative corpus (algorithm, issuer, audience, type, signature, `kid`, expiry, device, replay, revision and tombstone); clock-forward/backward and copied-storage simulations; key rotation/compromise tabletop; mobile secure-storage and offline-state E2E proof. Document that advanced hardware attestation/fraud detection is deferred, not claimed.

## Moderate Pitfalls

### Duplicate purchases become duplicate charges and finance incidents

**What goes wrong:** A valid web subscriber buys the equivalent Apple product (or inverse) because eligibility is checked after purchase, from stale projection data, or with bare product IDs. Automatic cancellation/migration then creates refund, tax, revenue-recognition and support liabilities.

**Prevention:** Before initiating a purchase, evaluate an account + logical-plan + rail-qualified eligibility snapshot; warn/block when an equivalent effective grant exists. Treat ambiguous/stale/repairing state conservatively with an explicit retry/support path. Never auto-cancel, transfer, refund, prorate, or merge in v1.59. Use stable Stripe idempotency keys for create operations; Stripe returns the first result for the same key, including 500s, so reconcile ambiguous results rather than issuing a new charge. [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)

**Owner / gate:** Phases 216 and 219. Web→iOS/iOS→web second-purchase tests, concurrent eligibility/purchase race tests, finance reconciliation and support exception runbook, duplicate-charge metric/alert.

### Webhook idempotency is necessary but insufficient

**What goes wrong:** Event-ID dedupe succeeds while two distinct Stripe event objects describe the same subscription transition; retries cause duplicated side effects, or a failed handler is permanently marked handled.

**Prevention:** Retain current transactional raw ingest/queue pattern, but idempotently reduce by domain object/version and make outbound side effects transactional/outboxed. Mark processing outcome and retry class; re-fetch/reconcile authoritative provider state after ambiguous transition. Do not expose raw webhook body in errors or telemetry.

**Owner / gate:** Phases 215–216. Duplicate-event-object, crash-after-write/before-side-effect, and replay tests; DLQ runbook and one-click safe replay drill.

### Apple policy/UX mismatch

**What goes wrong:** iOS presents Stripe/web checkout to unlock in-app digital study, calls web access “restore,” or shows local cancel/plan-change controls for Apple billing. Review rejection or misleading customer experience follows.

**Prevention:** Keep purchase and lifecycle capability rail-aware. Apple Review Guideline 3.1.1 requires IAP for in-app digital unlocking and a restore mechanism for restorable purchases; 3.1.3(b) permits cross-platform access to purchases acquired elsewhere when the items are also offered as IAP in the app. Region-specific external-purchase rules require a separate entitlement/legal review. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), [Apple IAP overview](https://developer.apple.com/in-app-purchase/)

**Owner / gate:** Phases 217 and 219. App Review checklist with reviewer account/notes, restore/capability UX test, region/entitlement matrix, and legal/product sign-off before submission.

### Privacy and observability are in tension

**What goes wrong:** Retaining JWS/receipt bodies, `appAccountToken`, device identifiers, email, or B2C Alpha identity in fixtures, logs, lease payloads or operator screens turns billing diagnostics into a breach surface.

**Prevention:** Data-minimize: opaque account/device references or keyed redactions, bounded encrypted evidence storage with purpose/retention/access control, and correlation IDs rather than raw payloads. Log verification outcome, rail/environment, normalized state, time, revision, and repair disposition. Ensure support views reveal only authorized, redacted diagnosis. Treat user deletion/retention/export requirements as host legal policy but document data ownership.

**Owner / gate:** Phases 215 and 219. Automated secret/PII scan across planning, fixtures, token claims and telemetry; retention/access-control review; support screenshot fixture review.

### Sandbox, TestFlight and production behave as different rails

**What goes wrong:** TestFlight’s sandbox notifications or sandbox identifiers enter production rows, a repair job uses the wrong endpoint, or timing/retry behavior seen in sandbox is treated as production proof.

**Prevention:** Store environment as part of every Apple evidence/grant/notification uniqueness and route API calls to the verified environment; Apple documents that TestFlight uses sandbox and transaction ID calls must use the matching environment. Treat sandbox as protocol coverage, not production lifecycle timing evidence. [Apple environment](https://developer.apple.com/documentation/appstoreservernotifications/environment), [Apple Server API](https://developer.apple.com/documentation/appstoreserverapi/)

**Owner / gate:** Phase 217/219. Environment collision fixtures, wrong-endpoint fallback tests, TestFlight smoke checklist, and production-canary reconciliation dashboards.

### Support/SRE operations lack an answerable state model

**What goes wrong:** An operator sees only “not entitled,” cannot distinguish a pending repair from revocation, replays blindly, or finance treats a logical entitlement union as an accounting migration.

**Prevention:** Diagnostic source of truth must show account snapshot revision, per-source rail/environment, normalized + provider state, observed time, redacted correlation, lease horizon/device status, quarantine/retry/error, and next safe action. Keep ledger evidence immutable. Define incident ownership: support resolves identity conflict; SRE owns delivery/repair/key incidents; finance owns refund/charge reconciliation; product/legal owns policy/App Review decisions.

**Owner / gate:** Phase 219. Runbooks/tabletops for late revocation, restore conflict, missed Apple notification, Stripe duplicate charge, key compromise and offline denial; alert-to-runbook linkage and on-call drill.

### OSS dependency and supply-chain drift becomes an authorization failure

**What goes wrong:** An unmaintained JOSE/JWS, x509, Apple API, or mobile secure-storage dependency is adopted without CVE/version/maintenance review; a library update loosens verification defaults or changes Apple payload handling.

**Prevention:** Prefer small, maintained adapters around pinned/reviewed dependencies; generate SBOM/dependency audit, lock versions, monitor advisories and Apple/Stripe changelogs, and test against captured verified fixtures. Never let an optional dependency absence silently disable verification or turn an error into an allow. Keep crypto library selection a Phase 218 explicit decision, not an incidental transitive choice.

**Owner / gate:** Phases 217–219. Dependency review + license/CVE gate, fixture compatibility tests, changelog watch owner, and release checklist requiring no unresolved critical advisories.

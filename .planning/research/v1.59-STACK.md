# v1.59 Stack Research — Account-Scoped Multi-Rail & Offline Entitlements

**Project:** Accrue  
**Researched:** 2026-07-31  
**Scope:** Apple observation rail, account-scoped entitlement projection, and offline entitlement proof.  
**Confidence:** MEDIUM — Apple protocol and JOSE recommendations are primary-source verified; the selected Elixir Apple library is a young third-party implementation and must earn admission through conformance tests.

## Decision

Use three deliberately separate implementation layers:

1. **`app_store_server_library ~> 2.2` behind an Accrue-owned Apple adapter behaviour** for App Store Server API calls and Apple-signed-data verification.
2. **`jose ~> 1.11` directly, behind Accrue-owned small crypto/key-provider behaviours**, for Accrue-issued ES256 offline JWS leases and, only if necessary, independently generated Apple API request JWTs.
3. **Host-owned Finch and Oban supervision** for all network pooling, scheduled reconciliation, retries, and key loading. `accrue` remains a library with its deliberately empty supervisor; it must not start a Finch, an Oban instance, a key-refresh process, or a Crosswake process.

This is a Stripe + Apple milestone only. Keep `lattice_stripe ~> 2.0` as the Stripe transport. Do not add Google Play, Braintree multi-rail parity, Crosswake runtime coupling, receipt validation, or a generic payment abstraction.

The entitlement policy is also locked here: a successful online reconciliation has a **30-day revalidation target**. If that time becomes stale while a learner is offline, already-downloaded study material and local progress continue; new premium downloads and every other value-expanding action wait for reconnection. **There is no 72-hour cutoff.** The signed lease must represent this state explicitly rather than reusing billing grace or silently turning a stale lease into a revoke.

## Why this fits Accrue

The current codebase is already explicit about two boundaries that this work must preserve:

- `Accrue.Application` starts no children. The host owns its Repo, Oban, and Finch pool. That is not an implementation inconvenience: it prevents a library dependency from choosing a process name, pool size, proxy/TLS policy, or job lifecycle for a host.
- `Accrue.Processor.Stripe` is the sole direct `LatticeStripe` caller, and the existing Stripe-native entitlement summary is advisory-only. Apple must neither bypass the new rail seam nor be inserted into that Stripe cache or into Stripe dunning/mutation paths.

Make Apple a verified **observer/reconciler**, not an `Accrue.Processor` lookalike. The adapter returns normalized evidence to the account-grant projector; it does not claim it can cancel, retry, swap, prorate, or dunn an Apple subscription. This protects the approved separation: rail-neutral access, rail-aware lifecycle management.

## Apple App Store Server API V2

### API-request authentication

The Apple API client needs a short-lived bearer JWT signed with the In-App Purchase private `.p8` key:

| Header / claim | Required value / rule |
|---|---|
| `alg` | exactly `ES256` |
| `kid` | the App Store Connect In-App Purchase key ID |
| `typ` | `JWT` |
| `iss` | issuer ID from App Store Connect |
| `iat` / `exp` | Unix seconds; ordinary API tokens must not expire more than 20 minutes in the future |
| `aud` | `appstoreconnect-v1` |
| transport | `Authorization: Bearer <compact-JWT>`; choose production or sandbox base URL from the evidence environment, never a caller-controlled URL |

Let the Apple adapter/library cache this token only below its short Apple-valid lifetime, keyed by `{environment, key_id, issuer_id}`. The private key comes from the host runtime secret provider each time the client/issuer is constructed (or from a host-owned rotation-aware cache); it is never compiled into configuration, logged, serialized, or placed in an offline token.

Use `Get All Subscription Statuses` and paginated transaction history as repair authority after verified evidence; notifications are prompt delivery signals, not a complete ordered ledger. Apple documents sandbox as a distinct base URL and requires that a transaction ID be queried in the environment that created it. Persist `rail = :apple`, `environment`, original-transaction lineage, and Apple transaction identifiers together in every unique key and cursor.

### JWS/x5c verification sequence

For every notification `signedPayload`, StoreKit-supplied signed transaction, API signed transaction, and signed renewal info:

1. Impose a compact-token/body-size ceiling before parsing and retain raw evidence only in bounded, protected quarantine storage.
2. Decode the protected header only to select verification material; do not treat decoded claims as trusted.
3. Require `alg == "ES256"`, a nonempty bounded `x5c` chain, and reject unknown critical headers / unsupported serialization.
4. Validate the presented X.509 chain to pinned Apple root certificate material, validate certificate usage/time, then verify the JWS signature with the leaf public key. Do not fetch arbitrary `x5u`/`jku` URLs and do not trust an unpinned root supplied by the sender.
5. Validate expected bundle ID, expected environment, and production numeric app Apple ID when applicable before projection. Verify nested signed transaction and renewal objects separately; outer notification validity does not authenticate a copied nested string.
6. Only then normalize immutable lineage, effective bounds, revocation/refund information, and `appAccountToken`; append idempotently and project transactionally. A verification failure grants nothing. A retryable OCSP/network error is quarantine/retry, not a negative lifecycle transition.

The selected library explicitly documents this verifier contract: it verifies x5c chains and validates environment/bundle ID; production requires `app_apple_id`. Enable online OCSP checks only when the host supplies an explicit timeout/retry/budget policy. An OCSP outage must queue retry and preserve the last proven grant; it must not create a new grant nor revoke an unrelated Stripe grant.

### `appAccountToken` and linking

Use the stable `EntitlementAccount` UUID as `appAccountToken` from StoreKit purchase initiation. On authenticated restore, accept a verified transaction only when its token resolves to the authenticated account. The Apple API can set/update an account token for an original transaction where Apple permits it; use that repair path only with authenticated account intent and verified original lineage.

Never link by email, Apple ID, device identifier, unverified client payload, or product ID. A valid transaction without an accepted account token/lineage goes to a quarantined repair record and triggers reconciliation, but is not a grant. This avoids accidental account transfer while still allowing automatic repair.

## Apple-library admission decision

**Recommendation: adopt `app_store_server_library` conditionally, behind an interface; do not crown it as canonical.** It is a useful implementation accelerator, not the contract.

Evidence is mixed:

- It is current (2.2.0, updated 2026-02-01) and has direct, relevant APIs: client calls, automatic token/certificate-public-key caching, telemetry, typed Apple models, `SignedDataVerifier`, and live OCSP test opt-ins.
- It is neither Apple-maintained nor ecosystem-proven: Hex reports five releases and zero dependants. Apple’s official server libraries are Swift, Java, Node, and Python—not Elixir.

### Mandatory conformance gate

Before merging it as a production dependency, pass all of the following with pinned version `~> 2.2`:

| Gate | Pass criterion |
|---|---|
| Apple corpus | Its verifier accepts checked-in genuine Apple sandbox fixtures for V2 notification, signed transaction, and renewal data, and rejects altered payload, signature, x5c, bundle ID, environment, and production app-ID cases. Fixtures contain no adopter data or credentials. |
| Independent verifier | A minimal Accrue JOSE/X.509 test verifier agrees with the library on all acceptance/rejection corpus cases. This prevents a library-specific parsing quirk from becoming access truth. |
| API contract | Fake Finch transport proves the exact authorization header shape, production/sandbox endpoint selection, status/history pagination/cursor handling, error classification, `429`, and retryable `5xx` mapping. No live key is needed. |
| Upgrade gate | CI runs the corpus against the resolved dependency version; dependency updates may not silently expand algorithms, accepted chains, or public Accrue types. |
| Supervision gate | `Accrue.Application` remains childless; a host-only integration test starts Finch/Oban and proves Apple calls/reconciliation work with those named resources. |
| Privacy gate | Fixture snapshots, telemetry, logs, diagnostics, and errors contain no `.p8` material, raw receipt body, customer email, device public key, or full offline token. |

If the package fails any security/correctness gate, retain the same behaviour and implement the limited v1 surface using host Finch plus JOSE and Erlang `:public_key` for certificate validation. Do **not** drop x5c validation merely to preserve package convenience.

## ES256 offline lease protocol

### Format and issuance

Use a compact, detached-from-server-state **JWS**, not an encrypted JWT and not a symmetric MAC. ES256 lets Crosswake verify offline using public keys without being able to mint a lease. Set the protected header exactly to:

```json
{"typ":"accrue-entitlement-lease+jwt","alg":"ES256","kid":"<active-key-id>"}
```

The canonical JSON payload must include:

`v`, `iss`, `aud`, `jti`, `sub` (account UUID), `device_jkt` (RFC 7638-style thumbprint of registered P-256 public key), `rev` (account projection revision), `iat`, `nbf`, `fresh_until`, `exp`, normalized effective plans/features/quantities, and `mode` (`fresh` or `stale_offline`). It must never include Apple transaction IDs, receipt/JWS content, email, user profile data, raw device key, or Stripe data.

Issuer requirements:

- load the active P-256 signing key through `KeyProvider.fetch_active/0`; allow a KMS/HSM-backed host implementation without changing token format;
- sign canonical JSON bytes with JOSE and the explicit `ES256` header, then self-verify the finished compact token with the stored public JWK before returning it;
- issue only after the account projection and revision have been read in the same DB transaction/snapshot that establishes its effective grants;
- preserve a generated `jti` and issuance audit record (hash/token metadata only) for diagnostics; the server never accepts a returned lease as fresh billing evidence.

### Offline semantics

The token has a **30-day revalidation target** (`fresh_until`). At `fresh_until`, client policy changes from normal access to `stale_offline`: continue the already-downloaded study/progress path, disallow fresh premium download, enrollment, export, purchase, account/rail mutation, or any other value expansion until online reconciliation succeeds. The client must show a reconnect-required state for restricted operations without deleting locally stored study material or progress.

There is **no independent 72-hour hard cutoff** in v1.59. `exp` must be an explicit signed protocol bound, normally aligned with a known provider access/revocation/period bound when one is sooner; it must not be computed as `fresh_until + 72 hours`. A provider refund/revocation discovered on reconnect increments the account revision and returns a signed deny/replacement lease. Offline access cannot react faster than the established revalidation opportunity, which is an acknowledged product tradeoff rather than a hidden grace stack.

Verifier requirements for Crosswake/host:

- select a cached public key by `kid`; enforce `alg == ES256` before cryptographic verification;
- validate issuer, audience, version, time claims with bounded clock skew, exact device thumbprint, account identity, and expected claim types/size;
- persist a secure monotonic high-water mark for `iat`, `rev`, and `fresh_until` to make a materially older lease or device clock rollback unusable;
- atomically retain the last valid lease while a network refresh is in progress; replace it only with a verified newer revision/issuance or explicit signed deny;
- treat client key compromise as device compromise, not a reason to make the server trust the device. Device binding limits token copying; it is not DRM.

## Key provider and rotation

Define a small host-implementable behaviour:

```elixir
@callback fetch_active() :: {:ok, %{kid: String.t(), private_jwk: JOSE.JWK.t(), not_after: DateTime.t()}} | {:error, term()}
@callback fetch_public(String.t()) :: {:ok, JOSE.JWK.t()} | :error
@callback verification_keys() :: {:ok, [%{kid: String.t(), public_jwk: JOSE.JWK.t(), retires_at: DateTime.t()}]}
```

Accrue provides an encrypted/runtime-env development implementation only if the project already has an approved secret convention; production hosts provide Vault/KMS/HSM or equivalent. Do not persist a private JWK in the billing database.

Rotation procedure:

1. Publish/add the new public key to the Crosswake key set and deterministic fixture bundle.
2. Make it the issuer key (`kid` changes) only after clients can obtain the key set.
3. Continue verifying prior keys until no valid issued lease can remain plus the documented clock-skew/reconnect buffer. Because this milestone has no 72-hour cutoff, calculate retirement from the longest actual signed `exp`, not a presumed 33-day formula.
4. For suspected private-key compromise, disable issuance immediately, publish/serve deny or forced-online policy at the next connection, and preserve audit evidence. Do not claim that an already-offline token can be remotely revoked.

Apple’s `.p8` credentials and Accrue’s offline signing keys are distinct key domains with distinct `kid`s, storage, rotation, telemetry, and incident runbooks.

## Deterministic fixtures and test stack

Produce public, synthetic fixtures in a versioned `test/fixtures/entitlements/` corpus (or generated checked-in files), never copied B2C Alpha data:

| Fixture set | Required cases |
|---|---|
| Apple V2 | verified sandbox notification/transaction/renewal examples; duplicate, delayed, out-of-order events; malformed compact JWS; bad signature; wrong bundle/environment/app ID; bad/too-long x5c; retryable OCSP failure; API status/history pagination. |
| Projection | Stripe-only survives Apple revocation; Apple-only survives Stripe cancellation; same logical plan deduplicates; quantity uses max; a revoked source does not erase a live other rail. |
| Offline lease | fixed P-256 test keys, stable `kid`, frozen clock, exact compact-JWS golden vectors, unknown key/algorithm rejection, wrong audience/device, stale-at-30-days behaviour, no-72-hour-cutoff assertion, newer revision replacement, deny replacement, clock rollback. |
| Crosswake contract | language-neutral JSON manifest containing public JWKs, token strings, expected decoded claims, expected verdict, and fixture protocol version. Crosswake verifies them independently. |

Use Mox behaviours for HTTP/Apple adapters and key providers, not global application environment mutation. Use existing clock seams/frozen time for expiration semantics. Apple sandbox interaction is an opt-in, credential-gated parity suite; deterministic conformance remains merge-blocking.

## Rejected alternatives

| Alternative | Decision | Why rejected |
|---|---|---|
| Hand-roll all Apple JWS/x5c verification in v1 | Reject as default | Certificate policy, OCSP, Apple environment/bundle checks, and nested JWS handling are security-critical. The fallback exists only if the third-party adapter fails corpus gates. |
| Trust Apple notification JSON after Base64URL decoding | Reject | Apple sends V2 `signedPayload` JWS; decoding does not establish provenance. |
| `app_store_server_library` as public domain model | Reject | It is third-party, current but young/low-adoption; swapping it must not be a breaking API or data migration. |
| JOSE alone as the Apple verifier | Reject | Strict JWS signature verification is necessary but insufficient; Apple needs pinned x5c path validation and bundle/environment/app-ID validation. |
| Symmetric HMAC offline token | Reject | Every offline verifier would hold a minting secret. ES256 gives verifiers a public key only. |
| JWT/Joken wrapper as the primary protocol dependency | Reject | The use case needs compact JWS, exact algorithm/key controls, and public-key operations. JOSE is lower-level, mature, and already sufficient. |
| Start Finch/Oban/cache worker in `Accrue.Application` | Reject | Violates established host-owned supervision and risks name, pool, runtime-config, and lifecycle conflicts. |
| Crosswake dependency or server-side client SDK in `accrue` | Reject | No verified shared public API and it would make core billing mobile-runtime-specific. Exchange fixtures and a protocol, not runtime coupling. |
| 72-hour stale-offline hard cutoff | Reject | Explicitly outside approved v1.59 policy. It would lock learners out contrary to the adopted offline-study requirement. |

## Compatibility and operational risks

- `app_store_server_library` may introduce a dependency/supervision/cache policy incompatible with Accrue’s host-owned posture. Inspect its child specification and dependencies during Phase 217; do not start it automatically. The adapter interface and corpus are the escape hatch.
- Apple credentials, environments, and app identifiers are configuration-sensitive. Fail loud at host boot for malformed Apple rail configuration, but preserve current Stripe-only boot/config as a supported default.
- OCSP is availability-sensitive. Treat temporary check failures as retryable quarantine; a network failure cannot become an entitlement grant or a broad revoke.
- Apple notifications are at-least-once and can be delayed/out of order. Only idempotent immutable evidence + repair status/history gives convergence.
- Offline proof’s worst-case stale exposure is a conscious 30-day revalidation tradeoff. Do not hide it with undocumented client policies, double-grace, or a 72-hour cutoff.
- Key rotation must be driven by actual issued-token horizon. Retiring an old key too early strands a valid offline learner; retaining it indefinitely enlarges compromise exposure.

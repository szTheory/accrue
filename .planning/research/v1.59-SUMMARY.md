# v1.59 Research Synthesis — Account-Scoped Multi-Rail & Offline Entitlements

**Milestone:** v1.59 / SEED-006  
**Status:** Canonical synthesis for this milestone  
**Date:** 2026-07-31

## Executive Summary

Accrue should add an account-scoped entitlement projection beside its existing gateway-processor model, not generalize the processor facade into a fake universal billing API. Verified Stripe and Apple evidence independently produces rail- and environment-qualified grants for one stable `EntitlementAccount`; a canonical snapshot unions effective plans/features and takes maximum quantities. Stripe remains controllable through its existing gateway lane. Apple is a verified observer/reconciler with explicitly externally managed lifecycle guidance.

The implementation must be additive. Existing single-processor configuration, `customer/1`, default associations, Stripe-shaped subscriptions, and the advisory-only Stripe `EntitlementSummary` retain their contracts. A multi-rail host opts into the account projection only after resource-aware gateway dispatch and scoped lookup remediation land. Apple evidence is linked solely by a verified UUID `appAccountToken`; unmatched or invalid material is quarantined and repaired, never heuristically assigned.

Offline access is a server-issued ES256, device-bound lease, not billing evidence or DRM. Successful reconciliation establishes a 30-day revalidation target. Once stale, already-downloaded study and local progress continue, while premium downloads and every other value-expanding action require reconnection. **There is no independent 72-hour cutoff in v1.59.** A signed explicit expiry may be shortened by a known provider access/revocation/period bound. On reconnect the server reconciles due rails and atomically replaces the cached proof with a newer lease or signed denial.

## Key Findings

### Product and scope

- B2C Alpha remains anonymized in all fixtures, documentation, telemetry, diagnostics, and tokens.
- Ship Stripe + Apple only. Google Play is explicitly deferred to SEED-007; do not turn rail seams into Android policy.
- Warn or block an equivalent second purchase from the account snapshot. Never automatically cancel, refund, transfer, migrate, merge, prorate, or select a preferred rail.
- Provider lifecycle is honest: Stripe may expose supported mutations; Apple returns an externally-managed capability/result and never enters Stripe dunning, cancellation, retry, swap, or proration paths.

### Public and data boundaries (recommended)

| Boundary | Recommendation | Non-negotiable rule |
|---|---|---|
| Gateway processor | Keep `Accrue.Processor` for controllable gateway resources | Do not add Apple lifecycle callbacks or turn `:processor` into a rail map. |
| Entitlements | New account projection, snapshot, eligibility, device, lease, and rail-observer APIs | Snapshot is the sole v1.59 multi-rail gate; `EntitlementSummary` remains advisory-only. |
| Account identity | Stable UUID `EntitlementAccount` | The UUID is the sole `appAccountToken`; never link by email, device ID, product ID, or unverified client claim. |
| Evidence and grants | Append/idempotently record observations, reduce through one `GrantProjector` | Scope all external identity by rail + environment + lineage; raw signed data is bounded and protected. |
| Mobile/Crosswake | Accrue owns protocol, fixtures, issuance, and public keys; host owns secure storage, verification integration, and UI policy | Do not add a Crosswake runtime dependency until the tracer proves its contract. |
| Runtime resources | Host owns Repo, Finch, Oban, secrets, pools, and key refresh lifecycle | `Accrue.Application` stays childless. |

### Technology and security posture

- Keep `lattice_stripe ~> 2.0` for the Stripe transport.
- Use `jose ~> 1.11` behind Accrue-owned issuer/verifier/key-provider behaviours for strict ES256 leases.
- Admit `app_store_server_library ~> 2.2` only behind an Apple adapter and only after corpus, API-shape, independent-verifier, supervision, and privacy conformance gates pass. Fallback is a small host-Finch + JOSE/`:public_key` adapter; never weaken Apple x5c validation for convenience.
- Apple JWS validation requires an ES256 allowlist, x5c chain validation to pinned Apple roots, certificate validity/usage checks, bundle ID, environment, and production app-ID checks where applicable. Nested signed data is verified separately.
- Lease verification requires fixed type/algorithm/issuer/audience, `kid`, device JWK thumbprint, account/revision/time checks, high-water rollback defense, atomic replacement, and deny-tombstone precedence.

## Accepted Tradeoffs

- Offline revocation cannot reach an already-disconnected device. The accepted control is revalidation/reconnect plus signed denial, not a hidden cutoff or a claim of remote DRM.
- Account-level access is rail-neutral; lifecycle remains rail-aware. This is intentionally not an all-provider billing abstraction.
- Duplicate prevention avoids accidental charges but does not solve finance/account ownership transfers. Exceptions are support-runbook work.
- Apple library convenience is secondary to a replaceable, fixture-tested adapter boundary.
- Crosswake is a contract consumer, not a server dependency; the tracer may block mobile-proof completion without invalidating core protocol work.

## Requirement Deltas and Supersession

| Topic | Canonical v1.59 requirement | Superseded wording to ignore |
|---|---|---|
| Offline timing | 30-day revalidation target; stale downloaded study/progress continue; expansion waits for reconnection; **no independent 72-hour cutoff** | Any 72-hour degraded/hard-expiry formula, `fresh_until + 72h`, or 33-day key-retention assumption. |
| Expiry/key retirement | `exp` is an explicit signed bound, normally shortened by known provider bounds; retire keys after the longest actually issued expiry plus skew/reconnect buffer | Fixed hard-expiry or key-retention arithmetic derived from the former 72-hour policy. |
| Crosswake | Feasibility tracer and deterministic protocol fixtures first | Assumed runtime coupling or undocumented client crypto API. |
| Purchase duplicates | Warn/block eligibility; no automatic migration | Auto-cancel, transfer, refund, proration, or ownership merge. |

The later v1.59 Stack research and the current task authority control this conflict. Earlier 72-hour language in the architecture signal, Features, Architecture, and Pitfalls research is historical input, not implementation policy.

## Confidence and Gaps

| Area | Confidence | Notes |
|---|---|---|
| Repository compatibility/remediation | High | Specific global dispatch and unscoped lookup hazards are identified. |
| Projection model and data boundaries | High | Durable accepted architecture and clear transactional invariants. |
| Apple protocol | Medium | Primary docs support the contract; sandbox conformance remains required. |
| Apple Elixir dependency | Medium-low | Relevant but young/low-adoption; admission is gated. |
| Offline crypto protocol | Medium-high | Standards-backed design; mobile verifier and storage must be proven. |
| Crosswake integration | Low-medium | Contract is clear; no verified public runtime API was found. |

Locked purchase default: an equivalent live grant on another rail returns a blocked eligibility result by default; hosts may render that result as a warning and explicitly override it, but Accrue never auto-cancels, transfers, refunds, migrates, or prorates. Remaining phase-level research gates—not milestone-scope ambiguity—are provider-to-logical-plan catalog syntax, bounded evidence retention, Crosswake secure-storage/high-water atomicity, Apple sandbox corpus, App Review region matrix, production reconciliation SLO thresholds, and key-compromise runbook authority.

# Automation and delivery seams

Use the existing acceptance lanes, strengthen named gaps beside each UI change, and retain one bounded agent inspection cycle per delivery batch. Target **zero required human UAT**. Owner feedback is optional subjective input after delivery. No new framework, parallel UI workflow, paid visual judge, or reactivation of the parked v1.56 ratchet is needed.

This is a source and evidence review for requirements/roadmap preparation. No app was started, fixture reset/reseed performed, implementation changed, or test suite executed. Fresh browser observations, effective styles, actual browser zoom, timings, and current screenshots remain delivery tasks. The [kickoff stocktake](../../notes/2026-10-09-admin-operator-impeccable-kickoff.md) reports the preview's HTTP 404 and verified historical capture fingerprints; this pass does not promote those captures into current browser proof. Remote CI, assistive technology speech output, physical touch devices, and live-provider outcomes were not observed.

Read Impeccable's `operate.md` and `audit.md` as planning lenses, without rerunning context/init/detector or producing a source-only aesthetic score. Operate favors familiar controls, consistent task vocabulary, and reachable investigation detail. Its generic 44px audit heuristic is not a WCAG AA threshold; use the precise standards below.

## Accessibility acceptance without invented thresholds

Use task completion and measurable criteria for touched controls; do not demand a new global certification or a human UAT round.

| Check | Precise basis / delivery acceptance |
| --- | --- |
| Keyboard and assistive semantics | Native control roles and accessible names; sensible focus order, visible focus, no keyboard trap, errors associated with their input, and updated status available without stealing focus. For modal behavior, exercise focus entry, Tab/Shift-Tab containment, Escape, and a logical surviving focus target on close. The [W3C dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) is interaction guidance; inspect long structured content instead of attaching the entire drawer as one description. Accessibility-tree/ARIA assertions are evidence of semantics, not observed screen-reader speech. |
| Contrast | Ordinary text at least 4.5:1; qualifying large text at least 3:1, with the stated exceptions. Required visual information for controls, states and meaningful graphics at least 3:1 against adjacent colors. Check actual backgrounds/compositing and controls in each effective theme. A border is not automatically a required identification cue. [Text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html). |
| Focus obstruction | WCAG 2.2 AA 2.4.11 requires the focused component not be entirely hidden by author content; full visibility is a stronger product goal, not the AA wording. Test actual scroll positions and sticky/overlay obstruction as well as a nonzero outline. [Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html). |
| Reflow | At an equivalent 320 CSS px width, non-excepted content must retain information/function without two-dimensional scrolling. A table's two-dimensional relationship may qualify for an exception; its cells, heading, filters and pagination do not inherit that exception. Preserve the existing responsive cards where helpful, without imposing cards on every content type. [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). |
| Zoom / enlargement | Resize text to 200% without lost content/function. Keep direct 320px and CSS `html.style.zoom = 2` stress checks, but label the latter **CSS zoom simulation**. It is not an observation of the browser's zoom control. In the bounded agent browser pass, exercise actual browser zoom, record the method/effective viewport, inspect changed list/detail/drawer controls, and reset it. If browser tooling cannot do so, state that limitation instead of claiming actual zoom. [Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html). |
| Coarse pointer | WCAG 2.2 AA 2.5.8 specifies 24 × 24 CSS px or its documented spacing/equivalent/inline/other exceptions. 44 × 44 is the enhanced AAA criterion, usable as an intentional larger target choice for frequent/consequential touch actions. A 24px minimum height alone proves neither criterion. Assert actual hit areas/spacing in the effective coarse-pointer mode and synthesize taps for touched shell/dismissal/action controls; emulation is not a physical-device claim. [Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum), [enhanced](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html). |
| Reduced motion | Reuse existing token and actual drawer-transform tests with their normal-motion negative controls. Retain immediate state/focus feedback when travel is suppressed; do not replace functional feedback with a blanket animation kill or add choreography to routine navigation. |

The cheapest faithful acceptance is a shared component assertion plus a representative mounted interaction wherever host styles, auth, direct entry, or patches matter. Axe is supplementary: [Playwright says automated checks cannot detect all WCAG violations](https://playwright.dev/docs/accessibility-testing). Zero required human UAT does not convert automated results into universal WCAG, screen-reader, or physical-device certification.

- **HTTP-only observer disposition — required:** Phase 239's `page.on("request")` non-GET collector observes page HTTP requests. For broader “no billing mutation” acceptance, reuse authoritative ExUnit state/dispatch/audit assertions on the same read-only path in the disposable fixture; if browser event recording helps, Playwright exposes [WebSocket `framesent`](https://playwright.dev/docs/api/class-websocket), but heartbeats/joins/filters must not be mislabeled writes. - **Capture provenance:** record application identity/HTTP response, route and query, fixture namespace, state, chosen preference and effective theme, viewport/zoom/input method, source revision plus changed-source fingerprints, served CSS/JS/font URLs and digests, browser/OS/lockfile, image digest, command/result and inspection notes. These dispositions reuse the documented ScryPath selection/busy/focus/cascade/evidence lessons, Threadline direct-entry/long-filter lessons, and Mailglass app-identity/freshness lesson. No additional broad sibling-project audit is needed.

## Visual baselines, volatility and bounded inspection

**Fail-closed expected snapshot set — required.** The current browser workflow checks whether *any* PNG exists before enabling pixels. The current eight PNGs exist; a missing individual expected image fails once the spec runs, but deletion of all PNGs would silently skip that gate. Replace the any-file condition with a complete expected-set contract derived from the existing spec's surface/theme names, including any explicitly added baseline. Missing all or part must fail. Do not weaken it by skipping the spec, auto-updating acceptance snapshots, raising pixel tolerances, or switching its job to advisory. Keep existing `threshold: 0.2` / `maxDiffPixelRatio: 0.01` unless a separate evidenced policy decision is made.

The existing spec masks absolute datetimes. `td:nth-child(4)` depends on subscription column order; broad “Started/Ends/Renews” text masks and the whole header renewal fact can hide labels/context after refactoring. On a touched baseline, use semantic timestamp-value locators, assert expected mask matches and that amounts/status/actions remain unmasked, and prefer fixed fixture time for a new stable exemplar if it is a small fixture-only change. Never mask money, state, actions, customer identity, error copy, or entire overlays to obtain a pass. `hideCaptureOnlyChrome` hides palette-related nodes; closed resting screenshots therefore cannot prove an open palette. Give a changed open state its actual interaction assertion and inspected capture.

Mint intentional golden updates using the existing Linux on-demand job after inspecting the intended composition and recording the baseline source/fixture/assets. The [Playwright visual comparison documentation](https://playwright.dev/docs/test-snapshots) explains environment-dependent rendering and snapshot review. Local macOS images help inspection but are not replacement Linux goldens. Eight old desktop baselines do not establish a current invoice, payment, recovery, coupon, Connect, or narrow composition.

Captures, defect scans, micro-edits and rebuilds all count in that cycle. Stop when named acceptance is met; reopen only for new named evidence or explicit owner feedback. A failed safety/behavior gate gets its necessary defect repair and targeted verification, not another aesthetic scoring round. No routine human sign-off is a finish dependency.

## Cost, flakiness, negative controls and performance

There is already duplicated work: `host-integration`'s `mix verify.full` runs the full host browser suite, followed by three `playwright-e2e` shards; group contracts and reduced motion also recur in older Admin guardrails. Preserve existing required gates. For each **new assertion**, name one semantic owner and extend its existing file/lane; do not add another wrapper/full-suite invocation or new workflow. A later consolidation requires measured equivalent coverage and is outside this cleanup's default scope. The separate real async search configuration and Braintree/provider lanes retain their existing purposes; Fake Admin styling work does not need new provider runs or provider claims.

Use locator/state/event readiness instead of new fixed sleeps; separate fixture setup time from assertion time. Keep the current one-worker/sandbox and isolated fixture paths unless the measured requirement demands change. Add a test-only controlled hold/error at the owning existing fixture seam for busy/update checks; do not hold production responses or infer busy coverage from a skeleton specimen. Correct failures at the owning selector/contract. Do not suppress failures by broad exclusions, retries, inflated timeouts, wildcard masks, or artifact disappearance.

During delivery, demonstrate the new guard catches its named failure using the cheapest relevant negative control: absent expected PNG; wrong served response digest; removed accessible name/hidden focus target; early reconnect enablement; wrong money/owner/duplicate dispatch. Prefer existing test runner/fixture self-tests or a reversible isolated mutation; do not build a new failure-injection platform. Restore the control and show the faithful check passing. Preserve existing negative controls (token parity, reduced-motion normal-mode tests, verifier self-tests) without rerunning their entire battery for every unrelated copy edit.

**Measured diagnostic baseline:** read-only byte census at the source head above: committed Admin CSS **130,089 bytes**, JS **156,747 bytes**, Geist Sans **56,800 bytes**, Geist Mono **58,048 bytes**; combined **401,684 bytes**. These are uncompressed file sizes, not served transfer, parse cost, load latency, or current render measurements. Archived plan “duration” fields measure work sessions, not UI performance or suite runtime. No current timing baseline was found in the reviewed v1.63 handoff evidence.

At the first fresh mounted exemplar, record served raw/encoded resource sizes, cold/warm load-to-task-ready and LiveView-ready times, representative filter/drawer response times, long tasks/layout shifts where the tool supports them, and focused-check setup/assertion elapsed time. Record fixture scale, browser/runner and cache state, and retain before/after samples under the same conditions. Use those measurements to declare a **diagnostic regression budget based on observed variance and the changed workload** before propagation; unexplained deterioration requires investigation. Do not invent “100ms”, Lighthouse scores, global p95s, Core Web Vitals field claims, or new blocking timing thresholds from this source-only pass. Routine CSS/copy work should not add a dependency, font, animation workload or duplicate network fetch without a task benefit and measured cost.

## Requirement-worthy gaps and order

These are promotion candidates, not newly activated requirement IDs:

1. **Serve and observe the actual changed exemplar:** current app/source/fixture/assets identity; computed typography/spacing/colors; desktop/narrow/theme states; diagnostic performance baseline. Rebuild package assets and ensure host compiled parity in the first slice.
2. **Preserve task safety and context:** existing auth/money/step-up/stale-target/duplicate/uncertain-state assertions alongside changed copy/controls; fresh direct entry and related/back/query context at each consumer journey.
3. **Exercise changing state:** real busy → idle control integrity, full keyboard/focus/validation paths, connected readiness and replaced controls, System effective theme/persistence, labeled coarse-pointer and zoom evidence. Add the focused check with the changed shared component or journey.
4. **Close evidence blind spots:** fail-closed expected pixels; HTTP-scoped read-only claims or authoritative mutation checks; capture provenance and volatility/mask policy; honest local/remote/provider/AT limits.

Checks must arrive **with their changes**, not wait for the final evidence phase. The first exemplar chooses the shared pattern and its acceptance owner. Billing and investigation propagation carry their scoped checks and current composition inspection. The last slice reconciles existing evidence, justified goldens, unresolved dispositions and the reachable feedback preview; it must not discover missing safety owners for the first time.

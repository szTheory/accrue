## People, jobs and scan order

Engineers and support/billing operators are equal primary audiences. A novice operator needs recognizable nouns, visible scope, a clear next step, and a consequence they can explain to a customer. An experienced engineer needs the same orientation plus exact identifiers, provider, actor, timestamps, source delivery, eligibility, unknown facts and payload evidence. A separate basic/expert mode would create two interfaces to maintain and is unnecessary for this cleanup.

| Job | First answer the operator needs | Evidence and controls that remain available |
|---|---|---|
| Find the correct billed account | Who is this customer, whose billing is it, and which provider record is involved? | Owner/account context, local and processor identifiers, scoped customer search and list results. Actor and billed entity must stay distinct. |
| Explain current billing and access | What is the subscription's lifecycle, amount/period, collection state and access consequence? | Exact money/currency, lifecycle boundaries, canonical entitlements and separately labeled provider observations, eligible actions and related invoices/payments. |
| Handle an invoice or refund | Which record, amount and supported action am I reviewing; what changes if I confirm? | Target identity, exact reviewed amount, provider limitations, material state, confirmation/step-up, current evidence after dispatch. |
| Investigate recovery | Which owner and UTC window am I reviewing, and what is the subscription's current state versus its campaign history? | Window, currency-specific metrics, current at-risk state, historical failure and campaign boundaries, safe links back to the originating view. |
| Investigate/replay delivery | What arrived, what processed, what is unknown, and which selected deliveries are still eligible? | Processor event ID, delivery status, attempt evidence, actor/source/derived events, live/test mode, bounded selection, payload and honest queue outcome. |
| Review discounts/Connect | What stored terms or readiness facts apply, and what local change is supported? | Coupon versus promotion-code relationship, expiry/redemption limits/provider; stored Connect snapshot uncertainty separate from local fee policy. |

Use **identity/scope → current state and exact amount or material boundary → supported next action → related evidence** as the default scan order. These are content priorities, not a mandatory four-column layout. Do not push a known failure, uncertain amount, authorization restriction, stale observation or action consequence into a closed section to shorten the page.

The current [DashboardLive](../../../accrue_admin/lib/accrue_admin/live/dashboard_live.ex) contains Customers, Find a customer, Subscriptions and recent audit activity. Several older KPI/attention/launcher helpers remain in `Copy` but are not rendered there. Treat the current Home as the incumbent; unused copy and old goldens do not authorize rebuilding its historical command center. Its shell already exposes the other jobs.

## State language and explicit exceptions

Provider-specific setup/fidelity boundaries must retain their factual meaning even when routine API narration is removed. Simplification must not conceal exact actor/source IDs, payloads, timestamps, live/test mode, relationship scope, failure reasons or unknown evidence. Lazy raw-data/activity disclosure is already an accepted pattern, not an absent engineering mode. Routine amounts, current lifecycle/blockers and eligible next actions need visible priority. Closing every disclosure, removing all dense tables, or replacing all buttons with a More menu would be taste-driven scope expansion.

## Reused sibling safeguards

The kickoff's documented sibling lessons justify focused acceptance, not assertions that Accrue currently has those defects:

- Command selection must have one authority: exercise pointer movement then ArrowDown/Enter and inspect both active row and ARIA.
- LiveView busy feedback must survive idle→busy→idle and later updates; markup-replacing disabled labels, disappearing icons and unstable hook IDs deserve actual activation checks.
- Corrected validation, dismiss/success and route/row replacement must return focus to a surviving element; an error outside an inert dialog is not a useful error.
- Long filters and unbroken identifiers need narrow/direct-entry coverage; clipboard paths, if touched, need actual success/failure evidence rather than icon presence.
- Stored System preference and effective light/dark theme are distinct; localized state colors and zero counts cannot establish billing health. Computed served styles establish consumption; token declarations alone do not.
- Identify the app/source/fixture/served asset before declaring a capture current. Do not infer a viewport-fixed overlay scrolling defect from a full-page screenshot. Preview remains read-only after login; mutation proof uses a disposable fixture.

Use the already agreed single inspection batch, one corrective batch and one confirmation ceiling for each delivery batch. No new aesthetic score, paid judge or follow-on audit loop is recommended.

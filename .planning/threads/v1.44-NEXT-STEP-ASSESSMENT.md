# Milestone Next-Step Assessment (v1.44)

**Assessment Date:** 2026-05-27
**Target Milestone:** v1.44

## 1. Framing & Current State
Accrue is a fully-featured, idiomatically Elixir billing library for Phoenix SaaS developers. With the recent completion of v1.39 (Entitlements), v1.40 (Dunning), and v1.41-1.43 (Search, Ad-hoc Invoices, and the 1.2.0 Hex Publish), Accrue has achieved **6 of 6 on the canonical SaaS loop** (bill → change/cancel → recover → self-serve → gate access → operate). 

**Current State:** 90-95% "done" for its core stated scope. The foundation is robust, the documentation is comprehensive, and the adopter story is complete. We are currently in an intake-gated maintenance mode. However, there are high-leverage "polish" wedges remaining that can dramatically improve developer/operator ergonomics and prove the library's ROI.

## 2. Adopter Coverage Map
- **Well-served:** Subscriptions, checkout, basic metering, webhook reconciliation, simple entitlements, email-based dunning, operator admin, local developer environments (Fake lane).
- **Partially-served / Still-rough:** Dunning visibility (no easy way for operators to see *how much* revenue the dunning engine is saving them); complex multi-channel notifications (in-app, SMS); rich metered/tiered entitlement math.

## 3. Candidate Research & Recommendations

We deployed subagents to evaluate the top deferred items. Here is the deep architectural and product analysis for each.

### Candidate A: Recovered-Revenue Analytics Dashboard (LiveView)
**Goal:** Add a "Money Saved" dashboard to `accrue_admin` visualizing the success of the v1.40 dunning engine.
- **Pros/Cons:** Proves the library's value instantly ("Accrue saved you $14k this month"). Keeps data inside Accrue rather than relying on disjointed Stripe metrics. The risk is scope creep into becoming a BI tool.
- **Idiomatic Elixir:** Standard PostgreSQL `group_by` aggregations over the existing `Accrue.Billing.Event` ledger. No heavy dependencies (like TimescaleDB). If performance degrades at massive scale, we can introduce Oban rollup workers later.
- **Lessons Learned:** 
  - *Baremetrics:* Frame it positively as "Recovered Revenue" rather than "Failed Payments".
  - *Laravel Spark:* Keep it simple. 3-4 high-signal charts. No complex filtering.
  - *Stripe:* Make it transparent. Allow operators to click a funnel drop-off and see the exact Oban job/timeline that triggered it.

### Candidate B: Multi-channel Dunning (In-App, SMS, Push)
**Goal:** Expand dunning beyond email using the Chimeway adapter or standard Phoenix tools.
- **Pros/Cons:** Dramatically higher recovery rates (SMS is 90%+ open vs Email 20%). Tiered escalation. However, SMS introduces TCPA/GDPR compliance risks, and hardcoding adapters bloats the library.
- **Idiomatic Elixir:** Accrue acts as the **state machine and scheduler**, not the delivery transport. Define an `Accrue.Dunning.Notifier` behaviour. Ship with a `Swoosh` default and `Chimeway` optional adapter. Let the host app handle actual delivery.
- **Lessons Learned:**
  - *ChurnBuster:* Provide secure magic links for frictionless, passwordless card updates.
  - *Stripe:* Separate the *retry* schedule from the *notification* schedule.
  - *Crucial Footgun:* The Oban worker **must** fetch live invoice status inside `perform/1` before triggering the Notifier to avoid "False Positives" (sending an SMS after the user already updated their card).

### Candidate C: Rich Metered/Tiered Entitlement Math
**Goal:** Enable volume discounts, graduated tiers, and complex usage math evaluated locally.
- **Pros/Cons:** Zero-latency entitlement checks (`Accrue.can?`); rich local UI (progress bars). But, replicating complex math risks synchronization drift with Stripe.
- **Idiomatic Elixir:** **Hybrid CQRS-style pattern**. Accrue is the source of truth for *authorization* (Read Path), but acts as an *event forwarder* for the actual *billing* (Write Path to Stripe). Configuration via `NimbleOptions`. Use integers/`Decimal` for precise math (never floats). Use `Enum.reduce` for graduated tier evaluation.
- **Lessons Learned:**
  - *Lago/Orb:* Avoid Postgres row contention for usage tracking. Use ETS/GenServer batchers for high-throughput `Accrue.track` calls.
  - *Race Conditions:* Limit checks must use atomic Postgres `UPDATE ... WHERE usage < limit RETURNING *` or Redis token buckets.

## 4. The Perfect Recommendation: The Highest Leverage Next Step

**The Pick for v1.44:** **Candidate A — The Recovered-Revenue Analytics Dashboard**

**Why:** It is the highest-leverage, lowest-risk next step. We just shipped the Dunning Engine (v1.40). Building a Baremetrics-style "Recovered Revenue" dashboard in `accrue_admin` instantly proves the ROI of Accrue to any adopter. It requires **zero new database tables** (relies purely on aggregating the existing event ledger), poses no compliance risk, and provides a massive DX/UX win. 

**What "Done Enough" Looks Like:**
- A single LiveView page in `accrue_admin` (`/analytics/dunning`).
- A Hero Metric: "MRR Recovered (Last 30 Days)".
- A simple Funnel Chart: Entered Dunning → Recovered → Exhausted.
- A drill-down table of "At Risk" subscriptions (campaign currently active).
- Public underlying Ecto query module (`Accrue.Analytics.Dunning`) so developers can build custom dashboards if desired.

**Suggested Ordering After v1.44:**
1. **v1.45:** Multi-channel Dunning (In-App Banners first, as they are low compliance risk and high impact for SaaS).
2. **v1.46+:** Park Candidate C (Rich Tiered Math) unless explicitly demanded by adopters. It is a massive undertaking that borders on "overbuilding" for a library currently in maintenance posture.

## 5. Blunt Maintainer Takeaway
*If I were you, what would I build next?*
Build the Recovered Revenue dashboard, then stop. You've hit the diminishing returns boundary for a foundational billing library. Accrue is incredibly strong. Don't turn it into a BI tool or a generic notification router. Build the dashboard to prove Accrue saves them money, add in-app dunning banners as a quick win later, and then let the community drive further feature requests.
